### 1.2 定位盲区（用户实际遇到的现象）

1. **HTTP 挂起无法定位**：100 页扫描 PDF ≈ 100+ 次 VLM 调用，HTTP 最长挂几十分钟；
   期间 `kb_document.status=0`，客户端无法得知卡在第几页、A/B/C 哪个通道。
2. **失败即失联**：客户端一旦断连/超时，文档永远停在 `status=0` 或 `2`，
   **无恢复、无重试、无明细**；`process
   failed_pages` 只随响应体返回一次，不落库，事后无从查起。
3. **观测空白**：VLM 环节的 token/耗时/失败在观测层是空的（诊断 Agent 也查不到）。
4. **进程内状态单点**：`BM25 内存索引 / reranker 信号量 / 断路器 / PostgresSaver 常驻连接`
   全部绑定单个 uvicorn worker；多 worker 部署时状态分裂，行为时好时坏，极难定位。

### 1.3 企业级标准处理方案（非简化版）

原则：**提交与执行解耦 —— HTTP 只负责收件，重活交给任务系统，状态全程落库可查、可恢复、可重试。**

#### 1.3.1 任务模型（DB 落库，不用内存队列）

新增 `ingest_job` 表：

```sql
CREATE TABLE ingest_job (
    id BIGSERIAL PRIMARY KEY,
    job_key VARCHAR(100) UNIQUE NOT NULL,        -- 幂等键：sha256(file_hash:user_id)
    user_id BIGINT NOT NULL REFERENCES kb_user(id),
    filename VARCHAR(500) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'queued', -- queued/running/done/failed/dead
    stage VARCHAR(30),                            -- parsing/chunking/embedding/indexing
    progress FLOAT DEFAULT 0,                     -- 0~1 进度
    step_detail JSONB,                            -- 分页/分阶段明细 [{page, channel, status, ms, token}]
    error TEXT,                                   -- 最近错误信息（含可定位上下文）
    attempt INT DEFAULT 0,                        -- 重试次数
    max_attempts INT DEFAULT 3,
    trace_id VARCHAR(50),                         -- 关联全链路 trace
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

- 幂等键：同文件同用户重复提交 → 返回已有 job，不重复解析（延续现有 `file_hash` 去重语义）。
- 状态机：`queued → running(stage 细分) → done | failed | dead`，`updated_at` 每次变更刷新。

#### 1.3.2 API 语义变更（202 Accepted）

- `POST /api/ingest/upload`：校验文件后**立即**返回 `202 { job_id, status: "queued" }`，不等待处理。
- `GET /api/ingest/jobs/{job_id}`：轮询进度（前端 Documents 页按需轮询或 SSE 订阅进度）。
- `POST /api/ingest/jobs/{job_id}/retry`：人工重试入口（面向 `failed/dead`）。
- 失败明细：`step_detail` 记录每一页/每一阶段的失败原因，用户和管理员可直接看到"第 37 页通道 C 转录失败（VLM timeout）"。

#### 1.3.3 后台执行器（worker）

- 独立进程（区别于 API 进程），从 `ingest_job` 取 `queued` 任务：
  - 单 worker 串行消费（本地资源受限的客观约束，不属简化——显式声明并文档化；
    生产环境可横向扩展 worker 数）。
  - `SELECT ... FOR UPDATE SKIP LOCKED` 抢任务，天然支持多 worker 并发消费。
- 步骤逐级更新：每解析一页/每完成一个阶段，`UPDATE ingest_job SET stage, progress, step_detail`。
- 失败重试：按 `attempt` 指数退避重试；超过 `max_attempts` → `dead`（死信），
  人工通过 retry 入口恢复。
- 断点续跑：job 持有 `parse cache`（现有 `data/parsed/{hash}.json` 机制可复用），
  页面级 VLM 结果已有 hash 缓存，**重试几乎零成本**。

#### 1.3.4 可观测补全

- `vlm.py` 调用结果回传 token / elapsed，写入 `step_detail` 与观测层（修掉写死 0 的注释欠账）。
- 每个 job 贯穿 `trace_id`（复用现有 `X-Request-ID` 关联设计），web 侧日志可串联
  任务创建 → 页面解析 → VLM 调用 → 向量化 → 入库完成。

#### 1.3.5 前端

- Documents 页：上传后进入任务列表，轮询 `jobs/{id}` 渲染进度条 + 阶段文案 + 末次错误；
  失败提供「重试」按钮。禁止"整页 loading 等到天荒地老"的现状。

#### 1.3.6 验收口径

1. 提交 50MB 扫描 PDF 后 1s 内拿到 `job_id`，HTTP 不挂起。
2. 轮询进度能看到 page 级明细；人为断网后 job 停留在最后成功页，恢复后**可续跑**。
3. 模拟第 N 页 VLM 失败 → `step_detail` 精确到页与原因；重试后跳过已缓存页直接续跑。
4. 多实例启动 2 个 worker，任务不重复消费（SKIP LOCKED 生效）。

## 二、其余同类问题（同轮备案，待用户按节奏逐项处理）

### 问题二：Agent 问答链路全程同步 invoke，环节失败被吞成"正常降级结果"

- **证据**：`rag-python/src/agent/main_graph.py` — `route_node`(88)、`grade_node`(198)、
  `reflect_node`(254)、`rewrite_node`(214) 全部 `except LLMError: 降级默认值`；
  `stages` 只记 `{stage: ms}`，无失败/重试/降级标记；`qa_log` 只落耗时聚合。
  complex 档串行 4~5 次 LLM 调用，单请求最坏 20+ 分钟，HTTP 全程同步挂着。
- **影响**：用户得到平庸/错误答案时，无法判断是检索差、route 判断失败、还是 generate 降级。
- **标准做法**：降级显式化 —— 每节点失败写入 `state.degraded_reasons[]`，
  随响应与 `qa_log` 落库；API 响应增加 `degraded` 字段；SSE 全程分阶段事件
  （route/retrieve/generate 逐段发事件，前端显示步骤条，区分"思考中"与"卡死"）。

### 问题三：HITL 审批的 suggest 阶段同步跑两轮完整回归评估

- **证据**：`rag-python/src/agent/approval_graph.py:41-48` — `submit_change` 同步
  `graph.invoke`，先跑 current 回归再跑 candidate 回归（40 题 × 2），阻塞数分钟；
  评估失败只记 `compare.note="回归对比失败"`，审批照走，审批人拿到无数据依据的单子。
- **标准做法**：suggest 任务化（复用 1.3 任务模型），或至少异常落单可见 +
  前端明确标注"评估数据缺失，请人工判断"。

### 问题四：全局异常吞细节且响应不回带 trace_id

- **证据**：`rag-python/src/api/app.py:24-37` 未捕获异常统一"服务内部错误"（日志有堆栈，
  这是对的），但**错误响应不含 trace_id / correlation ID**；Java 网关异常响应
  （`rag-java/.../ChatController.java` `rootMsg`）剥到最底层 cause，
  两层叠加后真实根源黑盒化，用户报障无定位凭证。
- **标准做法**：全局 handler 与 SSE error 事件统一 `{error, trace_id}`；
  网关透传 trace_id 回前端与审计表，报障可凭 ID 串日志。

### 问题五：进程内状态全部依赖单进程同步模型

- **证据**：`bm25_index.py` 全量内存索引（懒加载+版本号）、`reranker` 信号量限 1 并发、
  `circuit_breaker` 状态、`PostgresSaver` 常驻连接 —— 全绑定单 uvicorn worker；
  同步长调用（LLM 120s）占满 worker，单 worker 下一个慢请求拖垮所有用户。
- **标准做法**：显式声明单 worker 部署并文档化（客观资源约束不属简化）+
  进程内状态（BM25 至少迁移为 DB 侧或可重建的共享状态）结构化考虑；
  至少将「单 worker 假设」从隐式改为显式可配置与启动校验。
