## 三、用户协作规范（硬性要求，违反会严重影响体验）

### 沟通
- **全程中文**交流；技术术语保留原文
- **大白话**讲解，别堆术语；每条结论/问题**标注影响**（用户会问"这影响什么"）
- 用户明确要求**挑战性讨论**：不要顺着他的想法说话，像同事一样质疑、给反面观点；他自认理解可能不对，需要的是深度讨论伙伴

### 动手前（最重要）
- **任何实质性操作前必须确认**：创建文件、写代码、改文件、跑命令——先说明要做什么、怎么做，等用户确认
- **方案先对话沟通再出正式计划**，不要直接甩计划让用户审批
- **方案偏离时暂停汇报**：遇到依赖缺失/环境问题导致原方案不可行，不要自行切换备选方案——列出原方案/备选方案/优劣，等用户决策

### 红线（用户三令五申）
- **严禁以"项目规模小/用不上/不值得/成本高"为由简化功能**——用户定位是面试项目但以真实企业级标准开发，功能默认要做，不做必须有技术原因且由用户决策
- **密钥绝不进 git、绝不写入长期记忆**（.env 管理，.gitignore 保护）
- **推断必须有证据**：无法验证的事实（如账号类型）明说"无法判断"，禁止凭格式/经验断言（用户会连续追问"你为什么这么认为"）

### 工程习惯
- **测试双验收**：每个功能阶段跑正常测试 + 边界测试（参数越界/越权/并发/安全），全部通过才继续
- **部署验证闭环**：部署后必须校验提交号 + 特征串 + 服务 active（不能只看"服务起来了"）
- **临时脚本用完即删**（服务器 /tmp 和本地 scripts/ 都要清）
- **PowerShell 5.1 环境**（本地 Windows）：复杂 Linux 命令一律"写脚本 → scp → 执行"模式，不要内联嵌套引号；管道输出会乱码/吞输出，长任务输出落盘再拉回
- **代码一致性**：改代码先读周边实现（复用工具前确认返回格式）；DB 迁移脚本要幂等
