# 坑位记录

> 开发过程中踩过的坑、以及已识别但未处理的隐患。**持续追加**：每踩一个新坑（或发现新隐患）就追加一条。
> 部署到云服务器前，本文件必须整体过一遍。

## 1. 【已踩·已修】X-Forwarded-For 可伪造，绕过 IP 限流

- **现象**：`AuthRateLimiter.getClientIp()` 优先取 `X-Forwarded-For` 头，客户端可直接伪造该头（如 `X-Forwarded-For: 203.0.113.101`），从而绕过"每 IP 每分钟 N 次"的注册/登录限流。
- **原因**：本地开发无反向代理，限流器只能信任客户端提供的头。
- **影响**：攻击者可无限注册/爆破登录（账号锁定仍按 username 生效，但 IP 维度限流失效）。
- **修复方案/处理**（已实施，2026-08-21）：新增 `ClientIpResolver`——默认（`GATEWAY_TRUSTED_PROXIES` 为空）完全忽略 XFF、仅用直连 IP（fail-safe，伪造 XFF 立即无效）；配置可信反向代理（IP/CIDR 列表）后按标准代理链语义从右往左取第一个非可信代理 IP（客户端预置伪造链也不怕：nginx 追加真实 IP 在最右）。支持 IPv4/IPv6/IPv4-mapped 归一化。验证：JUnit 6 用例（无代理忽略/可信代理/CIDR/伪造链/全代理回退/IPv6）全过；集成实测连续 4 次注册换 4 个伪造 XFF，第 4 次 429。

## 2. 【已踩】PowerShell 5.1 读取 UTF-8 无 BOM 脚本乱码

- **现象**：`.ps1` 脚本含中文且为 UTF-8 无 BOM 时，PowerShell 5.1 按系统 ANSI（GBK）解析 → 语法错误/中文断言乱码。
- **原因**：Windows PowerShell 5.1 默认用 ANSI 代码页读取脚本文件，不识别无 BOM 的 UTF-8。
- **规避**：写含中文的 `.ps1` 脚本时确保带 UTF-8 BOM（`[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding $true))`）。
- **注意**：PowerShell 7+ 默认 UTF-8，无此问题——但云服务器 Windows 环境若用 5.1 必须带 BOM。

## 3. 【已踩】psql 读取 UTF-8 SQL 文件报编码错误

- **现象**：`psql -f xxx.sql`（SQL 含中文注释，UTF-8 编码）报 `编码"GBK"的字符...在编码"UTF8"没有相对应值`。
- **原因**：Windows 下 psql 客户端按 GBK 读取 SQL 文件。
- **规避**：执行前设置 `$env:PGCLIENTENCODING="UTF8"`，或 SQL 文件转 GBK。
- **注意**：云服务器 Linux 环境无此问题，本地 Windows 开发必踩。

## 4. 【已踩】注册接口限流会干扰验收脚本

- **现象**：注册限流为每 IP 每分钟 3 次；验收脚本连续注册多个账号时命中 429，导致后续用例失败。
- **规避**：验收脚本的注册类用例间隔 ≥21 秒，或使用伪造 XFF 分散 IP（见坑 1）。
- **注意**：两个验收脚本（`verify_auth_step1.ps1` 与 `verify_files_step1.ps1`）不要紧接着跑，否则后者注册会被前者耗尽限流窗口。

## 6. 【已踩·已修】安全默认值写死在配置（Java 与 Python 双端补齐）

- **现象**：`GATEWAY_JWT_SECRET`、`GATEWAY_INTERNAL_API_KEY`、`SPRING_DATASOURCE_PASSWORD` 均有默认值，未设置环境变量时使用默认值运行（启动时有警告）；Python 侧 `config.py` 的 `PG_DSN` 也硬编码默认密码 `postgres:root`。
- **影响**：默认 secret 可被猜测 → JWT 可伪造；默认内部 key 若与 Python 侧不一致会导致网关签名校验全 403；默认数据库密码若被部署到公网库可直接登录。
- **修复方案/处理**（已实施，2026-08-21）：Java 侧 application.yml 全部改为无默认值（`${VAR:}` 空）+ `SecurityStartupValidator` fail-fast + `scripts/start-gateway.ps1` 从 .env 注入；Python 侧 `config.py` 的 `PG_DSN` 同样改为无默认值，缺失时启动即抛 `RuntimeError`（与 Java 网关策略对齐），并保留 prod profile 下 root 密码 fail-fast。验证：Python 侧 monkeypatch 隔离 .env 后无 PG_DSN 拒绝启动、正常路径不受影响；pytest 135 全过。

## 7. 【已踩】验收脚本断言基于假设而非实现语义

- **现象**：阶段 1a 边界测试里，重命名 "a/b.txt" 时断言预期为 "a_b.txt"（假设清洗=替换下划线），实际实现返回 "b.txt"（`getFileName()` 取路径最后一段），测试失败。
- **原因**：写断言时凭直觉假设了清洗行为，未先确认 `sanitizeFilename` 的实际语义（取最后一段是防穿越的第一道防线，比替换更严格）。
- **影响**：测试脚本报 FAIL，但失败的是断言本身而不是代码——浪费一轮排查，且差点误判为 bug。
- **规避**：写验收脚本断言前，先读目标代码确认其真实语义（尤其是安全类行为：清洗/截断/归一化的具体规则），再写断言；断言与实现不一致时，先判断哪个对，而不是默认实现错。

## 8. 【已踩】curl 输出的中文经 PS5.1 管道解码乱码，中文断言全失败

- **现象**：阶段 1b 边界测试用 `curl.exe` 上传并解析响应 JSON，脚本内对 `error` 字段的中文字符串比较（"文件类型与扩展名不符"）全部失败——但功能实际正确（错误信息确实返回了）。
- **原因**：curl.exe 输出 UTF-8 字节，PowerShell 5.1 从外部程序管道接收输出时按系统 ANSI（GBK）解码 → JSON 中的中文变乱码 → 与脚本内中文字面量比较永远不等。
- **影响**：3 项断言误报 FAIL，且误判方向是"功能坏了"，浪费排查。
- **规避**：验收脚本中不要比较 curl 管道输出里的中文；改为断言结构（`$null -ne $resp.error` 而非 `$resp.error -eq "中文"`），或改用 Invoke-RestMethod（内部处理编码）并捕获异常取状态码。

## 9. 【已踩】配额边界测试算错：恰好等于上限应放行

- **现象**：阶段 1b 配额测试把占用设为 QUOTA-10、上传 10 字节 → `used+size == QUOTA` 恰好相等，上传被放行，断言失败。
- **原因**：边界语义是 `used + size > quota` 才拒绝（等于上限合法），测试构造"差 10 传 10"恰好等于，命中合法边界。
- **影响**：误报功能 bug，实为测试设计错误。
- **规避**：写边界测试时先明确"临界点语义"（> 拒绝 / >= 拒绝？），构造用例时要超临界点至少 1 个单位（占用 QUOTA-1、上传 ≥2 字节）。

## 10. 【已踩·已修】DigestInputStream 只包剩余流，文件头没进 hash

- **现象**：阶段 2 秒传测试：A 上传文件后 B check-hash 永远不命中。服务端存的 hash 与真实文件 sha256 不一致。
- **原因**：魔数校验先读 1024 字节文件头，写盘时用 `SequenceInputStream(head, in)` 拼接——`DigestInputStream` 只包了 `in`（剩余流），文件头没进摘要。
- **影响**：秒传体系全链路失效（hash 错 → 永不命中 → 永远全量上传），且测试前无法发现（上传本身不校验 hash 正确性）。
- **规避**：`DigestInputStream` 必须包在拼接流**外层**（`new DigestInputStream(new SequenceInputStream(...))`），保证每个读出的字节都进摘要。写盘与算 hash 共流时，先想清楚"哪一层流覆盖了全部字节"。

## 11. 【已踩】PS 5.1 Invoke-RestMethod 按 ANSI 解码 UTF-8 JSON 响应

- **现象**：阶段 2 NFD 测试：服务端存库文件名正确（hex 验证 café.txt），但 PowerShell 从列表响应里读到的 filename 是乱码（caf??.txt），非 ASCII 断言全失败。
- **原因**：PowerShell 5.1 的 Invoke-RestMethod 解析 JSON 响应时忽略 charset，按系统 ANSI（GBK）解码 UTF-8 字节。
- **影响**：所有含非 ASCII 字符的响应断言都不可靠（之前中文断言"碰巧"没触发是因为只查 error 字段存在性）。
- **规避**：验收脚本中涉及非 ASCII 字符串的响应断言一律用 Python requests 完成（正确解码 UTF-8），PowerShell 只做 ASCII 断言/状态码断言。

## 12. 【已踩】测试残留污染：固定测试内容 → 固定 hash → 重跑必炸

- **现象**：阶段 2 normal 脚本第二次跑，blob ref_count=6（预期 3）——前一轮跑的活跃引用还挂在 blob 上。
- **原因**：秒传按内容 hash 去重，测试文件内容固定 → hash 固定 → 重跑时新引用叠加在旧引用上，
  引用计数断言基于"干净环境"必然失败。
- **影响**：误报功能 bug（实际 ref_count 与真实引用完全一致，代码正确）。
- **规避**：涉及共享数据（按 hash/blob 维度）的测试脚本，开头必须清理目标 hash 的全部残留（先删 user_file 引用再删 blob），保证环境干净后再跑。

## 13. 【已踩·已修】ResponseEntity<?> 返回 ResourceRegion 被 Jackson 序列化（500）

- **现象**：阶段 3 Range 下载测试：`GET /download` 带 Range 头返回 500，日志报 `HttpMessageConversionException: No serializer found for ... sun.nio.ch.ChannelInputStream`，引用链是 `ResourceRegion[resource]->FileSystemResource[inputStream]`。
- **原因**：Controller 返回类型 `ResponseEntity<?>` 泛型擦除为 Object → `ResourceRegionHttpMessageConverter.canWrite(Object, ...)` 的 `ResourceRegion.class.isAssignableFrom(Object.class)` 检查失败被跳过 → 退化为 Jackson 把 ResourceRegion 当 JSON 序列化（Jackson 能序列化任何类型）。
- **规避**：下载/文件流类接口返回类型必须写死（`ResponseEntity<Resource>` / `ResponseEntity<ResourceRegion>`），不能用 `<?>`——返回类型决定消息转换器选择。

## 14. 【已踩·已修】Spring 6.2 下 ResourceRegionHttpMessageConverter 写 206 时响应头已冻结

- **现象**：把 download 返回类型改成 `ResponseEntity<ResourceRegion>` 后，converter 被正确选中，但又报 `UnsupportedOperationException`（`MultiValueMapAdapter.add → UnmodifiableCollection.add`），栈在 `ResourceRegionHttpMessageConverter.writeResourceRegion` 的 `headers.add(Content-Range)`。
- **原因**：Spring 6.2 的 `ServletServerHttpResponse` 在写 body 前置 `headersWritten=true`，之后 `getHeaders()` 返回只读副本；ResourceRegionHttpMessageConverter 内部还要往响应头追加 Content-Range/ACCEPT-RANGES → 只读集合 add 抛异常。
- **规避**：不依赖该 converter——自算区间（HttpRange.getRangeStart/getRangeEnd + 越界 416 判断）后返回自定义切片 Resource（AbstractResource 子类，getInputStream 里 skip + 限长流），头全部在 Controller 层设置。

## 15. 【已踩】测试数据撞秒传：init 命中返回 hit 无 upload_id

- **现象**：阶段 3 边界测试：B 的非法序号/超大小用例全部 404（日志里 URL 是 `/upload//chunk`，upload_id 为空）；hash 篡改用例的 UPDATE 语句报 psql"语法错误在输入的末尾"（`WHERE id=` 后为空）。
- **原因**：B 的测试文件与 A 的内容相同（同为 25MB 全零）→ A complete 入库后 B init 秒传命中 → 响应只有 `{hit:true}` 没有 upload_id；而"秒传命中"正是服务端正确行为，脚本没料到。
- **规避**：需要真实会话的用例必须用与已入库内容不同的文件；测试用例先自问"这条期望命中秒传还是落空"，再决定用哪份数据。

## 16. 【已踩】Invoke-RestMethod 遇 4xx 抛异常中止脚本（ErrorActionPreference=Stop）

- **现象**：阶段 3 边界测试"分片缺失 complete 拒绝"用例：服务端正确返回 400，但 Invoke-RestMethod 对 4xx 抛异常 → 脚本直接终止（后续用例没跑）。
- **原因**：`Invoke-RestMethod` 对 4xx/5xx 视为错误抛出；`$ErrorActionPreference="Stop"` 下无法继续。
- **规避**：定义 PostJsonCode/UploadChunkCode 辅助函数（curl.exe 输出到临时文件 + `-w "%{http_code}"` 拿状态码 + .NET ReadAllText 按 UTF-8 读 body），统一处理"期望 4xx"的请求；另外 curl 对 4xx 不抛异常，不能包进 HttpStatus{} 断言（会误报 200）。

## 17. 【已踩·已修】uploadInit 缺 IllegalArgumentException catch：业务拒绝变成 500

- **现象**：阶段 5a 边界测试：磁盘阈值调大后，整传返回 400（正确）、分片 complete 返回 400（正确），但**分片 init 返回 500**。
- **原因**：`FileController.uploadInit` 调 `createUploadSession`（会抛"磁盘空间不足"/"会话数超限"等 IllegalArgumentException），但 init 端点没有 try/catch——整传/complete 都有 catch → 400，唯独 init 漏了，异常冒泡成 500。
- **规避**：新增端点时，业务拒绝异常（IllegalArgumentException）的 catch → 400 是**基线要求**，与既有端点对齐；验收脚本把"同一条拒绝路径在不同端点上"都测一遍（整传/init/complete 三处磁盘拒绝全测），能抓出这种"同一错误语义不同端点不一致"的问题。

## 18. 【已踩】新增 .ps1 脚本忘转 UTF-8 BOM：中文语法错误

- **现象**：阶段 5a 写 `start-gateway.ps1`（含中文注释）后直接运行，PS 5.1 报"表达式或语句中包含意外的标记""字符串缺少终止符"等解析错误。
- **原因**：坑位 2 的复发——Write 工具创建的文件是 UTF-8 无 BOM，PowerShell 5.1 按 ANSI 解析中文 → 语法错乱。

- **复发记录**：R6 阶段新写的 verify_rag_r6_normal/edge.ps1 又忘转 BOM，PS 5.1 报"字符串缺少终止符"——转 BOM 后正常。规则升级：**Write 工具写完含中文 .ps1 后立即转 BOM 是固定动作，不再等报错**。

## 19. 【已踩】变量名不一致：yml 读 GATEWAY_INTERNAL_API_KEY，.env 只有 INTERNAL_API_KEY

- **现象**：阶段 5a 环境变量 fail-fast 落地后，启动脚本报"缺失 GATEWAY_INTERNAL_API_KEY"——.env 里只有 Python 侧用的 INTERNAL_API_KEY，两个名字指同一把钥匙。
- **原因**：yml 的变量名（GATEWAY_INTERNAL_API_KEY）与 .env 的历史变量名（INTERNAL_API_KEY）不一致；之前有默认值兜底所以从未暴露。
- **规避**：跨服务共用的配置用 Spring 嵌套占位符回退 `${GATEWAY_INTERNAL_API_KEY:${INTERNAL_API_KEY:}}`（新名优先、旧名兜底）；部署时统一用标准名，两侧只维护一个变量。

## 20. 【已踩·已修】extractExt 返回带点扩展名：白名单集合格式不匹配导致全拒

- **现象**：上传白名单落地后，`.txt`（白名单内）上传也返回 400"不支持的文件类型"——`checkAllowedExtension` 的 `contains` 永远 false。
- **原因**：`extractExt` 第 683 行 `return "." + ext`（**带点**，如 `.txt`，MagicBytes 注释明确写过"ext 小写扩展名（带点，即 extractExt 的输出）"）；但写白名单时凭"注释里写了白名单校验"就假设输出**不带点**，集合存的是 `txt` → `contains(".txt")` 永远 false。
- **规避**：这是坑位 7"断言基于假设"的复发——**调用既有工具方法前，读实现确认返回格式是写调用方代码的前置步骤**，尤其涉及字符串格式（带点/不带点、大小写、是否 trim）时不能凭注释推断。

## 21. 【已踩·已修】秒传复用 blob：worker 用 user_file 归属拼路径导致物理文件缺失

- **现象**：R6 worker 解析秒传文件（内容与已入库文件相同）全部 failed"物理文件缺失"；同一用户新内容的文件解析正常。
- **原因**：物理存储按**首个上传者目录**组织——`data/files/{file_blob.owner_user_id}/{stored_name}`（秒传只建 user_file 引用，不复制物理文件）。worker 初版用 `user_file.user_id` 拼路径，秒传文件的 owner 与当前用户不同 → 路径不存在。
- **规避**：跨表拼物理路径时，**归属关系看 file_blob.owner_user_id 而非 user_file.user_id**（user_file 只是引用；file_blob 才是物理文件的事实来源）。同理预览/下载等任何读物理文件的路径，都要以 blob 的 owner 为准。

## 22. 【已踩·已修】PS 5.1 Invoke-RestMethod 对无 charset 的 JSON 响应按 ISO-8859-1 解码：中文断言必失败

- **现象**：R6 预览接口返回的 JSON（Spring 无 charset 声明）中文全部乱码，`-like "*第一章*"` 断言失败；同一响应里 ASCII 标记（MD-HEADER-001）匹配正常。
- **原因**：PS 5.1 的 Invoke-RestMethod 在响应头无 charset 时默认按 ISO-8859-1 解码（curl.exe 反而正确处理）；与坑位 19 的"curl 输出经管道被 GBK 重读"是**两个不同机制**。
- **规避**：PS 5.1 测试脚本对 JSON 响应做**中文内容断言时，在源数据里埋 ASCII 标记**（如文件内容含 `MD-HEADER-001`），断言匹配标记；或改用 .NET HttpClient/curl 输出文件 + ReadAllText(UTF8) 读回。

## 23. 【已踩·已修】uvicorn 重启失败 ModuleNotFoundError：WorkingDirectory 必须指向包所在目录

- **现象**：验收脚本用 Start-Process 重启 qa 服务（`-m uvicorn qa.app:app --port 8091`），重启后端口无监听，edge 测试“qa 恢复后正常”失败，且测试结束后服务缺失。
- **原因**：`qa` 包位于 `rag-python/src/qa`，Start-Process 的 `-WorkingDirectory` 指向 `rag-python`（src 的父目录），uvicorn 按当前目录解析模块找不到 qa → ModuleNotFoundError 退出。

## 26. 【已踩·已修】Spring SseEmitter 输出 `data:` 前缀无空格：前端 startsWith('data: ') 静默丢全部事件

## 28. 【已踩】pgvector 列写入必须用 register_vector 显式连接注册

## 37. 【已踩·已修】FastAPI 假并发：async def 端点里跑同步阻塞调用，一个请求独占事件循环

- **原因**：FastAPI `async def` 端点中的同步阻塞调用不释放事件循环；LLM 客户端是同步 httpx，流式迭代同样同步。模型层实测反而没问题：embedding 并发 10 仅 42ms（ORT 线程安全），rerank 有 Semaphore(1) 串行排队但超时会降级 RRF 不阻塞。**最隐蔽的是框架层**：假并发比模型层串行严重一个数量级，且本地单用户验收永远暴露不了。

## 39. 【已踩·已修】子进程管道改造引入超时回归：stderr 同步遍历阻塞 wait(timeout)，kill 永不触发

- **现象**：解析进度回报改造（subprocess.run 改 Popen 边跑边读进度）后，`test_timeout_kill` 失败——慢解析子进程预期被超时 kill 返回 failed，实际返回 success。
- **原因**：改造时先写 `for line in proc.stderr:` 同步遍历（读页级进度行），再 `proc.wait(timeout)`——子进程 sleep 期间 stderr 无 EOF，循环阻塞在 for 上，**wait(timeout) 根本没被执行**，超时机制整体失效；子进程最终正常完成输出结果。管道读取方式改变引入的时序回归：原来的 subprocess.run 内部正确实现了 wait+kill。
- **影响**：超时 kill 是解析域防御层核心（异常文件拖死管线），失效意味着恶意/损坏文件可无限期占用 worker。既有 pytest 用例（test_timeout_kill）在改造后立即抓到回归——**测试先行的价值直接体现**。
- **修复方案/处理**：stdout 与 stderr 均改为读线程（daemon + join timeout），主流程**先** `proc.wait(timeout)` 保证超时 kill 生效，读线程边跑边解析 RAG_PROGRESS 进度行回调。验证：pytest 135 全过；PDF 页级进度回调正常（2 页 → 0.25 → 0.45）。教训：**改子进程 IO 模式时，先想清楚"谁在阻塞等谁"——主流程的 wait 必须独立于任何管道读取，否则超时/终止路径全部失真**。

## 41. 【已踩·已修】`.gitignore` 的 `_*.py` 误伤 `__init__.py`：包初始化文件从未入库

- **现象**：级联（双通道共识→免精排）在黄金集命中 1 题——refuse 越界题"红烧肉的做法"，跳过 rerank 后 top1 是"图片无法显示。请提供可访问的图片链接"块（chunk_type=image，VLM 失败产物，BM25 分 19.577 词面命中）；而 rerank 路径正确地把该块压下去（top1 换成 -3.912 的食堂菜单块）。

- **影响**：级联跳过把垃圾块当高置信上下文（rerank_skipped=True → low_confidence=False），丢掉 rerank 的纠错能力；若不修复，越界题/垃圾块场景可能顺着垃圾上下文编答案。
- **修复方案/处理**：共识判据排除低质量块（chunk_type=image + PLACEHOLDER_MARKERS 内容匹配均无共识资格）；修复后黄金集 0/40 误跳，简单直问（词面直查）命中且 top1 与 rerank 完全一致。教训：**启发式判据（级联/跳过）必须验证误判率，且要排除"无资格代表证据"的数据源（解析失败产物）；rerank 的价值恰恰是纠错这类误排，跳过它必须有强证据背书**。

## 49. 【已踩·已修】RETURNING count(*) 语法错误：issue_store 批量状态函数全失效

- **现象**：服务器灌语料后 worker 日志暴露 "issues sync failed: aggregate functions are not allowed in RETURNING"——resolve_for_file/reset_retrying/cancel_for_file 三个批量 UPDATE 函数用 `RETURNING count(*) AS n` 取行数，PG 语法不允许（RETURNING 只能返回行值不能聚合），三个函数实际全部失效（warning 不阻塞，但"无占位文件自动解决历史 issue"的闭环收尾环节是断的）。
- **原因**：本地冒烟只测了 create_batch/list/mark_retrying/mark_resolved 四个函数，恰好没覆盖三个批量函数（本地无占位文件解析场景，worker 未触发）；本地 33.txt 解析时同样会报错但被 warning 吞掉未排查。
- **影响**：失败块闭环 v2 的"自动解决"环节断开——文件重新解析成功后历史 pending/retrying issue 永远不落地；服务器真实流量（8 文件灌料）暴露，本地环境掩盖。
- **修复方案/处理**：改用 pg_store.execute 直接返回的 rowcount（封装层已返回 int）；本地冒烟全链路验证（reset=1/resolve=1/cancel=0 语义正确）+ pytest 135 全过。教训：**批量函数与单行函数都要端到端验证；"本地没触发"不等于"代码没 bug"——真实流量/灌料演练是验收的必要环节**。

## 50. 【已踩·已修】扫描型 PDF 永远报"未配置 VLM"：延迟初始化位置错误

- **现象**：服务器灌料时 scanned PDF 解析 failed（"未配置 VLM"），但本地同一份扫描件能正常转录；排查发现 VLM 复用 MIMO_API_KEY（MiMo v2.5 视觉模型，key 从未缺失），是代码把"调用方没传参"当成"未配置"。
- **原因**：`PdfParser` 的 VLM 延迟初始化（`self.vlm = _default_vlm()`）只写在 `_parse_scanned()`/`_describe_image()` 内部，而 `parse()` 的扫描型判定 `if self.vlm is None: raise ParseError("未配置 VLM")` 抢在前——pipeline 子进程统一用无参 `PdfParser()` 创建解析器（vlm=None），扫描件判定永远先抛错，延迟初始化永远到不了。文本 PDF 的图片块不受影响（走 `_describe_image` 的延迟初始化），所以本地测试一直没暴露。
- **影响**：所有扫描件/图片型 PDF 在 worker 链路（无参创建）下永远解析失败；"未配置"报错误导排障方向（误以为缺 key，实际 key 一直有效）。
- **修复方案/处理**：① 判定处改为先延迟初始化再判型（与内部惰性一致）；② `_default_vlm` 语义改为真正检查 `MIMO_API_KEY` 缺失才 raise（"未配置"= key 缺失，而非没传参）；③ 旧测试改 mock `_default_vlm` 抛错验证无 key 拒绝，新增无参构造扫描件正向测试（mock 返回 fake，验证惰性链路）；pytest 136 全过。教训：**"未配置"类报错必须区分"依赖缺失"与"调用方没传"；子进程/工厂统一创建的路径，延迟初始化的位置必须覆盖所有先行判定分支——本地直调测不到的路径要模拟真实调用方（无参构造）**。
