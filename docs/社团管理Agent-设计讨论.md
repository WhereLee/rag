## 一、角色划分

| 角色 | 数量 | 职责 |
|---|---|---|
| 社长 | 1 | 管理层，参与活动决策 |
| 副社长 | 2 | 管理层，负责活动（企划/执行轮值） |
| 社员 | 若干 | 参加活动 |

简单概括：**社长与副社长负责活动，社员负责参加**。

> 边界说明：**院校级老师（指导老师）暂不引入系统**——评估结论是老师只有"能看到"的需求（查看活动留痕/复盘），无操作与管理诉求；故不建模老师角色、不引入权限体系，只预留只读可见通道（形态待定，见待定项 7）。

## 二、活动分工模式（轮值 + 搭档制）

以 A（社长或副社长）、B、C 为例：
- 每次活动：**一人主企划 + 两人执行**（搭档制：A 或 A+B 企划）
- 角色环节：
  - **企划**：A 或 A+B 负责（构思活动主题/方案）
  - **资源安排**：B 或 B+C 负责（空教室申请、邀请老师莅临指导等）
  - **现场管理**：C 或 C+A 负责（活动现场组织）
- 轮转机制：下轮企划轮换到 B——同一活动内谁企划谁执行是动态的，角色跟着轮次走
- 每次活动留痕：谁负责企划、谁负责执行等（责任可追溯）

## 三、系统边界（重要设计决策）

- **系统管"活动级职责留痕 + 状态流转"，不管执行细节**（执行怎么谈、怎么做私下解决）
- 目的性是管理：记录谁企划、谁执行、活动状态，责任可追溯
- 执行任务分派方式：**企划人分派**（企划人在企划书里指定执行分工），分派细节线下讨论
- **非管理角色不入系统**：院校级老师仅"能看到"（只读可见），不做对象建模（见角色划分边界说明）

## 四、留痕数据的用途（三层）

1. **追溯**：历史活动可查（谁企划过什么、执行过什么、状态流转）
2. **复盘 Agent 的输入**：活动表单记录喂给复盘 Agent 生成复盘（用户已确认：这是留痕数据的首要去向）
3. **企划建议的数据源**（核心亮点）：下一次某成员做企划时，**企划建议 Agent** 基于历次留痕提供建议——历史活动变成"经验库"
4. **管理层跨届问答**（新增）：管理层会换届，留存数据（活动留痕 + 复盘结论）做成**管理层专用 RAG 问答**，新一届管理层可检索历史经验（详见第八节）

## 五、企划建议 Agent

- 定位：轮值企划时，Agent 基于历史活动数据（类型/规模/预算/复盘结论）给出企划建议
- 本质：**历史经验检索（数据）+ LLM 生成（建议）**——与 RAG 同一骨架（检索 + 生成），检索源从"文档"变为"历史活动记录"
- **冷启动两阶段**：
  - 阶段一（无历史）：Agent 基于通用知识生成建议（活动类型清单、预算范围、流程检查项等通用模板）
  - 阶段二（有积累）：切换到数据驱动（历史活动检索 + 复盘结论注入）

## 六、表单质量约束（保证留痕数据质量）

- **强制表单**：管理层填写留存文档，字段必填、限制字数等（防空白）
- **认知补充（关键）**：必填/字数保证"完整性"，保证不了"信息量"——需要**结构化指标字段**（参与人数、预算执行比例、超时/问题清单、现场异常数），复盘 Agent 才能做"好坏判断"而非"文字总结"
- 数据质量信号 = 表单结构化程度

## 七、复盘 Agent（质量信号的来源，闭环的关键）

- 定位：活动结束后，基于表单真实记录自动生成复盘
- 回答"历史活动好坏从哪来"：管理层落实 → 记录真实情况 → 复盘 Agent 生成复盘 → 沉淀为下一次企划建议的数据源
- 复盘输入（已确认）：活动表单记录喂给复盘 Agent（留痕数据的首要去向）
- 复盘输出（两条路，细节待定）：①给管理层看（活动总结报告存档）②提炼成"经验条目"喂给建议 Agent（大概率两个都要，产出格式不同）——经验条目同时是管理层 RAG 问答的数据源

## 八、管理层专用 RAG 问答（跨届经验传承）

- **背景**：管理层会换届（社长/副社长更替），经验不能随人走——留存数据（活动留痕 + 复盘结论）沉淀为经验库，做成**管理层专用 RAG 问答**
- **定位**：新一届管理层随时提问历史经验（"以前办过哪些活动"、"某类活动预算一般多少"、"哪个环节最容易出问题"）——从"翻历史记录"变成"直接问答"
- **与企划建议 Agent 的区别**：建议 Agent 是流程内触发（轮值企划时主动给建议）；问答是随时提问（被动检索回答）。两者**共用同一经验库**，使用时机与交互形态不同
- **复用 RAG 能力**：与 RAG 项目同骨架（检索 + 生成），检索源从"文档"变为"活动留痕 + 复盘条目"，与企划建议 Agent 共用同一套检索基础设施
- **权限边界**：仅管理层可用；老师只读可见通道形态待定（见待定项 7）

## 九、完整闭环（讨论共识）

```
企划（AI 建议 + 人拍板）
  → 分工执行（企划/资源/现场，轮值+搭档）
  → 表单记录（必填/字数/结构化指标，强制质量）
  → 复盘 Agent（基于真实记录生成复盘）
  → 沉淀（复盘/指标进入经验库）
  → 两个消费出口：下一次企划建议（数据源）+ 管理层跨届问答（数据源）
```

## 十、活动全流程的 LangGraph 编排（2026-08-24 讨论确认）

**结论：活动全流程适合用 LangGraph 编排——契合点是"人机协作的长时间流程编排"，不是"自动化流程"。**（用户认可：LangGraph 从 RAG 项目的"低频闲置"变成本项目的"核心引擎"）

### 环节 ↔ 节点类型映射

| 活动环节 | 节点类型 | LangGraph 能力 |
|---|---|---|
| 企划（AI 给建议） | agent 节点（LLM 生成草案） | 普通节点 |
| 人拍板/修改草案 | interrupt 节点（挂起等人确认后 resume） | 人工介入 |
| 分工分派（企划人指定） | interrupt 节点（表单输入） | 人工介入 |
| 执行阶段（线下 1-2 周） | 挂起等待（人完成后回来确认） | interrupt + 持久化 |
| 表单记录（必填/字数/指标） | interrupt 节点（结构化输入） | 人工介入 |
| 复盘（AI 生成） | agent 节点 | 普通节点 |
| 沉淀（经验条目入库） | 普通节点（写库） | 收尾 |
| 活动类型分支（讲座/户外/分享会） | 条件路由 | 条件边 |

### 两个关键设计（用户认可的增值点）

1. **checkpointer 自动留痕**：状态快照 = 追溯数据（谁在何时把活动从"企划中"推到"分工中"、当时的草案内容），`thread_id = activity_id`，一个活动一条线程——留痕是框架送的，不是额外开发
2. **PostgresSaver 跨天持久化**：活动执行期 1-2 周，图挂起等人工——状态必须落 PG（不能内存 MemorySaver）；服务/服务器重启后从检查点恢复，人回来继续走

### 三个代价（已认知，接受）

1. **人工交互层工作量最大**：每个 interrupt 节点都要前端配合（活动页操作 → resume API 恢复图），是纯业务开发，比状态机方案多一截
2. **业务依赖框架版本**：活动流程跑在 LangGraph 上，升级/API 变动直接影响业务流程——版本必须锁死
3. **对比数据库状态机**（parse_tasks 模式）：纯状态机更稳更简单，但"活动类型分路径"要硬编码状态枚举、AI 生成逻辑只能挂状态转换钩子；图方案流程可编程（动态分支 + AI 节点 + 自动留痕），值这个代价

### 面试素材

#### S1. 留痕数据的跨届资产化：管理层专用 RAG 问答 + 按需裁剪系统边界（2026-08-24，设计阶段）

- **结论**：业务系统的留痕数据不止服务当前流程追溯，还能资产化应对**组织换届**——管理层会换届，经验随人走，把活动留痕 + 复盘结论沉淀为经验库，做成**管理层专用 RAG 问答**（新一届管理层直接问历史：“以前办过哪些活动/某类活动预算一般多少/哪个环节最容易出问题”），复用 RAG 项目“检索 + 生成”全套能力，检索源从文档换成结构化记录。系统边界按真实需求裁剪：院校级老师只有“能看到”的诉求，**不建模老师角色、不引入权限体系**，只预留只读可见通道。
- **背景**：留痕数据原定服务“追溯 + 企划建议”；讨论时补问“数据除了服务当前流程还能服务谁”，暴露换届导致的经验流失风险——数据资产化是比“建议 Agent”更通用的跨届方案。老师侧需求评估后确认只有查看诉求，建模角色带来的权限/操作复杂度大于收益。
- **话术**：“设计时我问了一个问题：留痕数据除了服务当前流程，还能服务谁？答案是管理层换届会让经验流失——所以活动留痕+复盘直接做成管理层专用 RAG 问答，复用我 RAG 项目的整套检索与评估能力，检索源从文档换成活动记录。另一个边界决策：指导老师只有‘能看到’的需求，所以不建模这个角色、不加权限体系，只留只读通道——不为不需要的能力买单。”
- **追问1**：“老师不建模，‘能看到’怎么实现？” → 只读通道（归档查看/只读问答），与管理层问答同源不同入口；当前只确认需求存在，通道形态待定，真正需要时再引入，成本是可控增量。
- **追问2**：“管理层问答和企划建议 Agent 重复吗？” → 不重复：建议 Agent 是流程内主动触发（轮值企划时给建议），问答是被动检索（随时提问）；两者共用同一经验库，使用时机与交互形态不同。

#### S2. 活动全流程的 LangGraph 编排：人机协作流程才是 LangGraph 的主场（2026-08-24，设计阶段）

- **结论**：活动全流程（企划→人拍板→分工→执行→表单→复盘→沉淀）用 LangGraph 编排：agent 节点生成内容（企划建议/复盘）、interrupt 节点等人拍板（4 个人工决策点）、条件路由按活动类型分路径、checkpointer 持久化状态快照——**留痕自动产生**（thread_id=activity_id），跨天等待用 PostgresSaver 落库恢复。
- **背景**：RAG 项目里 LangGraph 图低频闲置的教训（真实流量只走简单档，复杂路径几乎不触发）；社团活动流程每天真实被走，且是"人拍板 + AI 辅助"的人机协作——这正是 LangGraph 的 human-in-the-loop 主场。
- **话术**：“RAG 项目里我体会过 LangGraph 图低频闲置的教训——能力完整但真实流量用不上。新项目选型时我特意验证了契合度：活动流程从企划到复盘有四个‘人等拍板’的决策点、有按活动类型分叉的路径、要跨天跨周持久化、还要全程留痕——LangGraph 的 interrupt/条件路由/checkpointer 四个能力正好一一对应，而且检查点快照就是业务留痕，不用额外开发追溯功能。”
- **追问1**：“为什么不用数据库状态机？” → 状态机做固定流程更稳，但活动类型分路径要硬编码状态枚举、AI 生成逻辑只能挂状态转换钩子；图的流程可编程（动态分支 + agent 节点内嵌），代价是框架版本依赖和人工交互层工作量，本项目场景值得。
- **追问2**：“interrupt 挂一周，服务重启怎么办？” → PostgresSaver 落库 + thread_id 恢复：重启后图从检查点继续，人工 resume 不丢状态；与业务状态机方案（状态字段 + 崩溃回收）殊途同归，只是状态载体换成图检查点。
