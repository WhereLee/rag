## 一、角色划分

| 角色 | 数量 | 职责 |
|---|---|---|
| 社长 | 1 | 管理层，参与活动决策 |
| 副社长 | 2 | 管理层，负责活动（企划/执行轮值） |
| 社员 | 若干 | 参加活动 |
| 指导老师 | 若干（预设账号） | 创建社团、任命社长/副社长、审批成员加入 |

简单概括：**社长与副社长负责活动，社员负责参加，指导老师管社团成立与管理层任命**。

> 老师账号来源决策（2026-08-25）：项目定位为"老旧管理系统的 Agent 功能化改造"，指导老师在旧管理体系中本就有账号——**不设计注册流程，直接预设一批账号（初始化数据）模拟存量**；生产部署时由初始化/迁移脚本创建。为此砍掉讨论中出现的发散方向：学校管理员账号、多校维度、老师注册审批流、学生注册选院校（一律不做，见第三节）。

## 二、活动分工模式（轮值 + 搭档制）

以 A（社长或副社长）、B、C 为例：
- 每次活动：**一人主企划 + 两人执行**（搭档制：A 或 A+B 企划）
- 角色环节：
  - **企划**：A 或 A+B 负责（构思活动主题/方案）
  - **资源安排**：B 或 B+C 负责（空教室申请、邀请老师莅临指导等）
  - **现场管理**：C 或 C+A 负责（活动现场组织）
- 轮转机制：下轮企划轮换到 B——同一活动内谁企划谁执行是动态的，角色跟着轮次走
- 每次活动留痕：谁负责企划、谁负责执行等（责任可追溯）

## 三、系统边界（重要设计决策）

- **系统管"活动级职责留痕 + 状态流转"，不管执行细节**（执行怎么谈、怎么做私下解决）
- 目的性是管理：记录谁企划、谁执行、活动状态，责任可追溯
- 执行任务分派方式：**企划人分派**（企划人在企划书里指定执行分工），分派细节线下讨论
- **系统角色**：指导老师（创建社团、任命管理层、审批成员）+ 管理层 + 社员；老师账号来源为预设（见第一节），不开放注册
- **不发散原则**（2026-08-25）：账号体系不往上发散——不引入学校管理员/多校维度/老师注册审批流；发散只会制造闲角色或增加业务复杂度，与"改造项目"定位不符

## 四、留痕数据的用途（三层）

1. **追溯**：历史活动可查（谁企划过什么、执行过什么、状态流转）
2. **复盘 Agent 的输入**：活动表单记录喂给复盘 Agent 生成复盘（用户已确认：这是留痕数据的首要去向）
3. **企划建议的数据源**（核心亮点）：下一次某成员做企划时，**企划建议 Agent** 基于历次留痕提供建议——历史活动变成"经验库"
4. **管理层跨届问答**（新增）：管理层会换届，留存数据（活动留痕 + 复盘结论）做成**管理层专用 RAG 问答**，新一届管理层可检索历史经验（详见第八节）

## 六、表单质量约束（保证留痕数据质量）

- **强制表单**：管理层填写留存文档，字段必填、限制字数等（防空白）
- **认知补充（关键）**：必填/字数保证"完整性"，保证不了"信息量"——需要**结构化指标字段**（参与人数、预算执行比例、超时/问题清单、现场异常数），复盘 Agent 才能做"好坏判断"而非"文字总结"
- 数据质量信号 = 表单结构化程度

## 七、复盘 Agent（质量信号的来源，闭环的关键）

- 定位：活动结束后，基于表单真实记录自动生成复盘
- 回答"历史活动好坏从哪来"：管理层落实 → 记录真实情况 → 复盘 Agent 生成复盘 → 沉淀为下一次企划建议的数据源
- 复盘输入（已确认）：活动表单记录喂给复盘 Agent（留痕数据的首要去向）
- 复盘输出（两条路，细节待定）：①给管理层看（活动总结报告存档）②提炼成"经验条目"喂给建议 Agent（大概率两个都要，产出格式不同）——经验条目同时是管理层 RAG 问答的数据源

## 八、管理层专用 RAG 问答（跨届经验传承）

- **背景**：管理层会换届（社长/副社长更替），经验不能随人走——留存数据（活动留痕 + 复盘结论）沉淀为经验库，做成**管理层专用 RAG 问答**
- **定位**：新一届管理层随时提问历史经验（"以前办过哪些活动"、"某类活动预算一般多少"、"哪个环节最容易出问题"）——从"翻历史记录"变成"直接问答"
- **与企划建议 Agent 的区别**：建议 Agent 是流程内触发（轮值企划时主动给建议）；问答是随时提问（被动检索回答）。两者**共用同一经验库**，使用时机与交互形态不同
- **复用 RAG 能力**：与 RAG 项目同骨架（检索 + 生成），检索源从"文档"变为"活动留痕 + 复盘条目"，与企划建议 Agent 共用同一套检索基础设施
- **权限边界**：管理层 + 指导老师可用（老师以管理者视角查看本社团留痕/复盘，属本职）

## 九、完整闭环（讨论共识）

```
企划（AI 建议 + 人拍板）
  → 分工执行（企划/资源/现场，轮值+搭档）
  → 表单记录（必填/字数/结构化指标，强制质量）
  → 复盘 Agent（基于真实记录生成复盘）
  → 沉淀（复盘/指标进入经验库）
  → 两个消费出口：下一次企划建议（数据源）+ 管理层跨届问答（数据源）
```

#### S1. 留痕数据的跨届资产化：管理层专用 RAG 问答 + 按需裁剪系统边界（2026-08-24，设计阶段）

- **结论**：业务系统的留痕数据不止服务当前流程追溯，还能资产化应对**组织换届**——管理层会换届，经验随人走，把活动留痕 + 复盘结论沉淀为经验库，做成**管理层专用 RAG 问答**（新一届管理层直接问历史：“以前办过哪些活动/某类活动预算一般多少/哪个环节最容易出问题”），复用 RAG 项目“检索 + 生成”全套能力，检索源从文档换成结构化记录。系统边界按真实需求裁剪：院校级老师只有“能看到”的诉求，**不建模老师角色、不引入权限体系**，只预留只读可见通道。
- **背景**：留痕数据原定服务“追溯 + 企划建议”；讨论时补问“数据除了服务当前流程还能服务谁”，暴露换届导致的经验流失风险——数据资产化是比“建议 Agent”更通用的跨届方案。老师侧需求评估后确认只有查看诉求，建模角色带来的权限/操作复杂度大于收益。
- **话术**：“设计时我问了一个问题：留痕数据除了服务当前流程，还能服务谁？答案是管理层换届会让经验流失——所以活动留痕+复盘直接做成管理层专用 RAG 问答，复用我 RAG 项目的整套检索与评估能力，检索源从文档换成活动记录。另一个边界决策：指导老师只有‘能看到’的需求，所以不建模这个角色、不加权限体系，只留只读通道——不为不需要的能力买单。”
- **追问1**：“老师不建模，‘能看到’怎么实现？” → 只读通道（归档查看/只读问答），与管理层问答同源不同入口；当前只确认需求存在，通道形态待定，真正需要时再引入，成本是可控增量。
- **追问2**："管理层问答和企划建议 Agent 重复吗？" → 不重复：建议 Agent 是流程内主动触发（轮值企划时给建议），问答是被动检索（随时提问）；两者共用同一经验库，使用时机与交互形态不同。
- **修订（2026-08-25）**：后续讨论中"老师只读"演变为"老师完整角色"（创建社团/任命/审批，RBAC 有 teacher）；再进一步，项目定位明确为"老旧管理系统的 Agent 功能化改造"——老师账号在旧体系已存在，不设计注册流程，预设账号模拟存量；同时砍掉中途讨论的学校管理员/多校维度/老师注册审批流。面试讲述以最终决策为准，可把演化过程讲成"边界收敛"故事（详见 S3）。

#### S3. 账号体系边界收敛：特权角色账号来源的发散与收敛（2026-08-25，设计阶段）

- **结论**：特权角色（指导老师）的账号来源是边界陷阱——预置别扭（"为什么是他"）、系统管理员创建暗示平台语义（系统之上还有权威）、注册验证增加复杂度；每个方案都隐含系统范围扩张。收敛方法：回到项目定位判断。本项目是"老旧管理系统的 Agent 功能化改造"——账号是存量数据，不是要设计的流程，直接预设/迁移即可，不发散。
- **背景**：从"指导老师创建社团"引出"老师账号从哪来"，讨论发散到学校管理员、多校维度、老师注册审批流，感知到与主题渐行渐远后收住——用户拍板：账号体系不是改造重点，预设账号模拟存量，重点放在社团内部管理的 Agent 化。
- **话术**："设计账号体系时我问：老师账号从哪来？预置别扭、管理员创建会把系统暗示成平台、注册验证加复杂度。我回到项目定位——这是对旧系统的 Agent 化改造，旧体系里老师账号本就存在，所以不设计注册流程，账号作为存量数据初始化。边界是设计出来的，不是默认的。"
- **追问1**："生产环境老师账号怎么创建？" → 初始化/迁移脚本，与开发期预设账号同一机制；账号生命周期（改密/禁用）已列入待定项 7。
- **追问2**："预设账号安全吗？" → 开发/测试用固定账号；生产由迁移脚本创建 + 首次登录强制改密，登录日志审计留痕。

#### S4. 跨表唯一约束的数据库落地：部分唯一索引的边界与触发器兑底（2026-08-25，实现阶段）

- **结论**：PostgreSQL 部分唯一索引的 WHERE 谓词禁止跨表子查询——"一人不能同时担任多个社团的管理层"这类依赖其他表（rbac_role.is_management）的约束，数据库层用 BEFORE INSERT/UPDATE 触发器硬性兑底，应用层事务内校验给友好提示，双层防线。
- **背景**：设计时先尝试部分唯一索引（RAG 项目技能复用），实测发现索引谓词必须是本行不可变表达式，无法引用 rbac_role 表；改用触发器函数 + RAISE EXCEPTION，应用层先查后写。
- **话术**："设计成员表时有一条跨表约束——一个人不能同时担任两个社团的管理层，判断依据在角色表里。PostgreSQL 的部分唯一索引只能在单表谓词上用，跨表做不到，我用了两层：应用层事务内校验给友好错误，数据库触发器硬性兜底防并发穿透。"
- **追问1**："触发器和应用校验重复吗？" → 不重复：应用层先查后写给中文提示；两个请求并发任命同一用户时应用层都查不到，数据库触发器保证最终一致。
- **追问2**："为什么不用唯一索引直接限制？" → 管理层是动态角色表（运行时增删），role_id 不固定；is_management 标记在另一张表，索引无法引用。

#### S5. 存储抽象：本地/COS 双实现按配置切换（2026-08-25，实现阶段）

- **结论**：文件存储抽象成 StorageService 接口，本地磁盘（开发）与腾讯云 COS（生产）双实现，@ConditionalOnProperty(storage.mode) 按配置切换；COS 密钥缺失启动即拒绝（fail-fast）；返回统一 URL 语义（本地 /uploads/** 静态映射，COS 拼接自定义域名/默认域名）。数据库只存 URL 引用，不存文件本体。
- **背景**：用户要求头像功能"测试时部署到服务器用真实 COS"——开发期本地磁盘也能全链路开发，部署时只改配置不碰代码；这是企业常见的存储后端可切换模式。
- **话术**："文件上传我做了存储抽象：StorageService 接口 + 本地磁盘和腾讯云 COS 两个实现，配置切。开发期本地跑，上线切 COS 只改一行配置。COS 密钥缺失直接拒绝启动，不会带病上线。"
- **追问1**："为什么不用 base64 存数据库？" → 企业明确坏味道：数据库膨胀、无法 CDN、无权限粒度；存 URL 引用 + 对象存储是标准。
- **追问2**："COS 和本地返回的 URL 语义怎么统一？" → 接口只返回字符串 URL，本地实现返回 /uploads/xx（静态映射），COS 返回完整域名 URL，调用方无感知。

#### S6. 登录防爆破三层防线 + 登出 token 失效（2026-08-25，实现阶段）

- **结论**：登录链路三层防线：①图形验证码（Redis 存答案，一次性消费）②连续失败锁定（Redis 计数，Lua 保证 INCR+EXPIRE 原子，超限锁定 N 分钟）③接口限流（@RateLimiter 注解 AOP，按用户/IP+方法计数窗口）；登出走 JWT 黑名单（jti 入 Redis，TTL=剩余有效期）；错误提示统一"用户名或密码错误"防账号枚举。
- **背景**：用户明确要求登录安全不能因用户量小而简化（"慢查询是指安全方面"）——验证码防机器、失败锁定防定向爆破、限流防分布式爆破，三层各管一层。
- **话术**："登录安全我做了三层：验证码挡机器脚本，失败锁定挡单账号爆破（Redis 计数，Lua 保证原子），限流挡 IP 层爆破（注解 + AOP，不用改业务代码）。登出不是摆设——JWT 无状态，登出把 jti 加黑名单到自然过期，token 立即失效。"
- **追问1**："验证码一次性消费怎么保证？" → 登录校验后立即删 Redis key，不管成功失败都用一次。
- **追问2**："为什么失败计数用 Lua？" → INCR + 首次设 TTL 两个操作，非原子会留下永不失效的计数 key，Lua 保证原子。

#### S7. 社团上下文权限校验：@ClubPermission 注解 + SpEL 切面（2026-08-26，实现阶段）

- **结论**：权限点（如 club:member:approve）没有"属于哪个社团"的维度，必须限定"对哪个社团行使"——自定义注解 @ClubPermission(clubId="#clubId", permission="club:member:approve") + AOP 切面：SpEL 从方法参数解析 clubId，校验两条路（① 用户是该社团指导老师→按 teacher 角色权限集；② 已通过成员→按 membership 角色权限集），无权限 403 带社团名。老师身份判定：sys_user.is_teacher 全局标记 + club.teacher_id 归属校验（老师不越权管别人的社团）。
- **背景**：RBAC 权限点全局定义，但审批/任命必须在社团内行使——纯权限点校验不够，需要"社团上下文"。若依式 @PreAuthorize 无法表达 clubId 维度，自研注解 + SpEL 参数解析是标准做法。
- **话术**："权限点本身没有社团维度，我做了 @ClubPermission 注解：SpEL 从方法参数解析社团 ID，切面里查你在该社团的身份（老师看 teacher_id，成员看 membership 角色），再对权限集。Controller 一行注解搞定，校验逻辑收敛在一个切面，后续活动管理直接复用。"
- **追问1**："为什么不用 Spring Security 的 @PreAuthorize？" → 可以但要写 SpEL 调 bean，社团 ID 从参数取的逻辑照样要自己写；自研注解语义更清晰，切面里还能带出社团名做 403 提示。
- **追问2**："老师为什么不能管所有社团？" → 老师只对 club.teacher_id 是自己的社团有权限集，避免特权蔓延——权限最小化。

#### S8. 换届模型：自离职 → 空位 → 老师任命（2026-08-26，用户拍板）

- **结论**：不存在"解除职务"操作，只存在换届：管理层本人点"离职"（角色降为社员，人留在社团）→ 职务槽位空出 → 老师任命新人只进空位。三个约束下沉数据库触发器：①跨社团唯一（一人不能同时任多社团管理层）②一社团一社长 ③副社长最多 2 人；应用层预检给友好提示，触发器兜底并发穿透。
- **背景**：用户拍板"不存在解除，只存在换届"——参考现实：社长干完自己退，位置空出来由老师任命；不做投票/弹劾等复杂机制。槽位约束用触发器表达（跨表依赖 rbac_role.is_management，部分唯一索引无法跨表）。
- **话术**："管理层更替我按现实模型设计：没有解除职务，只有离职——社长自己点离职，位置空出来，老师任命新人。三个硬约束（跨社团唯一/一社团一社长/副社长上限 2）下沉到数据库触发器，应用层预检给中文提示，并发穿透由触发器兜底。"
- **追问1**："离职后还能再当吗？" → 能：人还在社团（角色降为社员），老师可重新任命（空位时）。
- **追问2**："任命时如果旧社长没离职怎么办？" → 应用层预检提示"已有在职社长，需现任先离职"，触发器同样拒绝——只进空位是系统保证的。

#### S9. 生产级补强清单：雪花ID精度 / CAS 并发 / 防重粒度 / 接口防护（2026-08-26，用户要求"做到生产级"）

- **结论**：用户要求"当前部分先做到生产级"，体检后补强五处：①雪花 ID 超出 JS 安全整数（2^53），VO 层 @JsonSerialize(ToStringSerializer) 序列化为字符串（LoginVO/ClubVO/ClubDetailVO/MemberVO/MyClubVO 等全部 id 字段）；②审批/拒绝/重新申请改 CAS 条件更新（UPDATE ... WHERE status=期望值，影响行数 0 抛"已处理"），防并发双击后写覆盖；③防重复提交切面 key 从"方法+用户"细化为"方法+用户+IP+参数"——同一接口不同目标互不干扰（审批 A 不拦审批 B），同一目标双击才互斥；④写接口全部补 @RateLimiter（创建 10次/分、申请 30次/分）+ @RepeatSubmit(3s)；⑤分页 page≥1、size≤100 参数校验（@Validated + @Min/@Max），防全表扫。
- **背景**：功能冒烟通过 ≠ 生产级。逐条体检发现：雪花 ID 在真实浏览器必然丢失精度（Python 冒烟测不出来，JS Number 只有 53 位精度，19 位雪花 ID 必失真）；approve 读-改-写三步无并发保护；防重 key 粒度过粗会误拦连续审批；写接口无防护可被脚本刷。
- **话术**："生产级体检我按四个维度过了一遍：数据（雪花 ID 前端精度——这是 Python 测试测不出来的，必须 JS 场景验证）、并发（审批状态流转改 CAS，数据库条件更新比乐观锁字段更轻）、防护（写接口限流+防重，防重 key 带参数粒度）、参数（分页上限）。冒烟脚本也升级：并发线程双击验证防重真的拦截，不同目标并发验证 key 不误伤。"
- **追问1**："为什么不用全局 Jackson 配置 Long→String？" → 会把 memberCount 等业务 Long 也变成字符串；只对 ID 字段加注解，语义精准，前端拿到的类型可控。
- **追问2**："CAS 和乐观锁字段（version）有什么区别？" → 状态机明确的场景用条件更新更轻：不需要额外列，UPDATE 自带原子性；version 适合通用防冲突，条件更新适合"只允许特定状态流转"（如仅 PENDING→APPROVED）。

#### S10. E2E 自动化与图形验证码共存：直读存储的测试旁路（2026-08-27，实现阶段）

- **结论**：浏览器实测卡在验证码时不该"绕过"或"关闭"它——测试环境走可信旁路：从前端 Vue 组件状态读到 captchaKey（验证码图片 data URI 由该 key 驱动），再到 Redis 直接 GET 明文答案填回表单。登录链路（含验证码校验、一次性消费、失败锁定）全程真实执行，生产代码零改动。
- **背景**：用户指示"用浏览器试运行，卡在验证码环节就停止"。备选方案里万能码会污染安全逻辑，OCR 对抗变形字符稳定性差会让 E2E 必然 flaky——而 captchaKey 本就是服务端下发、本就落 Redis，等价于把"人眼识图"这一步换成"授权读取"。
- **话术**："E2E 过验证码我做的是旁路而不是拆闸门：脚本从页面组件状态拿到 captchaKey，去 Redis 读出答案原样提交——登录校验一步不少地跑完，只是替人的眼睛换了个取答案的方式。生产代码零修改，验证码防线也没有在任何环节被禁用。"
- **追问1**："为什么不用 OCR？" → 识别率不稳定会把不确定性引入被测系统之外的环节，登录用例偶发失败浪费时间；环境内可信读取是确定性方案。
- **追问2**："这不是把验证码变摆设了吗？" → 不是：验证码防的是外部机器脚本，它们拿不到服务器 key 与 Redis 权限；测试方本就拥有全部基础设施访问权，二者威胁模型不同。
- **追问3**："过程中有意外收获吗？" → 第一次填答案时 key 已过期产生一条真实登录失败记录（"验证码错误或已过期"），几分钟后在同一系统"操作日志"页看到这条记录——审计留痕的开发期排障价值顺带被验证，日志功能完成了一次功能自证闭环。

#### S11. 审批状态机的并发与超时设计：CAS 流转 + 阶段 deadline + 定时扫描 + 通知联动（2026-08-29，实现阶段）

- **结论**：概念审批（投票→复议→老师批复）状态机三类机制组合：①**CAS 条件更新**（UPDATE ... WHERE status=from SET status=to，影响 0 行抛"状态不可执行"）防并发双击双推进；②**阶段 deadline 独立重算**（提交=提交+36h、进入复议=进入+36h、进入待老师批复=进入+36h——不是从提交起算 36h 一路到底，避免投票期消耗老师时限）；③**@Scheduled 每分钟扫描** status IN (2,3,4) AND deadline<now 自动作废 + 通知，作废动作与通知同一事务。通知联动规则含业务例外：作废通知三位管理层，**老师批复超时额外通知老师本人**（打破"老师不接收作废通知"定稿——超时责任人是老师，他必须知道自己漏了）。
- **背景**：审批流程有多人参与 + 明确时限（36h），必须处理"没人按时行动"的收敛路径；定稿讨论时用户明确了 deadline 随阶段重算的语义（"投票期用掉 30h 老师只剩 6h 不合理"）。
- **话术**："审批状态机我重点处理了三个点：状态流转全部 CAS 条件更新，并发双击不会双推进；每个阶段独立 36h deadline，不共用总时长——投票耗掉的时间不惩罚老师；每分钟扫描超时自动作废，作废和通知同一事务，不会出现作废了没人知道。通知规则里有个业务例外很值得讲：老师批复超时，会额外通知老师本人——按定稿老师不接收作废通知，但超时责任人是老师，不通知他就没人知道他漏了。"
- **追问1**："定时扫描为什么不用 @Scheduled(cron)？" → fixedDelay 每分钟跑一次即可，扫描 SQL 本身带索引（status+deadline），每次只扫到过期行，量级可控；cron 精度无必要。
- **追问2**："CAS 和通知不在同一事务会怎样？" → 状态改了通知没发（或反序），会出现"已作废但无人知晓"；同事务保证要么全成要么全不成，通知表与状态表强一致。

#### S12. 透明留痕的时间线数据源：全量流水表 + 投票记录表双轨（2026-08-29，实现阶段）

- **结论**：概念详情页展示"谁在什么时候做了什么"：①concept_trace 全量时间线（action 枚举 14 种 + operator_name + detail 理由，系统动作 operator=null 显示"系统"）；②concept_vote 投票记录（round 轮次区分首轮/复议、result/comment 必填理由）。两条线都从详情接口返回（votes + traces），前端时间线组件直接渲染——**审计与展示共用一个数据源**，不另做审计表。
- **背景**：用户明确"不做管理层之间的交流功能，专注流程管理，所以留痕（谁/何时/什么）必须明确"——时间线既是老师审批时的审阅材料（看对话精简前的基座形态），也是审计追溯的数据源。
- **话术**："透明留痕我用两张表：流水表记动作时间线（谁在什么时候做了什么、理由是什么，系统动作标'系统'），投票表记每张票的轮次和理由。详情接口一次返回两条线，前端时间线直接渲染——老师审阅、事后审计、前端展示共用一个数据源，没有为了审计再造一套。"
- **追问1**："为什么投票单独建表不直接放流水？" → 投票有结构化字段（轮次/赞成拒绝）需要按状态机逻辑查询统计（两票齐没齐、有无拒绝票），流水表是追加型时间线；两张表职责不同，状态机逻辑直接查投票表。
- **追问2**："撤回时投票物理删除，审计不就没了吗？" → 删除前流水已记录（action=withdraw，detail="已投的票作废"），审计看流水不看投票表——投票表是状态机工作数据，流水才是审计事实。

### 工程坑位

#### K1. 【已踩】PG TIMESTAMPTZ ↔ LocalDateTime 映射失败（2026-08-25）

- **现象**：应用启动即失败，BadSqlGrammarException："Cannot convert the column of type TIMESTAMPTZ to requested type java.time.LocalDateTime"
- **原因**：DDL 用了 TIMESTAMPTZ（带时区），MyBatis 实体字段是 LocalDateTime（无时区），PG JDBC 拒绝转换。
- **影响**：应用无法启动，所有表都受影响。
- **修复**：DDL 统一改为 TIMESTAMP（不带时区），与 LocalDateTime 匹配；单时区业务（应用统一 GMT+8）语义正确。若要保留 TIMESTAMPTZ，实体需改为 OffsetDateTime/Instant，但 JSON 序列化与前端处理更复杂。
- **复用教训**：PostgreSQL 建表前先确认 Java 时间类型对应关系——TIMESTAMP ↔ LocalDateTime、TIMESTAMPTZ ↔ OffsetDateTime/Instant；国内单时区项目 TIMESTAMP + LocalDateTime 是主流。

#### K2. 【已踩】任命预检的排除自身陷阱：重复任命同一人未被拦截（2026-08-26）

- **现象**：重复任命同一人为同一职务（已是社长再任命社长）返回 200 而非拒绝。
- **原因**：槽位预检 SQL 用 .ne(membershipId) 排除自身（为了支持"副社长升社长"时旧身份不占位），但"自己已是目标职务"时也被排除了——count=0 预检通过，UPDATE 无变化。
- **影响**：接口语义不严谨：重复任命静默成功，与"只进空位"模型矛盾。
- **修复**：预检前先判断 membership.getRoleId().equals(targetRole.getId()) → 抛"该成员已是目标职务，无需重复任命"（业务码 1025）。
- **复用教训**：凡"排除自身"的排他查询，都要区分两种语义：排除自身的旧身份（允许角色变更）vs 排除自身的当前位置（重复任命应拒绝）——两个判断必须分开写。

#### K3. 【已踩】老师身份无落点：RBAC 角色表里 teacher 但用户无关联记录（2026-08-26）

- **现象**：实现"老师创建社团"权限校验时发现无法判定"当前用户是老师"——teacher 只是 rbac_role 表的一行，老师不在 membership（无社团上下文），系统没有任何记录表达用户级身份。
- **原因**：三层模型下角色是"用户在社团里的属性"，但老师是全局身份（不加入社团），模型没覆盖"用户级角色"。
- **影响**：创建社团/任命的权限校验无法落地。
- **修复**：sys_user 加 is_teacher 全局标记（老师=账号级身份，学生=社团级身份，语义分层）；预设老师账号时置 true；权限判定：is_teacher + club.teacher_id 归属双重校验。
- **复用教训**：设计角色模型时先分清"身份层级"：全局身份（老师/管理员）放用户表标记，组织内身份（社长/社员）放 membership——混在一起会留"角色无处安放"的洞。

#### K4. 【已踩】雪花 ID 前端精度丢失：Python 冒烟测不出来的必现 bug（2026-08-26）

- **现象**：社团 ID/成员 ID 在浏览器端失真——列表页跳详情 404、审批/任命操作"成员记录不存在"。
- **原因**：雪花 ID 是 19 位 Long（约 1.9e18），超过 JS Number 安全整数上限 2^53（约 9e15）；后端 JSON 直接输出数字，JS 解析时低 16 位丢失。
- **影响**：前端所有依赖 ID 的跳转/操作必然失败；后端接口与 Python 测试完全正常，**测试语言恰好避开 JS 精度问题**（Python 整数无上限），最容易漏。
- **修复**：VO 层 id 字段 @JsonSerialize(using = ToStringSerializer.class) 序列化为字符串；不做全局 Long→String（避免污染 memberCount 等业务数值）。
- **复用教训**：前后端分离 + 雪花主键的项目，验收必须包含"浏览器真实链路"测试；冒烟脚本语言用 Python 会掩盖此问题。

#### K5. 【已踩】防重复提交的"串行重放"语义：防重拦的是并发不是快速连点（2026-08-26）

- **现象**：测试脚本串行连发两次同一请求，期望"请勿重复提交"，实际返回业务幂等提示（1015/1016/1025）。
- **原因**：防重切面 SETNX 标记在请求执行完（finally）即释放——串行场景第二个请求到达时标记已释放，正常进入业务层；它防的是"同一时刻的并发双击"，不是"执行完毕后的快速重放"。
- **影响**：若用串行脚本断言防重必然失败，误判功能缺失；反之并发线程才能验证防重真实生效。
- **修复**：冒烟测试改用双线程并发打同一接口（断言恰一个成功），并用"不同目标并发"验证 key 粒度正确（互不拦截）。
- **复用教训**：测试"防重/防抖"类机制必须构造并发场景；串行重放验证的是业务幂等（第二次报"已处理"），两者语义不同、防线不同。

#### K8. 【已踩】系统动作写流水撞 NOT NULL 约束：超时作废静默失败（2026-08-29）

#### K12. 【已踩】并发测试的"假并发"陷阱：Start-Job 进程启动开销导致串行化（2026-08-29）

- **现象**：用 Start-Job 起两个 Job 并发打接口验证并发修复，两次都"成功"（如并发保存草稿两个都 200），误判修复未生效；数据库 version 从 0 直接跳到 2。
- **原因**：PowerShell Job 是独立进程，启动开销 100ms+，远超 HTTP 往返时间（约 5-10ms）——两个请求实际串行到达后端，第二个请求拿到的是第一个提交后的新状态（version=1），自然成功；Task.Run 方案在 PS 5.1 也不行（脚本块在无 runspace 的线程执行直接抛异常）。
- **影响**：并发修复的验证结果是假的——"串行也能过的断言"无法证明并发正确性；测试永远绿但并发 bug 依旧。
- **修复**：文件屏障模式——两个 Job 轮询同一信号文件（5ms 间隔），主脚本确认两个 Job 就绪后创建信号文件放行，毫秒级同时发出请求，制造真实并发窗口；改用此方案后并发保存草稿正确呈现"恰一成功一 1030"。
- **复用教训**：验证并发机制（防重/乐观锁/行锁）必须确认请求真重叠：串行也能过的断言是无效验证；Start-Job 裸跑、Task.Run 都是陷阱，文件屏障（或后端日志确认两条事务同时活跃）才是可靠手段。

#### K13. 【已踩】@Version 乐观锁三件套缺一不可：只加注解不注册拦截器=静默失效（2026-08-29）

- **现象**：实体加了 @Version 注解、saveDraft 也判了 updateById 返回值，但并发保存草稿两个都成功（version 0→2），1030 从未触发。
- **原因**：MyBatis-Plus 乐观锁生效需要两个条件同时满足：①实体字段 @Version 注解；②MybatisPlusInterceptor 注册 OptimisticLockerInnerInterceptor——配置类里只有分页插件，乐观锁拦截器缺失，updateById 退化为无条件全字段更新。
- **影响**：审查报告 P2-1 指出的"假乐观锁"在"修复"后依然为假，直到用真并发验证才暴露；此 bug 完全静默（无报错、无日志），只能靠并发测试或 SQL 日志抓出。
- **修复**：MybatisPlusConfig 注册 OptimisticLockerInnerInterceptor（与分页插件同链）；验证方式：真并发双存草稿断言恰一成功，或看库 version 是否 +1。
- **复用教训**：MyBatis-Plus 的 @Version 是"注解+插件"双要件，缺插件时注解完全无效且无任何提示；同类陷阱还包括 @TableLogic/@TableField(fill) 等需要配套配置的注解——排查"字段级能力不生效"先查插件链。

#### K14. 【已踩】schema 多脚本漂移：K8 修复只同步了一份建表脚本（2026-08-29）

- **现象**：代码审查发现 alter_concept_lifecycle.sql 的 concept_trace.operator_id 仍是 NOT NULL，而 init_db.sql 已改为可空；按 alter 脚本重建库，超时扫描系统动作（operator_id=null）插入必失败，整批作废回滚、定时任务静默失效。
- **原因**：K8 修复时只改了实际库 + init_db.sql，alter 脚本漏同步；两个脚本都带 `CREATE TABLE IF NOT EXISTS` 幂等语义，不会互相修正，漂移后旧脚本成为"部署即失效"的炸弹。
- **影响**：任何按旧脚本初始化/重建的环境，36h 超时作废整体瘫痪（状态卡死只能人工 SQL）；且日常开发看不到（库已被正确修改），只有审查/新环境才暴露。
- **修复**：alter 脚本补 `ALTER TABLE ... DROP NOT NULL` 幂等语句 + 同步扫描索引；后续改表结构必须同时改所有引用该表的脚本。
- **复用教训**：多份建表/迁移脚本并存时，结构变更必须全部同步（grep 全项目确认）；`CREATE TABLE IF NOT EXISTS` 不等于幂等修正——已建表的旧约束不会自动更新，迁移语句要显式写 ALTER。

#### S13. 并发正确性修复：条件 SET 原子流转取代"CAS + updateById 两步式"（2026-08-29，审查驱动修复）

- **结论**：状态机流转全部收敛为单条条件 UPDATE（WHERE id=? AND status=from SET status=to, deadline=...），取代"CAS 更新状态 + updateById 全字段覆盖"两步式；配合 vote 入口 SELECT ... FOR UPDATE 串行化"读状态→插票→计数→推进"，并发收官票不再卡死，撤回与投票并发不再产生孤儿票。
- **背景**：审查发现三步问题：①updateById 按 NOT_NULL 策略跳过 null 字段，撤回时 deadline 清不掉（前端详情显示旧截止时间）；②updateById 无条件覆盖全字段，并发下旧快照可静默回写状态；③vote 的"插票→COUNT→CAS 推进"是 check-then-act，两个收官票并发都判定"还差一票"，状态永不推进直到 36h 超时误作废。
- **话术**："状态机流转我坚持单条条件 UPDATE——WHERE 带 from 状态、SET 带 to 状态和 deadline，一个语句完成校验+流转+字段清理，比'先 CAS 再 updateById 整个实体'少一个事务内的竞态窗口。投票入口用 SELECT FOR UPDATE 把多步读改写串行化，悲观锁在这个短事务里比乐观锁重试更直接。"
- **追问1**："FOR UPDATE 锁行会不会拖慢并发？" → 投票场景单概念行、事务毫秒级，串行化代价可忽略；换来的是状态机不可卡死、审计与投票表一致。
- **追问2**："updateById 跳过 null 为什么是问题？" → MyBatis-Plus 默认字段策略 NOT_NULL：null 字段不进 SET——`setDeadline(null)` 后 updateById 实际没清 deadline。条件 UPDATE 显式 `SET deadline = NULL` 才能清。
- **追问3**：“乐观锁和条件 UPDATE 怎么分工？” → 草稿编辑（saveDraft）用 @Version 乐观锁（多写者冲突提示 1030）；状态机流转用条件 UPDATE（状态是流转判据，天然适合 WHERE 条件）；两种并发控制按业务形态分工，不混用。

#### K15. 【已踩】PowerShell 变量名大小写不敏感：$PASS 被 $pass 覆盖导致登录密码变 0（2026-08-29，D1 冒烟）

- **现象**：冒烟脚本登录永远 1003 用户名或密码错误，但同一段逻辑在 bash 内联执行却成功；调试脚本（几乎相同代码）也成功，唯独脚本文件失败，耗时近一小时定位。
- **原因**：PS 变量名不区分大小写——脚本里先定义 `$PASS = "Test123456"`，后定义 `$pass = 0`（Check 计数器），**后者覆盖前者**，Login 函数里 `password = $PASS` 实际提交 0。bash 内联版本没有 `$pass` 计数器变量，所以成功。
- **影响**：登录环节全部失败，后续断言连锁失败；且错误码 1003 与“真密码错误”无法区分，误导排查方向。
- **修复**：计数器改名 `$passCount/$failCount`，与密码变量彻底隔离；顺带把断言从“HTTP 状态码”改为“业务码”（鉴权失败 = HTTP 200 + code 401/403）。
- **复用教训**：PS 脚本变量命名必须全局唯一（不区分大小写）；调试变量名不要与业务变量撞名；同一逻辑“内联成功/脚本失败”时，优先怀疑作用域与变量覆盖。

#### K16. 【已踩】登录接口限流干扰调试：10 次/分钟 @RateLimiter 造成偶发 1003（2026-08-29，D1 冒烟）

#### K17. 【已踩】langgraph-checkpoint-postgres 2.x：from_conn_string 是上下文管理器，常驻服务不可直接持有（2026-08-29，D1 实现）

#### K18. 【已踩】create_agent 无 max_steps 参数：循环上限走 invoke 的 recursion_limit（2026-08-29，D1 实现）

#### S14. AI 会话留痕的成对写入策略：先落 user 消息、AI 失败保留、不落半截（2026-08-29，D1 实现）

- **结论**：Java 代理调 Python 前的写入顺序是**先落 user 消息 → 调 AI → 成功才落 assistant 消息**；AI 失败（1035）时 user 消息保留、assistant 不落。
- **背景**：会话表（concept_draft_session）是业务事实源，要同时满足三件事：①审计完整（发起人的每一条输入都留痕，即使 AI 挂了）；②重放永远成对（user 后面必有 assistant，不出现“半截对话”）；③重试不产生重复（失败时前端可重发，不会落两条 user）。权衡后：user 必落（审计），assistant 只在成功时落（重放干净）。
- **话术**：“AI 会话写入我按‘成对性’设计——user 消息先落库保证审计完整，assistant 只在 AI 成功返回后落，失败时用户看到 1035 提示、输入保留可重发；会话表永远成对，前端重放不需要容错逻辑。AI 挂了主流程零依赖，直接手动填表提交。”
- **追问1**：“AI 失败时 user 消息留着，重试会不会重复？” → 不会：失败时 assistant 没落，前端输入框保留原文，用户重发是一条新 user 消息；重放里不会出现无回复的孤儿消息（user 后必有 assistant）。
- **追问2**：“为什么不用事务包两条一起提交？” → 跨 HTTP 调用的“先落后调”天然不在同一事务（AI 是外部服务）；即使同事务，AI 失败回滚 user 消息会破坏审计（用户说过的话消失了）。

#### K19. 已踩·脚本层：PS 5.1 对无 charset 的 JSON 响应按 ISO-8859-1 解码，中文 mojibake（2026-08-29，D2 冒烟）

- **现象**：冒烟脚本里草案 reason 35 字符变 89 字符，"表单已同步"断言失败；python 侧同一接口解析完全正常。
- **原因**：Spring Boot JSON 响应 Content-Type 为 `application/json`（无 charset），PS 5.1 的 Invoke-RestMethod 对无 charset 响应按 ISO-8859-1 解码，中文字符（UTF-8 3 字节）变 3 个乱码字符；python httpx 按 UTF-8 解码所以正常。浏览器 fetch 也按 UTF-8，产品链路无损。
- **影响**：PS 冒烟脚本所有中文断言不可信；更糟的是把 mojibake 数据当入参提交，污染了测试库（采纳了乱码 reason）。
- **修复**：脚本统一改用 HttpWebRequest + StreamReader(UTF8) 显式解码（Invoke-Api 帮助函数）；污染数据用 python 脚本重新采纳恢复。
- **复用教训**：PS 5.1 与 JSON 接口交互必须显式 UTF-8 解码，Invoke-RestMethod 对无 charset 响应有编码坑；含中文断言的冒烟脚本一律走 Invoke-Api。

#### K20. 已踩·最严重：工具抛异常 → checkpoint 存坏历史 → 后续所有轮次 400 连环死锁（2026-08-29，D2 冒烟）

- **现象**：generate_draft 校验失败（decision_note 超 30 字）重试也失败后抛 RuntimeError，本轮 chat 500；**之后所有轮次**（即使换措辞）DeepSeek/MiMo 均返回 400 `tool_calls must be followed by tool messages`，无法自愈。
- **原因**：LangGraph ReAct 中 AI 消息（带 tool_calls）先落 checkpoint；工具抛异常时没有 ToolMessage 写入，checkpoint 存下"缺配对 tool 消息"的坏历史。下一轮续聊把完整历史发给 LLM，OpenAI 兼容协议要求 tool_calls 必须紧跟对应 tool 消息 → 400。坏历史永久存在于 checkpoint，每轮都 400。
- **影响**：单个工具异常导致该会话永久不可用（用户侧表现为 AI 一直 1035），需人工清 checkpoint 才能恢复。
- **修复**：① 工具函数**永不抛异常**：失败返回错误文本（说明原因 + 请模型重新调用/向用户说明），保证 LangGraph 主循环永远有 ToolMessage 可写；4 个工具全部 try/except 兜底。② 清理已污染 checkpoint（checkpoints/checkpoint_writes/checkpoint_blobs 三表按 thread_id 删除）。
- **复用教训**：LangGraph 工具函数是"消息契约"的一部分——异常会破坏消息配对完整性；任何工具的最外层必须是 try/except 返回文本，禁止裸抛。这是 ReAct 模式的状态安全红线。

#### K21. 已踩·超时链：MiMo 一轮 ReAct 40-60s，Java 30s / 前端 15s 超时双双命中（2026-08-29，D2 冒烟）

- **现象**：D2 冒烟 chat 全部失败：Java 日志 cost_time=30015ms（精确 30s）后报 "Error while extracting response ... application/octet-stream"；user 消息落库、assistant 不落。
- **原因**：MiMo 带思考/工具循环的完整一轮 ReAct 需 40-60s（多次模型调用叠加），远超 Java 代理的 30s 读超时（SimpleClientHttpRequestFactory readTimeout）与前端 axios 全局 15s；超时被 RestClient 包装成响应解析错误，误导排查方向。
- **修复**：Java `ai.draft.timeout-seconds` 30→120；前端 chatAi 单独 `{ timeout: 120000 }`（全局保持 15s 防普通接口悬挂）。
- **复用教训**：LLM 工具循环的端到端超时要按"一轮完整 ReAct"预算（多轮模型调用 + 工具往返），不能按单次模型响应估；DeepSeek 快（9s）掩盖了问题，换慢模型立刻暴露。

#### K23. 已踩·SQL：JSONB 列 insert 必须显式 CAST，varchar 隐式转 jsonb 被 PG 拒绝（2026-08-29，D2 实现）

- **现象**：落 tool 消息时 MyBatis-Plus 默认 insert 报 `字段 "tool_args" 的类型为 jsonb, 但表表达式的类型为 character varying`。
- **原因**：concept_draft_session.tool_args 是 JSONB 列，MyBatis-Plus 把 Java String 绑为 varchar 参数，PostgreSQL 不允许 varchar→jsonb 隐式转换（NULL 不受影响，所以只有 tool 消息炸）。
- **修复**：自定义 XML insert `CAST(#{toolArgs} AS jsonb)` + 空串防御（空串 CAST 也失败，置 null）；id 用 IdWorker 手动生成（XML insert 不走 ASSIGN_ID 自动填充）。
- **复用教训**：JSONB 列与 MyBatis-Plus 默认 insert 不兼容，读取用 `::text`、写入用 `CAST(... AS jsonb)`，两端都要显式。

#### S15. 工具输出宽容化：字段限长截断兜底 + 工具永不抛异常（2026-08-29，D2 收尾）

- **结论**：generate_draft 的结构化输出对模型宽容——校验失败先截断兜底（超长字段截到限长），仍失败返回错误文本而非抛异常。
- **背景**：decision_note 原定 30 字（一句话取舍摘要、进 trace 留痕），但模型频繁超限 → pydantic 校验失败 → 工具抛异常 → checkpoint 污染（K20）。30 字是对模型的苛求，用户拍板放宽到 100。
- **权衡**：限长是"质量护栏"（防超长字段污染表单），截断是"可用性兜底"（不让小毛病作废整份草案）；提示词仍引导短，截断只在模型不听话时生效。
- **追问1**：截断会不会截出语义残缺？→ 截断点在中文字符边界，只丢尾部修饰语，关键信息在前部，可接受。
- **追问2**：为什么不直接用 with_structured_output？→ 该机制对 MiMo 的 JSON 输出兼容性不稳定，手写 _extract_json + pydantic 校验 + 截断兜底三件套更可控。

#### K24. 已踩·工具链：Write 覆盖大文件时旧文件尾部残留，45 个编译错误（2026-08-29，D3 实施）

- **现象**：Write 覆盖 ConceptAiServiceImpl.java 后编译报 45 个"需要 class、interface、enum 或 record"错误，全部在文件 375 行之后。
- **原因**：Write 把新内容（374 行）写到文件前部后，旧文件 375 行起的残留内容（applyAiDraft 后半 + listMessages 重复 + 类闭合）未被截断，形成"新类闭合 + 旧代码碎片"的损坏结构。Save 环节报"unknown error"但部分写入已落盘。
- **影响**：编译失败一次，需人工 Read 确认 + python 截断修复（耗时约 5 分钟）。
- **修复**：Read 定位残留起始行（第一个类闭合 `}` 之后），python 截断到该行，验证关键方法存在 + 类闭合正确。
- **复用教训**：Write 覆盖已存在文件后必须验证文件行数与预期一致（Read 尾部）；出现"保存失败但 diff 正常"时优先怀疑文件损坏；大文件修改优先 SearchReplace 而非整体 Write。

#### S16. ai_brief 异步生成：提交不阻塞、失败零影响（2026-08-29，D3 决策）

- **结论**：概念提交后 ai_brief（发起人想法简析）由 @Async 异步生成，提交事务内只做状态机变更。
- **背景**：开发方案初稿"提交接口内调 Python /ai/brief"——但 MiMo 一轮生成 40-90s，同步内调会卡提交、占事务连接，且 AI 故障会阻塞提交主流程，违反"主流程零依赖 AI"原则。
- **权衡**：提交是原子状态机（CAS 防并发重复提交），不能把外部 LLM 调用放进同一事务；异步生成"提交时刻的会话"语义不变（提交后起草中校验禁止再对话，会话冻结），投票人/老师看到的内容与提交时刻一致。
- **实施**：submit 事务返回后由 Controller 调 `conceptAiService.asyncGenerateBrief(id)`（跨 bean 代理，@Async("logExecutor") 复用 log 线程池）；内部校验状态仍为 SUBMITTED 才生成（撤回/作废则跳过）；成功写 ai_brief + trace(ai_brief)，失败仅日志。
- **追问1**：异步生成中投票人看到什么？→ ai_brief 为 null 时前端不渲染区块（v-if），生成后自动可见。
- **追问2**：为什么 @Async 不放 submit 方法里？→ 自调用不走代理；放 Controller 编排层，事务提交后执行，时序干净。

## S18. 上帝服务拆分：门面模式混入业务域的判别与按域拆分（2026-08-30，结构梳理）

- **结论**："AI 能力门面"（Java 代理 Python 的服务）只应做代理转发，经验落库/SKILL 落盘是业务域动作——门面混入业务操作 = 上帝服务，后续每个域的扩展都会继续堆进同一个类。判别方法：看依赖注入数量与方法职责分类数；拆法按领域边界（经验域/技能域/会话门面），不是按方法数均分；Controller 必须只依赖 Service（越层 2 处一并修正：消息/日志查询迁入独立 Service）。
- **背景**：ConceptAiServiceImpl 448 行 9 方法注入 8 依赖，混了 AI 会话、经验、SKILL、定时/异步四类职责；MessageController/TeacherController 直接注入 Mapper（只读查询，分层规范破坏）。扫描方式：方法清单 + 注入关系 + Controller 越层三张清单，无循环依赖、接口-实现齐全（9/10）确认基建达标，问题集中在领域层职责粒度。
- **话术**："我做了结构体检：工程基建层（统一返回/异常/AOP 权限/日志/存储抽象）都是齐的，真正的风险是 AI 门面服务——代理转发和业务数据操作混在一起，448 行 9 方法 8 个依赖。判据是：门面只做转发，经验沉淀是业务域、SKILL 落盘是文件域。按域拆成会话门面/经验域/技能域三个服务，每个 100-200 行；顺手把两处 Controller 直连 Mapper 的越层修正掉。重构后回归：经验/SKILL 冒烟全绿，异步 brief 链路实测通过——行为不变是重构成功的第一标准。"
- **追问**："为什么不定时任务也拆出去？" → ConceptServiceImpl 的状态机聚合（11 方法含 scanTimeout）中，超时扫描与状态流转强相关（同事务改状态），拆出去收益低，后置为可选优化——拆分以职责边界为准，不是行数阈值。"重构怎么保证不破坏行为？" → 接口不变、逻辑原样迁移（不顺手改逻辑），回归跑既有冒烟脚本（D3 经验 7 项 + D4 SKILL 8 项）+ 补验异步 brief 与消息/日志接口。

## K27. 【已踩】雪花 Long ID 前端精度丢失：新增 VO 漏加 ToStringSerializer（2026-08-30，浏览器实测）

- **现象**：浏览器实测活动列表→详情导航报 1036"活动不存在"；发起人操作区不渲染；问卷三个字段前端解析出同一 ID，提交报"参数错误"。

## K28. 【已踩】SimpleBroker 只注册 /topic 漏 /queue：错误回执链路静默丢失（2026-08-30，浏览器实测）

## 子 Agent 边界与独立 RAG 问答服务（2026-08-30 讨论定稿）

### 一、子 Agent 概念澄清（技术含义）

- **定义**：子 Agent（Subgraph）= 嵌在主图内部的独立图，有自己的状态 schema、节点集、循环逻辑，通过"子图节点"挂入主图；主 Agent 执行到该节点时控制权移交，子图自主跑完再返回。
- **与工具的本质区别**：内部是否有 LLM 自主循环（LLM 参与每一步决策、循环次数/路径由运行时决定）vs 固定流程（内部可调一次 LLM，但下一步是写死的）。
- **判断标准（三条同时满足才用子 Agent）**：① 子能力内部需要多步自主决策；② 需要独立状态/记忆（一次调用表达不了）；③ 主 Agent 不需要也不应干预其内部过程。
- **概念谱系（防混淆）**：主 Agent（概念起草，独立服务）／ 独立 Agent（RAG 问答、复盘，并列的独立服务）／ 子 Agent·子图（嵌在某主图内部）／ 工具（主 Agent 可调用的能力，内部可调 LLM 但无自主循环）。**"子 Agent"特指子图**；RAG 问答服务有自己的主循环，属于"独立 Agent"而非"子 Agent"。

### 二、概念阶段边界确认（定稿）

- 概念阶段 7 个工具逐个核对：无任何一个子能力具备"内部自主决策"（检索=一次、生成=一次、读上下文=一次），全部保持工具形态。
- **不引入 interrupt**：交互模型是"一轮对话 = 图执行一次"，人确认在 Java/前端按钮；图内挂起需 resume 机制，与"Java 落库 + 前端确认"重复，硬加违反"finalize 移出图"决策。
- **不引入子图**：无自主决策需求；硬加（如"生成草案"子图内部重试）是重复主循环已有能力，收益为零。
- **升级触发条件（需求驱动，不提前拍）**：概念起草出现"深度多轮讨论"（主 Agent 自己决定检索维度/生成多候选/内部对比）时，才在其图内考虑子图；复盘 Agent 出现"内部多步自主"（自己决定补检索、回问负责人补录）时同理。

### 三、独立 RAG 问答服务（后续阶段·备用设计）

- **场景**：管理层（历史经验问答）/ 成员 / **访客（未参加社团的学生，快速了解社团）**多入口——访客场景证明其必须完全独立：独立入口、独立会话（thread）、独立权限分级（管理层全量 / 成员 / 访客受限，内容分级待设计）。
- **形态**：独立 Agent 服务（自己的图 + 自己的 thread + 自己的持久化），与概念起草主 Agent 并列，不是任何图的子图。
- **与主 Agent 衔接**：① 工具形态——主 Agent 调"统一检索工具"（读知识底座）；② 级联形态——工具内部 HTTP 调问答服务对话端点（Agent 调 Agent）。两者都仍是工具接口，不引入子图。
- **长记忆三层**：会话记忆（thread 持久化，PostgresSaver 已有机制）／ **社团知识底座**（经验库 experience_entry + 留痕向量 + 未来问答沉淀——真正的长期记忆，统一检索源）／ 用户偏好（轻量，先定义"记什么"再决定做不做）。
- **概念阶段经验复用** = search_experience 将来升级为"读同一个知识底座"的瘦客户端，数据源与 RAG 问答完全一致。
- **在线搜索**：MiMo 原生 web_search（OpenAI 兼容 API 的 tools 支持 web_search 类型；响应带 annotations 引用——网址/标题/摘要/发布时间；usage.web_search_usage 独立计量）。作为检索源 B（源 A 经验库 / 源 B 在线搜索），带引用可溯源，优于外部搜索 API 与纯常识兜底。
- **自适应检索（B1 已实现，2026-08-30）**：① 数据水位——Java `countForAgent` 统计本社团（含通用）非 thinking_pattern 经验总数，随 /ai/experience 返回 `similarActivityCount`；② 质量信号——search_experience 工具输出【数据水位】【历史经验命中】【在线检索补充】三要素；③ 主 Agent 策略（SYSTEM_PROMPT）——水位 ≥3 以经验为准 / <3 结合通用知识、命中不覆盖关键维度改写问句重试（上限 2 次）、覆盖度判断按子问题逐项核对；④ 联网兜底——工具内部独立 LLM 请求（MiMo 原生 web_search，`tools=[{"type": "web_search"}]`，响应带引用），原始搜索结果不进主 Agent 上下文；偶发失败降级为提示文案（永不抛异常，K20 铁律）；开关 B1_WEB_SEARCH_ENABLED、低水位阈值 B1_WEB_SEARCH_LOW_WATER（默认 3）。验证：web_search 真实调用返回整理要点 + 工具三要素断言 + 冒烟回归 8/8。
- **现状**：未实施，标注备用；概念阶段保持"工具 + 主 Agent 决策循环"形态。

#### K25. 【已踩】DETACHED_PROCESS 启动服务：cmd 弹窗 + 终端反馈丢失（2026-08-30）

- **现象**：用 subprocess DETACHED_PROCESS 启动 mvn spring-boot:run 和 uvicorn 后，桌面弹出两个 cmd 黑窗且常驻；我在终端拿不到任何服务输出（mvn -q 模式下日志文件甚至是空的）。

#### K30. 【已踩】MyBatis-Plus 纯 Mockito 单测：lambda cache 缺失 + insert 重载歧义（2026-08-30）

- **现象**：纯 Mockito 单测调用 Service 时抛 "MybatisPlus can not find lambda cache for this entity"（Lambda*Wrapper 构造失败）；`verify(mapper).insert(any())` 报 "method is ambiguous"。
- **原因**：① MP 的 Lambda*Wrapper 需要 TableInfo 缓存，该缓存只在 MyBatis 初始化（Spring 上下文）时填充，纯 Mockito 无上下文则为空；② MP BaseMapper.insert 存在重载，裸 any() 匹配歧义。
- **影响**：单测无法直接使用 LambdaQueryWrapper/LambdaUpdateWrapper；verify 编译不过。
- **修复方案**：① @BeforeAll 里 TableInfoHelper.initTableInfo(new MapperBuilderAssistant(new MybatisConfiguration(), ""), 实体类) 手动初始化（官方单测同法），只为被测 Service 用到的 Lambda 实体初始化；② insert/convertAndSend 等重载方法的匹配一律类型化 any(具体类.class)。另注意：mock selectList 返回列表时不会执行 SQL 条件过滤，测试数据需模拟"数据库已按条件过滤"（如 eq(adopted,true) 的查询只返回 adopted=true 的记录）。


#### K31. 【已踩】jsonb 列与 Java String 参数类型不匹配：updateById 静默失败（2026-08-31）

- **现象**：活动总结生成卡在 pending 状态，无任何失败日志；线程 dump 无异常线程，DB 行停在 insert 时刻。
- **原因**：DDL 列类型 JSONB（report/questions/answers），Java 实体是 String。MP updateById 生成 `SET questions=?`（varchar 参数），PostgreSQL 报 `字段 "questions" 的类型为 jsonb, 但表达式的类型为 character varying`（BadSqlGrammarException）。updateById 在 try/catch 外 → @Async 线程异常，SimpleAsyncUncaughtExceptionHandler 只打 ERROR 日志（增量终端输出易被淹没），DB 无更新。
- **影响**：总结生成看似"卡死"，实际是异常被吞；排查成本高（先查 jstack 才发现异常）。
- **修复方案**：DDL 改 TEXT（Java 侧整存整取，不用 jsonb 操作符/索引时 TEXT 完全够用）。教训：JSONB 列要么用 PG 驱动 stringtype=unspecified（见 K33 的坑），要么实体字段保持 String + 列用 TEXT；@Async 线程的异常排查要看完整日志文件而非增量输出。

#### K32. 【已踩】已存在行走 insert：主键冲突静默失败（2026-08-31）

- **现象**：手动"重新生成总结"后无任何 DB 变化（retry_count 不变），Python 服务未收到请求。
- **原因**：generate 的 upsert 用 `hasText(report) || hasText(questions)` 判断 insert/update——已存在的行（report/questions 为空）落入 insert 分支 → 主键冲突 DuplicateKeyException（try 外）→ 异步线程死亡。
- **影响**：重生成功能完全失效且无提示。
- **修复方案**：用 `boolean exists = s != null` 判断分支（s 从 selectOne 来即已存在）。教训：upsert 分支判断必须基于"是否存在"而非"业务字段是否为空"。

#### K33. 【已踩】stringtype=unspecified 与 `? IS NULL` 冲突（2026-08-31）

- **现象**：JDBC URL 加 `?stringtype=unspecified`（jsonb 修复方案）后，经验检索 SQL 报 `无法确定参数 $3 的数据类型`。
- **原因**：stringtype=unspecified 让 PG 把所有 String 参数当"未指定类型"，`? IS NULL` 上下文要求参数类型已知 → 推断失败。
- **影响**：全局开关影响所有 SQL（含老 SQL），回归风险大。
- **修复方案**：放弃 unspecified，直接 DDL jsonb→TEXT（K31 方案）。教训：全局 JDBC 参数开关慎用，优先局部类型对齐。

#### K34. 【已踩】LangGraph 1.2 子图 + 中断机制三个细节（2026-08-31）

- **现象**：① `class S(dict): pass` 状态写不进去（resume 后状态为空）；② `interrupt_before=["子图.节点"]` 编译报 `Interrupt node not found`；③ LLM 输出 JSON 带说明文本/多个对象时 json.loads 报 Extra data。
- **原因**：① LangGraph 状态必须 TypedDict 显式声明（无注解 dict 子类无 channel 定义）；② 1.2 的 interrupt_before 只接受主图节点名，不支持子图路径；③ LLM 输出不稳定。
- **影响**：子图中断恢复机制跑不通、结构化输出解析失败。
- **修复方案**：① TypedDict + total=False；② 用节点内 `interrupt()` 函数（运行时动态中断，主图 compile 无需配置，恢复用 `graph.invoke(Command(resume=value), config)`）；③ `json.JSONDecoder().raw_decode` 取第一个完整 JSON 值（先 { 后 [）。验证要点：中断后 `graph.get_state(config).next` 非空、`st.tasks[0].interrupts[0].value` 可取待确认问题。

#### K35. 【已踩】Python 直接回调 Java 401：异步线程无 SecurityContext（2026-08-31）

- **现象**：总结子图 retrieve_history 节点用 java_get 回调 Java 经验接口，返回 401 未登录。
- **原因**：Java 触发总结是 @Async 线程（无 SecurityContext），无 token 可透传；Python 侧独立请求也无 Authorization。

#### S23. 总结 Agent 子图架构：LangGraph 嵌套图 + 跨语言 HITL 中断恢复（2026-08-31）

- **结论**：活动总结用主图（ingest→review→output）+ 子图（audit→decide 条件边→clarify/retrieve_history/draft→lessons）实现，结构化指标 Java 算、AI 只做文字总结与经验提炼；跨语言人机协同用 PostgresSaver checkpoint（thread_id=activity_id）+ 子图内 interrupt() 实现"AI 提问→发起人回答→恢复生成"闭环。
- **背景**：总结需要 ① 确定性数据（Java 聚合七维指标）② AI 文字生成 ③ 数据异常时人工澄清（如留痕覆盖率低）④ 历史经验参考。单 Agent 对话无法表达"有条件的中断与恢复"，用图结构表达流程。
- **话术**："LangGraph 嵌套图表达业务流程：主图管生命周期（ingest→review→output），子图管审查细节（audit 规则审计 → LLM 条件边决策 clarify/history/ready 三路 → draft → lessons）。跨语言 HITL：checkpoint 存 Postgres，thread_id=activity_id；AI 需要人工信息时在子图节点内 interrupt() 暂停，Java 侧展示问题清单，发起人回答后 Command(resume=answers) 注入恢复，decide 节点见 answers 已存在即防死锁降级不再二次中断。子图内中断由最外层图统一处理，这是 LangGraph 1.x 嵌套图 + HITL 的标准玩法。"
- **追问**："中断后服务重启能恢复吗？" → 能，checkpoint 持久化在 Postgres，thread_id 不变即可从上次中断点恢复。"LLM 输出不稳定怎么办？" → 三层兜底：raw_decode 容错解析、decide/lessons 失败用默认值（ready/兜底经验）、draft 失败降级结构化数据摘要，图永不因 LLM 异常中断。"为什么不用 create_agent？" → 总结是确定性流程（审计→决策→起草→沉淀），不是自由对话，图节点比 ReAct 循环更可控；对话类（概念起草/文件撰写）才用 create_agent。#### S24. 操作日志密码脱敏的字段名规则：递归覆盖 + 白名单字段名（S1，2026-08-31，审查修复）

- **结论**：操作日志的参数脱敏不列字段白名单（新增接口漏配就裸奔），用字段名规则——递归遍历 Map/Collection/POJO，字段名小写包含 password/secret 即打码（复数 passwords、嵌套 DTO 全覆盖）。存储层存量数据用 SQL 正则 REPLACE 幂等清洗（开发库也可直接 TRUNCATE）。
- **背景**：审查发现日志切面只对精确字段名（password）脱敏，register DTO 里的明文密码字段没盖住；白名单式脱敏每新增一个接口都要记得配，漏配即泄漏。
- **话术**："日志脱敏我用字段名规则而不是字段白名单：递归遍历参数树，凡字段名小写含 password/secret 就打码——新增接口零配置也不会裸奔，嵌套 DTO、复数名都能覆盖。存量已入库的明文用 SQL 幂等清洗，脚本可重复跑。"
- **追问1**："字段名规则会不会误伤？" → 如 secretary 含 secret 会被打码——本项目字段无此冲突；规则覆盖度优先，打码比泄漏安全。"为什么不入库前脱敏？" → 入库存业务语义数据（审计需要），脱敏是展示层职责，两者分开。

#### S25. 慢 AI 调用的线程池隔离与拒绝兜底：小池 + AbortPolicy + 被拒直接落 failed（C3+B1，2026-08-31，审查修复）

- **结论**：AI 慢调用（40-90s）不能混用业务/日志线程池（会把定时任务池占满、日志写入堵死）。独立 aiExecutor：core 2/max 2/queue 50/AbortPolicy。被拒时不能只打日志——generate 未执行就没有"失败行"可被重试扫描器捞，必须在拒绝点立即 upsert failed 行（retry_count 不递增），定时重试才能接管。同批发现的隐性死锁：留痕截止自动收口依赖的调度器从未注册（类存在但无 @Scheduled 方法），状态机卡在留痕中只能人工 SQL——扫描器是状态机收敛路径的一部分，缺一个就是死锁。
- **背景**：审查逐类核对 @Scheduled/线程池时发现：SummaryScheduler 用 logExecutor（4 线程）排队总结任务，多活动同时总结把日志写入也堵死；RecordDeadlineScheduler 类存在但无注解方法，扫描从未执行。
- **话术**："慢 AI 调用我给了独立小池（2 线程 + 队列 50），把总结这类 40-90 秒的调用和日志、业务线程隔开——小池满时拒绝而不是排队拖垮别的池。拒绝点要兜底：任务还没跑就没有失败行可扫，我在拒绝时直接落 failed 行，重试调度器接管。审查还发现一个隐性死锁：留痕截止自动收口根本没注册调度器，活动卡在留痕中只能人工 SQL——状态机所有收敛路径都必须有对应扫描器。"
- **追问1**："为什么用 AbortPolicy 而不是 CallerRunsPolicy？" → 调用者是状态机推进线程，让调用线程自己跑 AI 会阻塞状态推进（违背"推进不被慢调用拖住"初衷）；AbortPolicy + 落 failed 行把重试交给后台。
- **追问2**："拒绝时落 failed 行，重试会不会一直失败？" → retry_count 不递增（不是生成失败，是没机会生成），重试间隔照旧，AI 恢复后自然成功。

#### S26. 分布式防重的"真防抖"：成功靠 TTL 自然过期、失败立即删 key（C1，2026-08-31，审查修复）

- **结论**：防重切面的正确语义是"窗口期内同一请求只允许一次尝试"，不是"执行完就放行"。真防抖：成功不删 key，窗口内（TTL）重复请求全部拒绝；失败路径立即删 key 放行重试——防重防的是并发双击，失败重试是用户正当诉求必须放行。旧实现 finally 无条件删 key：并发双击挡不住，业务失败也能立即重放，配合重试逻辑形成无限循环。
- **背景**：审查发现 RepeatSubmitAspect 在 finally 无条件删 key——两个请求一前一后（第一个未完成）会同时通过；且与"失败可重试"的调度语义叠加成死循环。
- **话术**："防重切面我按防抖窗口重新设计：进来 SETNX 占位，成功就让它自然过期——窗口内重复请求被拒；业务抛异常立即删 key，失败重试立刻放行。关键区分是成功和失败路径对 key 的处理必须不同。"
- **追问1**："成功不删 key，用户正常重试怎么办？" → 业务成功本身不该重试（幂等），窗口 3-5 秒后 TTL 自然释放；真需要重试的场景（AI 超时）走失败路径立即放行。
- **追问2**："防重 key 粒度？" → 方法+用户+IP+参数（S9 已定），不同目标互不干扰。

#### S27. 内部服务间认证：X-Internal-Secret 默认头 + 中间件校验（S5，2026-08-31，审查修复）

- **结论**：Java→Python 内部调用统一走 PythonClientFactory（DCL 懒初始化 + 默认头 X-Internal-Secret），Python FastAPI 加 http 中间件校验该头（/health 放行）；secret 缺失时 Java warn 不带头、Python 跳过校验——fail-open 仅限内网直连部署，暴露公网必须设置。4 处重复的 RestClient 构建收口为一个工厂（顺带修 DCL 单例隐患）。
- **背景**：审查发现 4 处 Java 代码各自 new RestClient 调 Python，无任何内部认证；Python 侧接口裸奔（任何人可调总结/起草接口）。
- **话术**："Java 调 Python 的内部接口我加了密钥头认证：统一工厂构建 RestClient 默认带 X-Internal-Secret；Python 中间件校验，health 放行。设计留口子：secret 缺失只 warn 不 fail-fast——内网直连可跑，部署文档标注为收紧项。"
- **追问1**："为什么不用 mTLS/JWT？" → 服务对服务场景，共享密钥头 + HTTPS 内网是成本最低的够用方案；JWT 要签发刷新、mTLS 要证书生命周期，超出当前威胁模型。
- **追问2**："secret 怎么轮换？" → 环境变量下发，工厂每次 get() 从配置读，改环境变量重启即生效。

#### K36. 【已踩】PowerShell 批量文本替换三连坑：CRLF 不匹配 + 位置参数数组展开成字符级替换污染（2026-08-31，Q1 重构）

- **现象**：用 PowerShell 函数做 Java 文件批量替换：① 所有替换全部 MISS（文件没变）；② 改用 here-string 传键值对后，文件被字符级替换污染——ownership 变 wwnership、Long 变 Lwng、@Transactional 变 @Transactiwnal，编译全面崩溃；③ 同命令反复执行污染叠加（ownership.ownership.ownership）。
- **原因**：① 目标文件是 CRLF 换行，脚本里的键是 LF——精确匹配必然失败；② 自定义函数用位置参数传数组，PowerShell 把数组展开成多个参数绑定到后续形参，函数内部 foreach 遍历的其实是字符串的字符——Replace('o','w') 变成逐字符替换。
- **影响**：源码被字符级污染（需 git checkout 恢复），多轮修复验证失真，浪费约 1 小时。
- **修复方案/处理**：① 放弃 PowerShell 文本操作，改用 Python 脚本（io.open utf-8 + str.replace + 断言替换次数）；② 替换前先 Read 确认换行符（CRLF/LF）；③ 每次替换后立即编译验证；④ 污染文件 git checkout 恢复（恢复不生效时先确认文件被 git 跟踪且无未提交干扰）。
- **复用教训**：PowerShell 批量替换文件是高频坑：函数位置参数传数组会被展开（显式 -ArgumentList 绑定）；CRLF/LF 混用导致精确匹配失败时先 normalize 换行；文本替换类操作优先 Python（确定性更强），做完立即编译验证。

> 依据：`docs/双项目集成方案-经验复用闭环.md`（D1–D8 决策 + 十任务清单），10 任务全部实施并验收通过。
> 闭环：管理层上传活动文件 → club 存储落表 → 推 rag 入库（解析/切块/向量化）→ 概念 Agent 起草时 search_experience 双源检索（SQL 经验 + rag 文件）→ 草案引用历史经验并带来源溯源。

### 实施内容

**rag 侧（知识引擎，只加不改原有行为）**
- `user_file` 增加 `owner_type`/`org_id` 列（personal/org 互斥隔离），`init_chunk.sql` §10 幂等迁移，本地库已执行验证；`user_id` 放开 NOT NULL（org 文件无属主用户，方案外发现）
- `retriever._scope_filter` 增加 org 分支：两空间互斥（同时指定抛 ValueError，防越权混查），新增 `test_retriever_scope.py` 6 用例
- `/api/org` 四端点（X-Internal-Key 鉴权）：`ingest`（multipart → sha256 秒传去重 → 原子 move → parse_tasks 幂等入队，复用整条解析管线，worker 零改动）、`deactivate`（软删）、`status`（懒同步用）、`retrieve`（检索器模式：只返回 chunks，不接生成——生成留在概念 Agent）

**club 侧（业务语义与编排）**
- Java：`RagClientFactory`（DCL RestClient + ingest/deactivate/retrieve/queryParseStatus + 单测 2 用例）；`activity_file_lib` 表 + 上传/列表/删除接口（白名单+50MB、推 rag 失败标 failed 不阻断、软删+存储清理+rag 失效）；`/clubs/{clubId}/ai/knowledge` 双源检索（SQL 经验条目 + rag 文件，@ClubPermission 校验）
- Python：`search_experience` 双源升级——输出【数据水位】【历史经验命中】【文件资料命中】（带来源《文件名》> 章节 [第X页]），低水位或两源未命中才联网兜底；Python 不直连 rag，鉴权链 Python→Java→rag
- 前端：ActivityDetail 增加"活动资料"区块（上传 / 入库状态流转标签 / 仅管理层删除）
- 配置：`.env` 增加 RAG_ENABLED / RAG_BASE_URL / RAG_INTERNAL_KEY，rag 关闭时文件业务不阻断（降级开关）
