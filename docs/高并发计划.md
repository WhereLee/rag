## 背景与目标

- **部署环境**：单机 4G 云服务器，Java 网关（8082）+ PostgreSQL + Python RAG 服务（8090，模型常驻）+ 前端静态资源共机。
- **核心目标**：
  1. 在 Java 侧完整经历高并发实现与调优（热点缓存、限流、连接池、异步化、JVM/GC），找到**实测极限值**；
  2. 用压测数据论证"流量超出 Java 极限时，由 Go 旁路组件接管读路径"的引入时机——把"交叉点"从数学推演变成实测结论；
  3. 为面试沉淀完整的演进故事：单语言全量 → 部署压测 → 分层调优 → 瓶颈定位 → 组件化扩展，全部有真实数据支撑。

## 决策记录（重要，防止走回头路）

1. **先做 RAG，后做高并发**（2026-08-20 用户决策）：RAG 的本地 ONNX 模型（embedding/reranker）与 VLM 缓存会常驻占用内存，调优目标环境的"内存预算"必须包含它们；否则调出的极限脱离真实部署形态，没有参考价值。
2. **否决"短链切一半"方案**（Java 创建 + Go 跳转）：用户要求 Java 侧完整学习高并发，把读路径（跳转）预先切给 Go 会让 Java 失去高并发场景。**Go 必须由实测瓶颈数据驱动引入，而非先验设计**。
3. **排期顺序**：RAG 管线（方向 A）→ 短链分享 Java 全量 + 部署 + 压测调优（本计划）→ Go 扩展（本计划阶段五）→ 部署收尾 5b。

## 阶段一：短链分享（Java 全量实现）

**功能范围**（全部 Java 实现，复用文件域基础设施）：
1. 创建分享：鉴权、权限校验（归属）、有效期、可选访问密码、审计日志 → 生成短码（base62，8 位）入库；
2. 跳转解析：`GET /s/{code}` → 查缓存 → 查库 → 校验有效期/密码 → 302 到下载地址；
3. 分享下载：`GET /api/shares/{code}/download`——**分享链接本身就是授权凭证**，与 JWT 登录态两套权限模型分清楚；支持撤销（删除分享）、计数；
4. 热点缓存：内存 LRU + TTL（如 60s）；演进路径：多实例时换 Redis 共享缓存；
5. 访问计数：异步/批量更新（防热点行锁），与秒传体系的 sweepBlobs 同思路——计数漂移由对账收敛；
6. 前端入口：分享按钮 + 链接展示 + 撤销。

**验收**：沿用双测试方法论（normal + edge：越权访问他人分享、过期、密码错、撤销后访问、并发计数、缓存命中与失效）。

## 阶段二：部署与压测基线

1. 部署形态：Java 网关 + PostgreSQL + Python RAG（模型常驻）+ 前端静态（nginx 或直接静态托管）；
2. 压测工具：JMeter（登录 / 上传 / 下载 / 分享跳转四个场景，各自独立脚本 + 混合场景）；
3. 基线：先压**未调优状态**，记录 QPS、p99 延迟、内存占用、GC 频率与停顿；
4. 压测标准（先行约定，防无底洞）：
   - 阶梯加压：并发数 10 → 50 → 100 → 200 → 500，每档跑满 5 分钟取稳态；
   - 稳态判定：QPS 波动 < 10% 且无错误率上升；
   - 极限定义：**p99 < 200ms 条件下的最大 QPS**；CPU 稳态 ≥ 85% 或内存打满视为资源耗尽线。

## 阶段三：分层调优（每层调完重压，记录变化）

| 层 | 调优项 | 观察指标 |
|---|---|---|
| JVM | -Xmx 与内存预算对齐、GC 选择（G1 起步，观察停顿）、线程栈 | GC 停顿、堆使用、OOM 风险 |
| 应用 | 线程池、异步化（计数/审计）、热点缓存命中率 | 线程数、等待时间、缓存命中 |
| 连接池 | HikariCP maximum-pool-size 与 PG 连接上限匹配 | 连接获取等待、池耗尽错误 |
| 数据库 | shared_buffers、work_mem、索引、慢查询 | 慢日志、锁等待、IO |
| 网络/OS | 文件描述符、TIME_WAIT、TCP 参数 | 连接建立失败、队列溢出 |

**预期**：瓶颈很可能先出现在 PostgreSQL（同机共享内存）而非 JVM——"分层定位瓶颈"本身就是高并发最值钱的经验。

## 阶段四：极限定位与瓶颈分析

1. 输出各场景极限表：场景 × 并发档位 × QPS × p99 × CPU × 内存 × GC；
2. 瓶颈分析：定位极限被哪一层卡住（线程？GC？DB 连接？磁盘 IO？），给出证据（jstat/jstack/慢查询日志）；
3. 结论格式示例："Java 在 4G 机器上，跳转场景 p99<200ms 的极限约 X QPS，瓶颈为 PG 连接数，CPU 未打满"。

---

## 阶段五：Go 旁路组件（数据驱动引入）

1. **引入原则**：只接管实测瓶颈路径（预计为跳转/下载等连接密集的读路径），不迁移有状态业务；
2. Go 组件形态：无状态 HTTP 服务 + 内存缓存 + 批量计数，读 DB 只查只读副本或直连（与 Java 同库）；
3. 对比压测：同机、同资源上限下，Go 组件的 QPS / 内存峰值 vs Java 基线；
4. 结论：**交叉点实证**——"流量 > Java 实测极限 X 时，读路径由 Go 接管"；
5. 面试价值：这不是"Go 比 Java 快"的空话，而是同一资源约束下两组实测数据的架构决策。

## 内存预算（4G 云服务器，调优时每个组件上限必须对齐）

| 组件 | 预算 |
|---|---|
| PostgreSQL（shared_buffers 128MB + 连接 + 缓存） | ~0.5 GB |
| Java 网关（堆 1GB + 元空间/线程/堆外） | ~1.5 GB |
| Python RAG（进程 + bge-base ~130MB + reranker ~200MB + VLM 缓存） | ~1.2 GB |
| 系统 + 前端静态 + 缓冲 | ~0.5 GB |
| Go 旁路（未来阶段五） | ~0.2 GB（届时从 Java 侧压缩腾挪） |

> 约束：调优时 JVM 堆、PG shared_buffers、Python 常驻三方互相挤占，任何一方调大必须说明从哪一方腾出。

## 面试故事线（本项目可讲的完整版本）

1. **为什么先 RAG**：调优的基线必须包含真实部署形态的内存占用——模型常驻是环境事实，不是参数；
2. **Java 全量 + 分层调优**：展示"定位瓶颈在 DB 连接层"的方法论，而非背参数；
3. **极限的量化定义**：p99 < 200ms 下的最大 QPS——可度量、可复现；
4. **Go 的引入时机**：实测数据证明"超过 Java 极限的流量由 Go 接管"，交叉点从推演变实测；
5. **与项目原则一致**：JWT 无状态、可多实例化、Redis 演进路径——组件化扩展是既有架构原则的自然结果。
