## 1. 单元 A：入库异步任务系统（面试拷打 Q6 / Q8 / Q9 / Q10）

### 1.1 目标
提交与执行解耦：HTTP 只收件（秒回 202），重活交给后台 worker；任务状态全程落库、可查进度、可断点续跑、可重试、幂等防并发双插。

### 1.2 数据模型（新增 `ingest_job` 表，迁入 `scripts/init_db.sql` 或新增迁移脚本）

```sql
CREATE TABLE IF NOT EXISTS ingest_job (
    id BIGSERIAL PRIMARY KEY,
    job_key VARCHAR(100) UNIQUE NOT NULL,          -- 幂等键：sha256(user_id:file_hash:replace)
    user_id BIGINT NOT NULL REFERENCES kb_user(id),
    filename VARCHAR(500) NOT NULL,
    doc_type VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'queued',  -- queued/running/done/failed/dead
    stage VARCHAR(30) NOT NULL DEFAULT 'pending',  -- parsing/chunking/embedding/indexing
    progress FLOAT DEFAULT 0,                      -- 0~1
    step_detail JSONB,                             -- 页级/阶段级明细
    attempt INT DEFAULT 0,
    max_attempts INT DEFAULT 3,
    lease_until TIMESTAMP,                         -- worker 租约（staleness 巡检回收依据）
    error TEXT,
    trace_id VARCHAR(50),
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_ingest_job_status ON ingest_job(status, lease_until);
```

- **幂等键唯一约束**是并发双插的最终防线（应用层先查再插存在竞态窗口）。
- 设计决策：`job_key` 含 `replace` 意图位 —— 同名替换是新意图，不允许与老 intent 共用 job。

### 1.3 API 语义变更（`rag-python/src/api/ingest_api.py`）

| 接口 | 变更 |
|---|---|
| `POST /api/ingest/upload` | 校验/落盘后**立即返回 `202 {job_id, status:"queued"}`**，不再同步跑全链 |
| `GET /api/ingest/jobs/{job_id}` | 轮询进度快照：status/stage/progress/step_detail 摘要/error |
| `GET /api/ingest/jobs?user_id=` | 当前用户任务列表（前端「任务中心」用） |
| `POST /api/ingest/jobs/{job_id}/retry` | failed/dead 人工重试入口（重置 attempt，status→queued） |
| 既有 `status/{doc_id}` / `documents` / `chunks` | 保留（文档级视角不变） |

**弃用说明**：`ingest_path`、`ingest_directory` 已在多租户下禁用/仅脚本使用，脚本同步直调改走 worker 语义（进程内直调 worker.process_job）。

### 1.4 后台 worker（新增 `rag-python/src/ingest/worker.py`）

- 独立进程启动（`python -m ingest.worker`），与 API 进程解耦。
- 主循环：
  1. 抢任务：`SELECT ... FROM ingest_job WHERE status='queued' OR (status='running' AND lease_until < NOW()) ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1`
     - `SKIP LOCKED`：多 worker 并发消费不冲突（可横向扩展）。
     - `lease_until < NOW()`：staleness 回收 —— worker 崩溃后任务不永久卡 running。
  2. 抢到后：`UPDATE ... SET status='running', stage, lease_until=NOW()+interval '5 min'`。
  3. 分阶段执行（复用 `sync_service.ingest_file` 拆出的内部逻辑，提升为可独立调用函数并在每页/每阶段回调更新 step_detail + progress）。
  4. 成功：`status='done'`；失败：attempt+1，`attempt < max_attempts` → 退避重试（status='queued'，`lease_until` 置空），否则 `status='dead'` + error 落库。
  5. 每次阶段/页更新：`UPDATE ingest_job SET stage, progress, step_detail, updated_at=NOW()`。
- **断点续跑**：复用现有双层缓存（`data/parsed/{hash}.json` 解析缓存 + `vlm_cache/{hash}.json` 页图缓存），重试时已成功页面零成本跳过 —— 这是"LLM 恢复后失败任务怎么办"的价值实现。
- 与现有单测/脚本的隔离：`run_experiments.py` 等不走 HTTP 的调用不受影响。

### 1.5 前端（`rag-frontend/src/views/Documents.vue` + `api/client.js`）

- 上传成功 → 显示任务卡片（job_id、文件名、阶段、进度条、失败页明细），**轮询 `GET /jobs/{id}`**更新进度；失败态给「重试」按钮。
- 删除现在的假进度（`uploadProgress 30/60/100` 硬编码）。
- `listDocuments/documentChunks/deleteDocument` **改走网关代理**（见单元 C，同一批改动，但归属安全收口）。

### 1.6 验收口径（对应拷打问题）

- [ ] 提交 50MB 扫描 PDF，1s 内拿到 `job_id`，HTTP 不挂起（Q8）
- [ ] 轮询能看到 stage 与 progress 递增；任务明细精确到页（Q8/Q12）
- [ ] 模拟 VLM 第 N 页失败：attempt 退避重试，重试时已成功页跳过（Q6/Q4）
- [ ] 模拟 worker 进程被杀：staleness 巡检（或新 worker 抢到过期租约）将任务回收重跑，不永久卡 running（Q9）

## 2. 单元 B：VLM 可靠性 + 可观测（面试拷打 Q4 / Q5 / Q7 / Q12）

### 2.1 VLM 调用分层处置与输出校验（`rag-python/src/ingest/vlm.py`）

- `chat_json` 调用结果带出 `token_in / token_out / elapsed_ms`，写入 `step_detail` 与结构化日志（**消除写死 0 欠账**）。
- 分层失败处置（与 `mimo_client` 已有重试配合，worker 层区分）：
  - 5xx / 超时 → 该页重试（退避），整批不因单页失败而失败
  - 429 → 快退避 + 熔断计数
  - 4xx（除 429）→ 不重试，直接页级标记 failed
  - JSON 解析失败 → 宽容提取兜底（已有）；仍失败 → 页级 failed(parse)
- **输出内容校验**（防"VLM 没抛错但返回坏东西"）：
  - 表格通道：输出必须含 markdown 表头分隔行（`|---|`）或 `no_table`；行列数 1≤n≤50
  - 扫描页通道：转录文本长度低于阈值 / 无换行 → 页级 failed(validate)
  - 校验失败页标记进 `step_detail`，**不阻塞整批**（与现有 `failed_pages` 语义一致）。

### 2.2 入库侧熔断接入（`rag-python/src/agent/circuit_breaker.py`）

- 把断路器从「问答侧单例」抽象为**按用途实例化**（factory：`get_breaker("qa")` / `get_breaker("vlm_ingest")`）。
- worker 每次 VLM 调用前 `allow_request()`，成功后 `record_success()`，失败 `record_failure()`。
- breaker OPEN 时：**不做无意义重试** —— 当前任务快速置 `failed(breaker_open)` + 退避后进 queued（或直接 dead 等人工），避免对已挂的 LLM 打重试风暴。

### 2.3 全局错误响应带 trace_id（`rag-python/src/api/app.py`）

- 全局异常 handler 与 SSE error 事件统一返回 `{"error": ..., "trace_id": ...}`。
- Java 网关 `ChatController`/`AdminProxyController` 异常分支透传 Python 响应中的 trace_id（改 3 处 catch 块）。

### 2.4 验收口径

- [ ] VLM 调用日志含 token/elapsed；`step_detail` 可查每次页级 VLM 的耗时与成本（Q12）
- [ ] 连续 N 次 VLM 失败后熔断打开，不再发起调用（Q5）
- [ ] VLM 返回垃圾表格/空转录被校验拦截并页级标记，不产生脏 chunk（Q7）
- [ ] 用户报障可凭错误响应中的 trace_id 串查全链路日志（Q12）

## 3. 单元 C：安全收口残项 + 注入检测（面试拷打 Q13 / Q14 / Q15）

### 3.1 文档查询/删除收口走网关（`rag-java` + `rag-frontend/src/api/client.js`）

- GET 查询（`documents / status / chunks`）：前端改走 `GET /api/admin/proxy/api/ingest/...`（网关 `GET_ALLOWED` 已含 `/api/ingest`，**零新增 Java 代码**）。
- DELETE（`deleteDocument`）：网关新增专用端点 `DELETE /api/admin/proxy/api/ingest/documents/{id}`（显式端点，不用通配 DELETE 透传，防暴露 Python 任意 DELETE 路径），user_id 从 JWT 取。
- Python 侧纵深：`documents/chunks/delete` 对 unsigned 请求（无网关签名头）拒绝 —— 网关注入 `X-Gateway-Sign: HMAC(X-User-Id)`，Python 校验签名后才信任 `X-User-Id`（解决"直连可伪造 X-User-Id"的信任边界漏洞，FAQ：内部签名校验）。

### 3.2 文件 magic bytes 嗅探（`rag-python/src/api/ingest_api.py`）

- 后缀白名单保留；增加内容嗅探：PDF `%PDF`、PNG `\x89PNG`、JPEG `FF D8 FF`、DOCX `PK\x03\x04`（且 zip 内含 word/）、文本类 UTF-8 可解码。
- 头字节与后缀不一致 → 400 拒绝（防伪装扩展名）。

### 3.3 VLM 转录内容指令注入检测（`rag-python/src/agent/prompt_guard.py` 扩展）

- 现有 `sanitize_query`（用户 query 净化）扩展出 `sanitize_doc_content(text)`：
  - 规则匹配（"忽略之前的指令/你现在是/system 覆盖/输出 markdown 指令"等模式）+ 可选轻量 LLM 分类。
  - 接入点：VLM 转录/结构化文本**入 chunk 前**（`sync_service` 或 worker 的 chunking 阶段）。
  - 命中 → 该页标记 `suspicious` 且不入 chunk 向量化（记 step_detail，可人工复核）。

### 3.4 验收口径

- [ ] 伪装扩展名（如 exe 改 .pdf）被 400 拒绝（Q13）
- [ ] 前端不再直连 8090 的文档读写接口，所有调用带服务端注入的 user_id（Q14）
- [ ] 直连 Python 且伪造 X-User-Id 的请求被签名校验拒绝（Q14 信任边界）
- [ ] 含指令注入的图片转录文本被拦截，不进入知识库（Q15）
