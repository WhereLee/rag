## 一、项目经历文案（可直接复制）

**社团管理 Agent —— 面向社团内部管理的 Agent 化改造系统**（独立全栈项目）
技术栈：Java 17 / Spring Boot 3.5 / MyBatis-Plus / PostgreSQL / Redis / JWT / Vue3 / Element Plus / Pinia / Python FastAPI / LangGraph

- 设计并实现活动概念全生命周期状态机（起草 → 双人投票 → 复议 → 老师批复 → 通过/作废）：状态流转收敛为单条条件 UPDATE（WHERE status = from），从根上杜绝并发双击双推进与"CAS 后全字段覆盖"的竞态窗口；"一社团一活跃概念"由 PostgreSQL 部分唯一索引（WHERE status IN 1-4）在数据库层兜底；36h 阶段超时由 @Scheduled 每分钟扫描自动作废，作废与通知同事务，无中间态
- 并发正确性经代码审查驱动修复：投票"插票 → 计数 → 推进"三步用 SELECT FOR UPDATE 行锁串行化，消除两个收官票并发互不可见导致的状态永不推进；草稿编辑启用 @Version 乐观锁（含 MyBatis-Plus 拦截器）；修复 3 个 P1 级问题——schema 脚本漂移（operator_id NOT NULL 与系统动作冲突）、并发收官票卡死、发起人离职后概念永久卡死（离职接口联动作废 + resign_void 留痕）
- 安全体系：JWT + RBAC 四角色，@ClubPermission 注解 + SpEL 切面统一做社团上下文权限校验（controller 与 service 双层）；登录防爆破三层（图形验证码 / Redis 滑动窗口限流 / 失败锁定）；@RepeatSubmit 防重提交；所有敏感操作全量留痕
- 透明留痕双轨设计：concept_trace 动作流水（谁/何时/什么/理由，系统动作标记"系统"）+ concept_vote 结构化投票（轮次/赞成拒绝/必填理由），详情接口一次返回，老师审阅、事后审计、前端时间线共用同一数据源；站内消息覆盖全部作废/通过场景，含业务例外（老师批复超时额外通知老师本人）
- 基于 LangGraph 实现企划起草 Agent：对话式构思 → AI 生成方案 → 人工确认后落表（Human-in-the-loop）；单 ReAct Agent（create_agent 主循环）+ 9 工具集（经验检索 / 在线搜索 / 社团上下文 / 表单读写 / 经验沉淀 / 思考角度归纳 / skill 生成）；统一经验库承载业务知识与发起人思考角度（thinking_pattern）跨会话复用；工具调用身份透传回 Java 业务层校验，AI 仅持有"起草中状态 + 本概念"的受控写权限，动作全量留痕，AI 不可用时主流程零依赖（降级为手动填表）
- 前端 Vue3 + Element Plus + Pinia：概念页投票/批复/时间线弹窗、消息铃铛未读实时刷新、会话重放，全链路浏览器实测通过

## 二、面试展开点（每条对应的可讲细节）

1. **状态机**：为什么用条件 UPDATE 而不是"CAS + updateById 两步"？——updateById 按 NOT_NULL 策略跳过 null 字段，deadline 清不掉；全字段覆盖存在旧快照回写状态的风险。单条条件 SET 更新把"校验 + 流转 + 字段清理"合成一个原子语句。
2. **并发**：为什么投票用 FOR UPDATE（悲观锁）而不是乐观锁？——投票是"读状态→插票→计数→推进"多步读改写，READ COMMITTED 下两个收官票互不可见对方未提交的行，都判定"还差一票"；行锁串行化后第二个事务要么看到推进后的状态被干净拦截，要么正确推进。锁的代价：单概念行、事务毫秒级，可忽略。
3. **乐观锁**：@Version 生效需要"注解 + OptimisticLockerInnerInterceptor 插件"双要件，只加注解静默失效——排查"字段级能力不生效"先查插件链。
4. **脚本漂移**：K8 修复只同步了 init_db.sql，alter 脚本漏改 operator_id NOT NULL——多份建表脚本并存时结构变更必须全部同步；CREATE TABLE IF NOT EXISTS 不会修正已建表的旧约束。
5. **留痕**：为什么投票单独建表不放流水？——投票有结构化字段（轮次/赞成拒绝）需要按状态机逻辑统计（两票齐没齐/有无拒绝票）；流水是追加型审计事实，两者职责不同；撤回时投票物理删除但审计在 trace。
6. **Agent 边界**：为什么审批流程不进 LangGraph？——异步多日等待 + 确定性流转，业务表 status + 定时任务足够；LangGraph 只承载会话型起草。为什么方案生成是工具不是子 Agent？——"要不要补检索/信息够不够"的判断可由对话主循环吸收，每次生成调用是确定性单步；子 Agent 留给有真实内部自主循环的复盘场景。同一判据两种选择。
7. **受控写**：AI 有写权限但被圈死——身份透传（代表发起人）、范围限制（起草中 + 本概念）、全量留痕（trace ai_draft 区分 AI 生成与人采纳）、人确认前置。
