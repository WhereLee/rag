# 面试素材积累

> 本项目开发过程中沉淀的、面试可讲的工程素材。每个素材按「结论 / 背景 / 话术 / 追问」组织。

## 1. 登录统一错误提示：防账号枚举

- **结论**：登录失败统一返回"用户名或密码错误"，不区分账号不存在/密码错误；注册场景保留"用户名已存在"提示。
- **背景**：区分提示等于给攻击者提供账号枚举接口（探测哪些用户名已注册）。注册接口无法避免暴露存在性（注册本来就要查重），但登录接口可以。
- **话术**："登录接口故意不区分错误类型，防止攻击者枚举有效账号；注册场景无法回避查重，所以保留明确提示。"
- **追问**："那怎么平衡用户体验？" → 错误提示统一，但配合 IP 限流 + 连续失败账号锁定（5 次失败锁 15 分钟），防爆破靠限流而非提示细节。

## 2. 并发注册竞态：查重与插入的窗口

- **结论**：先 SELECT 查重再 INSERT 存在竞态窗口（两个并发请求同时通过查重），兜底方案是捕获数据库唯一约束冲突（DuplicateKeyException）→ 返回友好 400，而不是 500。
- **背景**：`kb_user.username` 有 UNIQUE 约束，并发同名注册时第二个 INSERT 撞约束。业务层查重只是"快速失败"，正确性必须靠数据库约束。
- **话术**："查重是性能优化，唯一约束才是正确性保证；我在 Service 层捕获唯一约束冲突转成业务错误，保证并发下不出现 500。"
- **追问**："为什么不用分布式锁？" → 单库场景数据库约束就是最可靠且零额外成本的方案；分布式锁是为跨实例场景准备的，当前单实例不需要。

## 3. 密码策略与 BCrypt 72 字节限制

- **结论**：密码策略 8-32 位，限字母/数字/常见符号（`^[A-Za-z0-9@#$%^&*._\-]{8,32}$`）。上限 32 的依据：BCrypt 只取输入前 72 字节，ASCII 场景下 32 字符 = 32 字节，远低于限制，杜绝静默截断。
- **背景**：若允许 128 字符且不限字符集，中文等多字节字符会触发 BCrypt 静默截断——用户以为设置了 128 位密码，实际只校验前 72 字节，这是隐蔽的安全漏洞。上限 8 位是 OWASP ASVS / 等保 2.0 要求。
- **话术**："密码上限不是拍脑袋定的，取决于哈希算法输入限制。BCrypt 72 字节截断，所以要么限 ASCII 字符集让长度天然安全，要么按字节数校验。"
- **追问**："要不要强制字母+数字组合？" → 可以加，属于产品策略；当前只限字符集（长度+字符集已满足等保基本要求），强制组合会牺牲部分可用性，视产品定位决定。

## 4. 枚举单例可变字段的线程安全陷阱

- **结论**：`AuthRateLimiter.LoginResult` 最初是枚举，`locked(remainSec)` 把剩余秒数写在枚举实例字段上——多线程并发调用会相互覆盖。重构为 record（不可变，无共享可变状态）。
- **背景**：枚举单例在 JVM 中全局唯一，往枚举字段写可变状态 = 所有线程共享同一个可变对象，是典型的并发隐患（也是面试常考的"枚举为什么不能被修改"的延伸）。
- **话术**："状态不该放在枚举里。需要携带动态数据的返回值用 record/POJO，枚举只表达固定语义。"
- **追问**："record 为什么线程安全？" → record 的字段是 final 不可变，构造后无法修改；访问器只读，天然无竞态。

## 5. 参数校验分层：DTO 注解校验 + Service 业务校验（待补充示例，后续完善）

- **结论**：格式校验（非空/正则/长度）放 DTO 层用 `@Valid` 注解，业务校验（唯一性等）放 Service 层，Controller 只做编排。
- **背景**：`spring-boot-starter-validation` + `@RestControllerAdvice` 统一返回 `{error}` 结构；Service 层保留格式校验作为兜底防御（防止绕过 Controller 直调 Service）。
- **话术**："校验分两层：入口层校验'请求合不合法'，服务层校验'业务允不允许'。"

## 6. 文件名清洗的两道防线：防路径穿越的标准做法

- **结论**：文件名入库/重命名前必须清洗，防线一：`Paths.get(name).getFileName()` 只取路径最后一段（`a/b.txt` → `b.txt`，从根上消灭穿越）；防线二：正则替换控制字符与危险字符（`/\:*?"<>|` → `_`）。
- **背景**：路径穿越攻击（`../../etc/passwd`）是文件名类的头号威胁。只做字符替换不够——`a/b.txt` 替换后仍是歧义路径；先取最后一段再做字符级清洗才是完整防线。存储名与服务端生成的 uuid 分离（原始名仅展示）是第三层兜底。
- **话术**："文件名安全我做了三层：取路径最后一段、危险字符替换、展示名与存储名（uuid）分离——存储层永远不信任用户提供的名字。"
- **追问**："重命名时怎么处理？" → 与上传共用同一套清洗逻辑（同一函数），保证两条入口行为一致。

## 7. 文件类型校验：为什么 Content-Type 不可信，要用魔数

- **结论**：上传文件的 Content-Type 是客户端自报的，可任意伪造，只能用于展示；类型安全决策必须基于文件头字节（magic bytes）：PDF=%PDF-（宽容到前 1024 字节）、PNG=89 50 4E 47、JPEG=FF D8 FF、docx/xlsx/pptx 是 zip 容器（PK 头）。无魔数的类型（txt/md）无法校验，放行。
- **背景**：攻击者可把 exe 改名 .pdf 上传（Content-Type 伪造为 application/pdf），解析器/预览器处理时才会暴露风险——所以要在入口拦截。校验点放在"读文件头 → 与扩展名匹配 → 不匹配 400"，读头与写盘共享一次 IO（SequenceInputStream 拼接头+剩余流，避免读两次）。
- **话术**："类型校验分两层认知：展示层信 Content-Type（友好映射），安全层信魔数。有魔数的类型必须匹配，无魔数的放行——这是能力边界，不是偷懒。"
- **追问**："校验在什么时候做？" → 上传入口（Java 网关）做第一道，解析前（Python 侧）可再验一次（纵深防御）。

## 8. 上传可靠性：写 tmp → 插库 → 原子 move 的三段式

- **结论**：文件落盘与数据库记录无法做到单事务原子，工程实践是收敛崩溃窗口：写 {uuid}.tmp → 插库 → 同目录 ATOMIC_MOVE 到正式名（同盘 rename 原子）。正式目录只出现"已插库"的文件；失败回滚（删 tmp + 删记录）；进程崩溃残留由定时清理任务兜底（清超时 tmp + 扫无 DB 记录的文件）。
- **背景**：直接"写正式路径再插库"的窗口是：磁盘有文件、库里没记录（孤儿）。三段式把窗口缩小到"move 与插库之间"的同盘原子操作，几乎不可能失败；剩下的小窗口用清理任务收敛，删除物理失败（Windows 文件锁）也走同一兜底。
- **话术**："文件系统与数据库没有事务，我做的不是消除窗口而是收敛窗口 + 兜底收敛：原子 move 让正式目录永远有据可查，清理任务扫无主文件。"
- **追问**："清理任务会不会误删？" → 只删两级路径（{userId}/{file}）下的无记录文件 + 超 TTL 的 .tmp；DB 记录（status=1）的文件永不碰。

## 9. 秒传与内容去重：file_blob + 引用计数的完整体系

- **结论**：物理文件与用户引用拆表：`file_blob`（sha256 UNIQUE，一份物理文件）+ `user_file`（用户引用，blob_id FK）。上传/秒传都只建引用；删除走引用计数，归零才删物理文件。
- **关键设计**：① hash 由服务端流式计算（DigestInputStream，边写边算，不整读内存）；② 并发同 hash 用 `INSERT ON CONFLICT (file_hash) DO NOTHING` 兜底，冲突方复用已有 blob 并删掉自己的文件（唯一约束是正确性保证）；③ `owner_user_id` 记录首个上传者——物理文件在他目录，共享引用者下载/删除都按 owner 定位（否则删不到/读不到）；④ 悬空 blob（崩溃/回滚残留）由清理任务按"实际引用数"收敛，引用计数漂移自动修正。
- **话术**："秒传不是简单查重，是一套一致性体系：唯一约束防并发双写、owner 字段解决共享文件定位、清理任务把崩溃窗口收敛掉——三层保证 blob 与文件系统最终一致。"
- **追问**："hash 用 sha256 不怕碰撞吗？" → 秒传/去重场景碰撞概率可忽略（非安全场景），且 size 校验是第二道防线；若需更强可对比内容（成本高，当前不必要）。

## 10. 数据库迁移脚本的真正幂等：DO 块条件执行

- **结论**：`CREATE TABLE IF NOT EXISTS` 只防"建表"，不防"补列"（已存在的表不会加新列）；`INSERT ... SELECT` 引用的旧列被删后重跑必失败。真正幂等 = 结构语句用 IF NOT EXISTS + 数据迁移包在 `DO $$ IF EXISTS (信息架构表判断) THEN ... END IF` 里。
- **背景**：阶段 2 迁移脚本第一次重跑就炸（file_blob 已有但缺新列、user_file.stored_name 已被上一次执行删除）。改用信息架构判断后任意次重跑安全。
- **话术**："迁移脚本我按'任意次重跑安全'写的：结构幂等用 IF NOT EXISTS，数据归并包在条件块里，执行过一次后条件自然为假。"
- **追问**："为什么不用版本表？" → 版本表（flyway/liquibase）是团队多环境的标准答案；单库场景条件块更轻，但多环境部署时建议上版本管理。

## 11. 分片上传会话体系：断点续传与并发安全

- **结论**：大文件上传拆成 `init(建会话) → chunk(传分片) → complete(合并+校验)` 三段，会话落库（upload_session + upload_chunk 表），上传一半断网后重新 init 也能通过 status 接口恢复未传分片。
- **设计要点**：
  1. **合并前整体 sha256 复验**：分片可能被篡改/串片，complete 时对合并文件重算 hash，与 init 声明不符直接拒绝（400），不污染 blob 库；
  2. **分片大小上限校验**：每片不能超过声明 chunk_size（防超大分片绕过单文件上限）；
  3. **会话归属校验**：所有分片接口按 `session_id + user_id` 查询，跨用户访问返回 404（不暴露会话存在性）；
  4. **幂等重试**：分片缺失 complete 返回 400 后，补齐分片再 complete 即可成功，不需要重新 init；
  5. **超时收敛**：清理任务按 updated_at 清理超过 TTL 的未完成会话及其临时目录。
- **话术**："分片上传我按四层设计：客户端算 hash 先走秒传（命中零字节）；不命中才分片；每片独立校验；合并时整体复验，保证入库的文件与声明 hash 一致。断点续传靠会话表 + status 接口。"
- **追问**："为什么 complete 还要整体复验？" → 单片校验只能防传输错误，防不了攻击者拿合法分片顺序打乱/替换后声明"完成"——整体 hash 是最后一道关，且只在合并时算一次，成本可接受。

## 12. Range 下载与 Spring 消息转换器的选择机制

- **结论**：HTTP Range（`bytes=start-end`）语义：命中返回 206 + `Content-Range: bytes a-b/total`，越界/非法返回 416。Spring 侧坑在于返回类型决定消息转换器：`ResponseEntity<?>` 泛型擦除为 Object 后，`ResourceRegionHttpMessageConverter` 的类型检查失败，退化为 Jackson 把 ResourceRegion 当 JSON 序列化（500）；返回类型必须写死 `ResponseEntity<Resource>`/`ResourceRegion`。
- **背景**：阶段 3 验收测试抓到该 500；改用自算区间 + 自定义切片资源（只暴露 [start, start+count) 字节的输入流）实现，headers 全部在 Controller 层设置，不依赖转换器内部行为。
- **话术**："下载支持 Range 是流媒体/断点下载的基础。实现上我自算区间并返回切片资源：单 range 取第一个，越界 416；头在 Controller 层显式设置（Content-Range/Content-Disposition/Content-Length），行为完全可控。"
- **追问**："为什么不用 ResourceRegionHttpMessageConverter？" → 它要求返回类型精确匹配且 Spring 6.2 下 206 场景会向已冻结的响应头再写 Content-Range 抛异常；自实现 30 行且行为可测，转换器留给标准场景。

## 13. 测试数据设计的"秒传命中陷阱"

- **结论**：验收脚本里若多个用例复用同一份固定内容（同一 hash），先跑的用例把内容入库后，后续 init/check-hash 会**秒传命中**返回 `{hit:true}` 且**没有 upload_id**——依赖会话 id 的后续用例（非法序号、篡改、超时清理）全部落空或访问空 id。
- **背景**：阶段 3 边界测试的非法序号/超大小/hash 篡改用例全报 404（URL 变成 /upload//chunk），SQL 报"语法错误在输入的末尾"（WHERE id= 后为空）——服务端行为正确，是测试数据撞了秒传。
- **规避**：需要真实会话的用例必须用**与已入库内容不同的文件**（内容/大小任一不同即可）；涉及"内容去重"特性的测试，先想清楚每条用例期望命中还是落空。

## 14. 验收脚本里的 4xx 断言：Invoke-RestMethod 会抛异常中止

- **结论**：`Invoke-RestMethod` 对 4xx/5xx 响应直接抛异常（`$ErrorActionPreference="Stop"` 下脚本立即中止），无法拿到响应体；curl 则对 4xx 不抛异常。因此脚本里"期望 4xx 且要断言错误信息"的请求必须用 curl 拿状态码 + body（写临时文件再读），或把请求包进 try/catch。
- **背景**：阶段 3 边界测试的"分片缺失 complete 拒绝"用例直接抛异常中断脚本（服务端正确返回 400，是断言方式问题）。
- **规避**：定义 `PostJsonCode`（curl 输出到临时文件，`-w "%{http_code}"` 拿状态码，.NET `ReadAllText` 按 UTF-8 读回再解析 JSON）统一处理"期望 4xx"的请求；期望 2xx 的请求继续用 Invoke-RestMethod。

## 15. 磁盘空间监控：双阈值设计（比例 + 绝对量）

- **结论**：上传前用 `Files.getFileStore(root).getUsableSpace()` 检查磁盘剩余空间，**双阈值取或**：剩余比例 <5% 或绝对剩余 <1GB → 拒绝上传（400"磁盘空间不足"）。双阈值的原因：纯比例在大磁盘上阈值过大（2TB 的 5% = 100GB），纯绝对值在小磁盘上过松（32GB 盘剩 1GB 比例只剩 3%）；两个阈值互补覆盖。
- **检查点**：整传、分片 init（声明大小）、分片 complete（合并前再查一次，分片传输期间磁盘可能已变化）。
- **配套**：定时任务每小时检查一次，剩余比例 <10% 时 WARN（提前暴露，不阻断）。
- **话术**："磁盘监控我按两个阈值做：剩余比例防'比例过低'，绝对量防'大磁盘比例失真'；上传/init/complete 三处检查，complete 前会再查一次——分片传完合并前磁盘可能已经变了。"
- **追问**："磁盘检查失败怎么办？" → 检查本身 IOException 时记录 WARN 放行（不因监控自身故障阻断业务），但拒绝分支是明确的 400。

## 16. 安全配置 fail-fast：无默认值 + 启动即拒绝

- **结论**：敏感配置（JWT secret、DB 密码、内部 API key）在 yml 中**不留默认值**（`${VAR:}` 空），启动时校验缺失/空白直接抛异常退出。对比"留默认值 + prod 环境才拒绝"的方案：后者部署时只要忘了切 profile 就静默用默认值，fail-fast 让"配置不全=不可启动"成为硬约束。
- **实现**：校验逻辑抽成静态纯函数（输入三个值返回缺失清单），单测 5 个用例直接覆盖；启动脚本从 .env 注入环境变量（Spring Boot 不读 .env），缺失时提前给清晰提示。
- **话术**："安全配置我按 fail-fast 设计：没有默认值，缺失直接启动失败并列出缺哪些变量。校验是纯函数，单测覆盖。本地开发用启动脚本从 .env 注入。"
- **追问**："为什么不留本地开发默认值？" → 默认值=可猜测值=攻击面，且本地和生产的差异越大越容易在部署时踩坑；统一'必须显式配置'，用 .env + 启动脚本解决本地便利性。

## 17. Spring 嵌套占位符：同一配置两个变量名（兼容演进）

- **结论**：`${GATEWAY_INTERNAL_API_KEY:${INTERNAL_API_KEY:}}` —— 优先读新变量名，缺失回退旧变量名。用于 Java 网关与 Python 服务的内部鉴权共用同一把钥匙（Python 侧 .env 里变量名是 INTERNAL_API_KEY，网关兼容读取），两侧天然一致，不会出现"配了但名字不同"的静默失效。
- **话术**："内部 key 两个服务共用，但历史变量名不同。我用 Spring 嵌套占位符做回退：新名字优先、旧名字兜底，两侧只需维护一个变量。"
- **注意**：嵌套占位符只解决"读取"，真正的一致性是部署时只配一个变量名（选 GATEWAY_INTERNAL_API_KEY 作为标准名）。

## 18. 上传白名单与解析域一致性："格式准入"策略

- **结论**：RAG 项目里"允许上传"与"能解析"必须一致——先确定解析域支持的文件格式白名单（txt/md/pdf/docx/xlsx/pptx/png/jpg/webp），上传域按同一白名单拒绝制拦截（不支持格式直接 400，不采用"存了但入库时跳过"的松弛方案）。理由：用户上传一个永远无法问答的文件是负资产，早拒优于晚拒。
- **实现**：白名单配置化（`gateway.upload.allowed-extensions`，可调）；两层校验——**扩展名白名单粗筛（400"不支持的文件类型"）→ MagicBytes 防伪装（类型必须与扩展名匹配）**；xlsx/pptx 与 docx 同为 zip 容器（PK 头），复用同一魔数校验分支；前端 accept 属性 + before-upload 同步拦截，体验一致。
- **话术**："格式准入我按'上传即准入'设计：上传白名单 = 解析能力边界，解析不了的格式直接不让上传。校验分两层：扩展名白名单先拦，魔数校验防伪装——xlsx/pptx 复用 zip 容器判断。"
- **追问**："为什么不在入库时再判断？" → 用户上传成功的文件就期望能问答，入库时跳过会产生"存了但没用"的隐性垃圾；且拒绝制让上传域的约束与解析域能力天然同步，后续扩展格式只需改一处配置。

## 19. 解析触发链："数据库任务表 + 轮询消费"替代消息队列

- **结论**：异步解析任务的触发通道，不引入 MQ，直接用 PG 任务表（parse_tasks）+ SELECT ... FOR UPDATE SKIP LOCKED 轮询消费——PostgreSQL-as-queue 模式。上传完成写 pending，Python worker 每 3 秒拉取执行，状态机 pending→parsing→success/partial/failed。
- **背景**：两条候选——Java 主动 HTTP 通知（120s 长连接 + 强耦合 + 网关挂则链路断）vs 任务表轮询（解耦、失败重试天然、worker 独立进程）。选轮询，代价是 ≤3s 延迟与空轮询成本（一天 28800 次索引查询 < 6 秒 CPU，可忽略）。
- **话术**："解析是重活（单文件最长 120s），不能让网关同步等待。我用了数据库即队列：Java 只写 pending，Python worker 独立进程轮询，SKIP LOCKED 保证多 worker 不抢同一任务，任务状态在库里天然持久化——没有 MQ 的丢消息问题。"
- **追问1**：轮询效率/空转？ → 索引查询微秒级，空轮询开销可忽略；演进可加 PG LISTEN/NOTIFY 唤醒，轮询兜底。
- **追问2**：worker 崩溃怎么办？ → parsing 状态停留超 5 分钟回收为 pending（崩溃恢复）；pending 任务永不丢失；进程级挂靠 systemd 重启。
- **追问3**：为什么不用 Redis Stream/RabbitMQ？ → 当前负载 PG 任务表足够且零新增组件；任务量增长时换 Redis Stream，parse_tasks 保留为状态记录层，迁移可控。

## 20. 秒传去重与物理文件归属：file_blob 是唯一事实来源

- **结论**：秒传（内容 hash 命中）只建 user_file 引用、不复制物理文件，物理文件存于**首个上传者目录** data/files/{owner_user_id}/——任何下游读物理文件的路径必须以 file_blob.owner_user_id 为准，而非当前 user_file 的 user_id。
- **背景**：worker 解析秒传文件时用 user_file.user_id 拼路径，全部"物理文件缺失"；改用 blob.owner_user_id 后正常。这是去重架构的自然推论：引用可以多，物理实体只有一个归属。
- **话术**："我们的去重是把物理文件（file_blob）和用户引用（user_file）拆成两张表，hash 唯一 + 引用计数。下游系统（解析、预览）拼文件路径必须从 blob 查 owner，因为秒传用户的 user_id 不等于文件实际所在目录。"
- **追问**：删除时引用计数怎么维护？ → ref_count 减一，归零才删物理文件；删除失败告警，清理任务兜底重试。

## 21. RRF 融合 + rerank 的实证收益：黄金集 Recall@5 从单路 76%/88% 提到 100%

- **结论**：混合检索融合不是锦上添花：25 条黄金集四组对比——纯向量 76%、纯 BM25 88%、RRF 融合 96%、RRF+rerank 100%。单路各有盲区（专有名词 BM25 强、语义近义向量强），融合是必要项，rerank 补齐最后 4 个百分点。
- **背景**：黄金集刻意覆盖两类弱点（编号/人名/技术名精确匹配 vs 同义改写），单路无法兼顾；RRF 用排名倒数 1/(k+rank) 融合（k=60），绕开向量分 [-1,1] 与 BM25 分无界的尺度不可比问题。
- **话术**：“我们建了 25 条黄金测试集覆盖专有名词与语义近义两类弱点，四组方案对比：向量 76%、BM25 88%、RRF 96%、加 rerank 后 100%。结论是单路都有盲区，融合是必要项；rerank 用 logits 绝对分，还能顺便做低分拒答。”
- **追问1**：RRF 的 k 为什么取 60？ → Cormack 2009 论文经验值；k 越大对低排名越宽容，60 在多数场景均衡，也可网格搜索标定。
- **追问2**：为什么不用加权融合？ → 向量分与 BM25 分数尺度不同且 BM25 无界，加权系数难标定、易过拟合；RRF 只用排名天然尺度无关，且实现简单。

## 22. rerank 分数语义：cross-encoder logits 绝对分才能设拒答阈值，softmax 相对分不可比

- **结论**：bge-reranker-v2-m3 输出 logits（跨查询可比的绝对分），拒答阈值（-5.0，规范 §4.2）直接作用于 logits；softmax 归一化是相对概率，只在同一查询内可比，不能设跨查询阈值。
- **背景**：计划初值“归一化分数 < 0.2 拒答”在实施时发现模型原生输出是 logits；实测正样本 top1 分数均 > 0，与 -5 有充分间隔，-5 作为剔除线不误杀，拒答路径全部正确触发。
- **话术**：“拒答阈值必须建立在分数语义上：reranker 的 logits 是绝对分跨查询可比，softmax 只是相对概率。我们直接用规范 -5 的剔除线，黄金集实测正样本与阈值间隔充分，无样本被误杀。”
- **追问**：低分但未达阈值怎么办？ → 标记 low_confidence 随 meta 事件下发前端，不拒答但提示置信度低（C5 标定结论：低置信线 0.0 偏保守但行为安全）。

## 23. SSE 透传网关：事件原样字节搬运，避免 SseEmitter 二次编码

- **结论**：Java 网关转发 Python SSE 事件时用 `emitter.send(byte[])` 原样转发 UTF-8 字节，不用 String 中转——否则 SseEmitter 按平台默认编码二次编码，中文变双重编码乱码（历史真实坑）。
- **背景**：链路 Python(FastAPI 8091) → Java 网关(8082) → 前端 fetch ReadableStream；网关只做 JWT 鉴权 + X-User-Id 注入 + 字节搬运，不解析事件内容；上游不可达时补发 error 事件保证前端有提示。
- **话术**：“流式透传的坑是编码：Python 输出 UTF-8 字节流，网关用 String 中转会被默认编码再编一次导致中文乱码。我们 BufferedReader 读行、byte[] 原样送 SseEmitter，前端 TextDecoder 流式解码，链路无损。”
- **追问**：为什么不用 WebFlux/WebClient 转发？ → 当前 MVC + SseEmitter + 线程池已满足（单用户流式）；并发扩大时换响应式是演进项，接口契约（SSE）不变。

## 24. 前端验收分层：接口测试全绿 ≠ 页面可用，真实浏览器实测补 DOM 层盲区

- **结论**：链路验收必须分层——接口层（curl/脚本断言 JSON）只能证明后端通了；SSE 前缀格式、流式渲染、状态切换等 DOM 层兼容问题只有真实浏览器能测到。本项目正是被 MCP browser-use 实测抓到：Spring SseEmitter 输出 `data:` 无空格，前端 startsWith('data: ') 静默丢全部事件，接口测试全绿但页面空白。
- **背景**：验收脚本（PS/curl）只断言响应 JSON 内容（`"type": "meta"` 等），不检查事件外层 `data:` 前缀；浏览器实测一次全流程（注册→上传→解析→提问→流式渲染）立刻暴露。
- **话术**：“我们的验收分两层：接口层用脚本断言后端语义（状态码、JSON 内容、SSE 事件序列），UI 层用浏览器自动化走真实用户路径——上传、等待解析、提问、看流式渲染和引用展示。这套组合抓过真实 bug：SSE 事件格式在网关层被重包，前端解析不兼容，接口测试全绿但页面空白。”
- **追问**：浏览器自动化测什么？ → 真实交互路径 + DOM 渲染断言 + 控制台错误扫描（list_console_messages）+ 网络请求状态；截图存档可追溯。

## 25. 两级问答存档（L1 精确直返 + L2 语义参考）：减少 LLM 调用的工程形态

- **结论**：对用户重复/近义提问做两级命中：**L1 精确命中**（查询归一化后 MD5 查 qa_cache，命中直接返回存档答案，零检索零 LLM 调用）+ **L2 语义命中**（精确未命中时用 query embedding 余弦检索同用户存档，sim≥0.9 命中则把历史 Q&A 作为 few-shot 参考段注入 prompt，提升回答一致性）。拒答不存档（坏答案污染后续命中）；答案质量变化（文件重解析/软删）通过 invalidated 标记失效，重问后自动重建。
- **背景**：RAG 问答中"同样问题问两次"很常见（重复确认、近义表达）。实测 bge-base 下"服务器最低配置是什么"与"服务器需要什么硬件"相似度仅 0.888——**0.9 阈值会漏掉这种"人觉得近义、模型觉得差一点"的词对**，阈值标定必须用真实命中数据，不能拍脑袋。
- **话术**："我按两级做问答存档：精确命中零成本直返（省一次完整检索+LLM 调用），语义命中把历史答案作为参考注入（省不了调用但提高一致性）。拒答不存档、文件变更失效、命中计数——一致性靠失效标记+重建，不靠定时清理。"
- **追问**："缓存命中直接返回，会不会答非所问？" → L1 是归一化后的完全一致（语义等价），L2 有 0.9 相似度门槛且注入时明确标注'历史回答参考，可能不完全相关，以资料为准'，LLM 会结合当前检索资料裁决。

## 26. 查询归一化三段式：全角半角 + 空白压缩 + 尾标点去除

- **结论**：精确命中前把用户查询归一化到"语义等价的最小形态"：① 全角标点/空格转半角（`str.maketrans` 字符表，含全角逗号句号问号括号引号）；② 连续空白压缩为单空格 + strip（含全角空格 U+3000）；③ **尾部标点去除**（`[。！？?!.]+$`）——"你吃了吗？"与"你吃了吗"语义等价，但 MD5 不同，不去尾标会导致精确命中率大幅下降。
- **背景**：P3 验收实测：用户输入"生产服务器最低配置是什么？　"（全角问号+全角空格）与标准问法 hash 不同 → L1 未命中。前三步处理后仍残留尾随问号 → 补第三步才全通过。归一化本质是"定义语义等价类的规范形"。
- **话术**："精确命中的难点不在'命中'而在'归一化'——我把等价类定义成三段式：字符级（全角→半角）、空白级（压缩）、语气级（尾标点）。句中标点不动，只去尾部，保证不误伤语义。"
- **追问**："为什么不用 L2 语义兜底？" → L1 的成本是零（一次 MD5 查询），L2 是完整 embedding 检索；归一化把'语义相同但字面不同'的场景尽量归入零成本路径，L2 只处理'语义近似'。

## 27. 缓存失效的一致性链：重解析/软删 → invalidated → 重问重建

- **结论**：问答存档的正确性依赖完整失效链：① 文件重新入库（ingest 成功）→ 关联存档置 invalidated（块变了旧答案不可信）；② 文件软删（Java 直连同库 SQL，`WHERE user_id=? AND ? = ANY(file_ids)`）→ 失效；③ 失效后再次问答走全链路，新答案经 `ON CONFLICT (user_id, query_hash) DO UPDATE ... invalidated=FALSE` 自动重建。失效=保守置灰，重建=幂等覆盖，不需要定时清理任务。
- **背景**：P3 实现时发现"删除文件后 L1 仍直返旧答案"是真实一致性 bug（计划中已预见，但最初未落地）——旧答案引用已删文件且 citations 为空，用户会被误导。Java 与 Python 同库，删除事务里直接补一条 UPDATE 即闭环（避免跨服务调用）。
- **话术**："缓存失效我按'事件驱动 + 幂等重建'设计：任何让旧答案不可信的动作（重解析、软删）都置 invalidated；下次同问自然走全链路并重建。没有定时清理——失效标记和 ON CONFLICT 覆盖让状态机自洽。"
- **追问**："恢复回收站文件后缓存还在吗？" → invalidated 保持（保守），恢复后用户再问同问题会重新检索、重新写入（UNIQUE 冲突走 DO UPDATE 重置），答案基于恢复后的文件，行为正确。

## 28. BM25 强命中保护：混合检索的拒答信号融合

- **结论**：rerank 低分剔除（规范 §4.2，logits < -5 判不相关）会把"BM25 明确关键词命中"的块误杀——实测 bge-reranker 对"缓存用什么技术" vs "缓存：Redis 7"这类短口语查询+强词项命中组合打分 -6.17（低于 -5），而 BM25 给 3.82 分。修复：剔除时检查 BM25 top5 正分命中集，命中则降级保留（reranked=False），由 qa 层按低置信处理而非拒答。拒答判定从"单一信号"变成"混合信号"：rerank 低分 + BM25 无命中 → 拒答；rerank 低分但 BM25 命中 → 低置信作答。
- **背景**：混合检索（向量+BM25+RRF+rerank）的每一路信号都有盲区——向量对语义近义强、BM25 对字面词项强、rerank 校准因查询类型波动。让"最后一刀"（rerank 阈值）完全否决"前面命中"（BM25 强命中）等于丢弃混合信号；保留+降级标记是"两路信号取并集、置信度取交集"的折中。
- **话术**："低分拒答不能只信 rerank 一路信号。BM25 词项命中是强相关证据，rerank 打分对部分短查询校准偏低。我做了一层保护：BM25 top5 正分命中的块不被剔除线误杀，降级为低置信返回；两路都弱的才拒答——召回取并集，拒答取交集。"
- **追问**："会不会把无关块也放进来？" → 保护只作用于 BM25 有正分（词项重叠）的块，且 qa 层仍标记 low_confidence 提示；完全无关查询 BM25 无命中，依旧全剔空走拒答（实测"火星殖民"查询保持拒答）。阈值（top5）可随真实命中数据标定。

## 29. 跨用户问答复用：秒传 blob 与缓存体系联动 + 内容边界安全设计

- **结论**：不同用户上传相同内容文件（秒传去重 → 同 blob）后，B 问 A 问过的相同/近似问题可复用 A 的存档回答，减少重复 LLM 调用。关键设计：① **内容边界安全**——复用条件为"缓存引用的每个文件，B 都持有同 blob 文件"（NOT EXISTS 检查），防止经缓存泄露对方私有文件；② 复用后写入 B 自己的缓存，file_ids 映射为 B 的文件（失效维度归本人），记录 cache_shared_from 来源 id 供审计；③ 前端对跨用户复用**不显示"来自历史回答"标签**（中性展示，不暴露"来自别人"）；④ 语义近似问题走 L2 跨用户参考注入（同样受内容边界约束）。
- **背景**：秒传体系（file_blob 按内容 hash 去重）天然给出了"内容相同"的判定维度——两用户持有同 blob 文件 = 回答所依据的内容完全一致。安全边界用 SQL 子查询实现：`NOT EXISTS (SELECT 1 FROM user_file uf1 WHERE uf1.id = ANY(qc.file_ids) AND uf1.blob_id NOT IN (B 的 blob 集合))`。
- **话术**："跨用户缓存复用我按内容边界做：秒传保证 blob 相同=内容相同，所以只有'回答完全基于双方共有内容'的缓存才允许复用，杜绝经缓存泄露对方私有文件；复用后写进本人缓存、失效维度映射到本人文件、来源留痕，前端不显示来源标签。"
- **追问**："B 复用了 A 的回答，A 的文件后来改了怎么办？" → A 重解析 → A 的缓存按 file_ids 失效（invalidated）；B 的缓存引用 B 自己的文件 id，B 的文件没变则 B 的缓存仍有效——两份缓存生命周期独立，互不干扰。

## 30. 输入输出治理：分层校验上限 + 推理模型的 token 预算必须同时覆盖思考与正文

- **结论**：问答系统输入输出限制不能只做单层：① 问题长度 500 字上限分层实施——Java 网关（校验失败立即 400，不占 Python 资源）+ Python 业务层（同规则兜底）+ 前端 maxlength+show-word-limit（输入即拦截，体验友好）；② 输出预算 max_tokens=8192 必须**同时覆盖 reasoning 与 content**——推理模型的 reasoning tokens 计入 completion 预算，若预算只够思考、正文被挤空（实测 thinking=false 场景正文仅 1 字），回答不可用。
- **背景**：思考开关功能上线后检查输入输出治理缺口：query 原本仅非空校验（任意长度可打爆历史注入/LLM 输入）；max_tokens 从 4096 提到 8192 是因为 4096 时"思考 233 字 + 正文 48 字"的实测样本显示 reasoning 占比超 70%，长思考时正文会被挤到极短。分层校验的价值：网关层拦截成本最低（不给下游留垃圾请求），前端拦截体验最好（用户实时看到计数），业务层是最后防线。
- **话术**："输入限制我分层做：网关挡长度、业务层兜底、前端给反馈。输出侧的关键认知是推理模型的预算要同时算上思考——reasoning 计入 completion token，预算不足时正文被挤空，所以上限要按'思考+正文'一起估，而不是按正文长度估。"
- **追问**："500 字上限怎么定的？" → 企业知识库问答场景问题普遍 <100 字，500 字足够覆盖极端长问（含粘贴错误内容），同时限制历史注入与 LLM 输入的膨胀风险；阈值可按业务日志分布再标定。

## 31. 验收脚本测试查询必须先查缓存：L1 命中直返让"全链路"断言失真

- **结论**：任何验证"走全链路/有思考/有检索"类行为的验收脚本，测试查询必须**先查 qa_cache 确认该用户未问过**（含归一化等价问题、跨会话/跨用户复用产生的条目）；否则 L1 精确命中直接返回（meta.cached=true，无 thinking 事件、无检索），断言误报成"功能回归"。另注意：服务假死期间处理完成的请求已写库但 SSE 发送失败（客户端见 error），重启后同问会直接命中缓存——现象相同、根因不同。
- **背景**：三次踩同一坑（P4 验收 Q1 撞 S1 缓存、思考开关验证撞缓存、输入限制验证撞缓存），每次都是脚本选"自然合理"的问题而未检查缓存现状；排查时先怀疑功能回归，实际是测试设计问题。
- **话术**："缓存体系上线后验收脚本多了一个前置步骤：先查测试用户的 qa_cache 有哪些问题，选一个不存在的。否则你以为在测全链路，实际测的是缓存直返——断言无 thinking 失败不是功能 bug，是测试撞了缓存。"
- **追问**："怎么避免缓存污染？" → 验收数据用随机标记（uuid 后缀）构造内容，问题也带标记；仍要查缓存是因为同内容文件的秒传会让历史运行的缓存继续有效（同 blob 跨用户复用）。

## 32. 反馈闭环全链路：用户评价 → 异步归因 → bad case 升级回归集（HITL）

- **结论**：问答系统把"用户不满"变成"可执行的改进证据"需要完整链路：① 前端回答下方点赞/点踩（点踩可附原因）；② done 事件携带 qa_log_id（**缓存命中路径也要落 qa_log**，否则缓存回答无法反馈）；③ 点踩时生成 bad_case（快照：问题/回答/检索块），**LLM 归因异步化**（retrieval vs generation 判定耗时 20-60s，同步调用会拖垮提交响应——实测网关 30s 超时截断，数据已入库但前端收 502）；④ bad_case 经人工确认（HITL）升级为回归集题目，自动归因结论（retrieval→改进检索/generation→改进 prompt）指导下一步优化。
- **背景**：反馈 API 与归因器（attributor）后端早已存在（Phase 4 计划内），但前端从未接入、done 事件不带 qa_log_id、缓存命中不落 qa_log——闭环是断的。浏览器验证连环暴露：前端兜底 done 事件覆盖真实 qa_log_id（按钮永不显示）→ 网关 30s 超时截断同步归因（502 但数据已入库）→ 拒答文案污染 qa_cache（BM25 降级路径 rejected=False 但 LLM 输出"资料中未找到"）。
- **话术**："反馈闭环我按'采集→归因→升级'三段做：任何回答（含缓存命中）都能评价；点踩立刻生成带快照的 bad case，LLM 归因放后台线程（同步会拖垮提交）；人工确认后才升级为回归集题目——保证坏例子不靠运气复现，而是变成每次回归必跑的用例。"
- **追问**："归因错误怎么办？" → 归因只写 bad_case.attribution（LLM 结论 + 规则兜底：无检索结果→retrieval），人工确认（confirm）环节可推翻并补充参考答案；确认后才影响回归集，归因本身不直接改系统行为。"缓存命中怎么反馈？" → 缓存路径同样落 qa_log（cache_hit=TRUE），qa_log_id 随 done 事件下发，反馈链路对 L1 直返回答同样生效。

## 33. 停止生成：AbortController + 断开传播链 + 中断落库语义（回答不完整不写缓存）

- **结论**：流式问答的"停止生成"是三层协作：① 前端 AbortController 中止 fetch（每次发送新建，中止后 signal 不可复用）；② Java 网关 emitter.send 异常 → finally 断开到 Python 的上游连接（断开自然传播，无需额外协议）；③ Python 生成器收到 GeneratorExit → finally 兜底：**已生成部分仍落 qa_log**（审计/反馈可用）但**不写 qa_cache**（回答不完整，写了会污染 L1 命中）。三层的核心是"中断语义"：用户停止 ≠ 什么都没发生，部分回答是有效审计数据；但不完整回答绝不能进入存档。
- **背景**：实现时的关键坑是**本地回环无法端到端复现"生成中中断"**——TCP 缓冲吸收 + 快 LLM 使断开检测晚于生成完成，误以为兜底失效排查 4 轮。最后拆两层验证：临时慢速 SSE 服务确认 uvicorn 断开→GeneratorExit→finally 执行（框架行为），集成断言改为"缓存不得含截断部分回答"（安全属性）。生产真实场景（思考 1-4 分钟 + 公网延迟）中断必然发生在生成中。
- **话术**："停止生成我按'断开传播链'设计：前端 abort 断 TCP，网关的 emitter 写失败自动断开上游，Python 生成器被 GeneratorExit 中断后 finally 兜底——已生成部分落审计日志（用户停止也是有效行为记录），但不写问答缓存（半截回答会污染 L1 命中）。三层各司其职，不需要额外的停止协议。"
- **追问**："中断的回答会不会污染历史会话？" → qa_log 记录部分回答（session 历史里可见，标注 cache_hit=FALSE），前端显示"已停止生成（回答不完整，未存入问答存档）"；qa_cache 不写，同问再触发全链路。"为什么本地测不出中断？" → 回环 + 短响应的 TCP 缓冲使断开检测晚于生成完成，属测试方法限制；框架行为单独验证（慢速 SSE 服务 + 断开 → finally 执行）。

## 34. 问答并发能力实测分层：embedding 最轻、rerank 信号量串行、事件循环阻塞才是致命项

- **结论**："多人同时问会不会一个一个处理"实测答案是三层的——① **embedding 并发有效**（ORT session 线程安全：10 并发同时算 42ms 全完成 vs 串行 174ms，每请求仅从 17ms 涨到 31ms）；② **rerank 硬串行**（全局 Semaphore(1)：并发 6 时每任务 p50 从 0.75s 放大到 2.9s，真实 top50 配置下单次 3.4s 排队更狠）；③ **FastAPI 假并发最致命**——`async def` 端点里直接跑同步阻塞调用（retrieve 含 rerank 3.4s、LLM 同步 httpx 流式 5-15s），一个请求独占事件循环，**所有并发请求全程排队**（第 N 人等待 ≈ (N-1)×(前戏+生成 10-20s)），比模型层串行严重一个数量级。
- **背景**：用户问"多人同时问 embedding 只能一个一个处理？"，实测推翻了直觉——embedding（10-60ms）是链路最轻的一环；rerank 用 bge-reranker-v2-m3（569MB 多语言大模型）+ top50 候选，单次 3.4s 占前戏 97%，且信号量限并发 1；而代码审查发现事件循环阻塞是比前两者更隐蔽的真凶（async def + 同步调用不 await 就没有并发）。修复：准备阶段整体 `asyncio.to_thread`（_prepare_ask 提取）+ LLM 同步流式放 daemon 线程 + queue.Queue 桥接 + `asyncio.to_thread(q.get)` 消费 + persist（含 maybe_extract 可能调 LLM）同步异步化。验证：pytest 135 全过；桥接模拟 2 并发总耗时 2.0s（串行应 4.0s）。
- **话术**："并发问题我实测分层：embedding 10 并发 42ms 全算完（ORT 线程安全），rerank 有信号量串行（并发 6 排队放大 3.8 倍），但最隐蔽的是 FastAPI 假并发——async def 端点里同步阻塞的检索和 LLM 流式独占事件循环，一个请求卡全站。修复是把同步密集段丢线程池、同步流式用队列桥接线程，事件循环只做编排。"
- **追问1**："为什么不用 httpx 异步化 LLM 客户端？" → 同步流式已稳定服务 agent/评估等多处调用方；线程桥接零侵入、行为不变，异步化留作演进（客户端单一职责，不因一处并发改造动全局）。
- **追问2**："线程池会不会耗尽？" → 默认 executor min(32, cpu+4)，问答前戏与流式消费共用；高并发时排队受网关限流兜底，且 rerank 超时降级 RRF 不阻塞链路。
- **追问3**："rerank 3.4s 怎么治？" → 三个实测选项：候选 50→20（1.4s）、换 base 小模型（top50 1.9s）、base+top20（0.76s）；质量取舍须黄金集验证（E2 证明 rerank 是质量最大单点，不能无脑砍）。

## 35. rerank 配置对比实验：候选数 50→20 + 换 base 模型，质量零损失、延迟降 5.8 倍

- **结论**：黄金集 32 题（含证据关键词，新链路 retriever）三组同口径实测——v2-m3@top50（生产现状）MRR 0.8906 / recall 0.9062 / 单题 17.8s；v2-m3@top20 与 base@top20 的 MRR 和 recall **完全一致**（0.8906/0.9062，context_precision 仅差 0.008），单题耗时降到 5.3s / 3.1s。即：候选数 50→20 和换 base 小模型在黄金集上检索质量零损失，延迟降 3.3~5.8 倍；base 模型（110MB vs 569MB）额外省 ~460MB 内存——对 4G 部署预算是从"几乎打满"到"有腾挪空间"的质变。
- **背景**："rerank 是质量最大单点（E2：关闭后 MRR 0.3998）"意味着不能无脑砍，但"砍多少"必须用数据说话。实验控制：评估走新链路 `retriever.retrieve`（evaluator 仍走旧链路 kb_chunk，不能直接复用）；reranker 全局单例导致组间必须串行切模型；**rerank 相关实验并发必须为 1**（Semaphore(1) + RERANK_TIMEOUT=15s 下并发 4 全部排队降级 RRF，出过 MRR=0 的假数据）；评估用户必须是 corpus 文档持有者（多租户隔离下用户文件集不同）。
- **话术**："我做了 rerank 的配置对比实验：候选 50 砍到 20、大模型换 base，黄金集 MRR 完全一致但延迟降了 5.8 倍、内存省 460MB。E2 告诉我 rerank 不能关，实验告诉我它可以更小——两轮数据合起来才是完整的调优决策：质量单点保留，但配到刚好。"
- **追问1**："换小模型会不会在更大语料上退化？" → 黄金集 32 题覆盖 8 个 corpus 文档各类型问题，当前语料下无退化；语料扩展后以回归集复测（黄金集已入库 eval_question，对比实验脚本可重复）。
- **追问2**："为什么实验和线上耗时差这么多？" → 基准脚本用 30 字短 query + 短候选，黄金集问题更长、候选块更长（512 token 上限更易触满），且串行无批处理——相对关系（5.8 倍）才是结论。
