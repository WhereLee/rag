# 双项目集成方案：社团经验复用闭环（club × rag）

> 版本：v1.0 · 2026-08-31
> 定位：决策完整的设计方案——实施者按本方案执行不再需要做架构决策；分期明确，只做阶段 1。
> 适用范围：rag（`WhereLee/rag`，知识引擎）+ club（`WhereLee/club-agent`，业务系统）两个独立仓库的集成。

---

## 0. 一页纸叙事（为什么做这件事）

两个项目不是"一个文档问答 + 一个社团管理"，而是一个故事：

> 社团管理 Agent 覆盖活动全生命周期（概念 → 审批 → 执行 → 留痕 → 复盘）。活动结束后，经验会沉淀成知识资产——复盘报告、管理层上传的参考资料文件。但这些资产是"死"的，新一届管理层换届后经验随人走。我把自己做的文档问答引擎（rag）接进业务系统：**文件入知识库 → 新活动起草时 Agent 自动检索历史经验 → 反哺策划**。管理层换了一届又一届，经验留在系统里。

**面试价值**：展示的不只是"做了两个系统"，而是"识别了两个系统之间的数据流并把它落地"——业务建模（活动生命周期）+ 工程深度（两套系统各自细节）+ 系统思考（闭环设计）。**叙事主角是闭环，LangGraph 是其中"AI 编排"的技术细节。**

---

## 1. 目标与边界

### 1.1 目标

打通一条**最小完整闭环**（阶段 1，唯一必做）：

```
管理层上传活动文件 → rag 入库（解析/切块/向量化） → 概念 Agent 起草时检索 → 草案引用历史经验
```

### 1.2 边界（明确不做，后置）

| 不做 | 原因 | 后置时机 |
|---|---|---|
| rag 生成式问答接入概念 Agent（应答器模式） | 生成/编排必须留在概念 Agent（LangGraph 体现点）；rag 只做检索器 | 无（永久不做） |
| experience_entry 结构化经验进 rag 向量库 | 短文本 SQL 检索足够，塞向量库稀释检索质量 | 无（永久不做，双源分离） |
| 复盘报告文本入库 | 闭环主线是"文件 → 检索"；复盘入检索是增量 | 阶段 2 |
| 管理层跨届问答（人问入口） | 需要独立入口/权限/UI，分散主线 | 阶段 3 |
| 成员/访客检索入口 | 权限分级设计未定 | 阶段 3 |

## 2. 现状盘点（已核实的事实）

### 2.1 rag 侧

- **入库管线**：上传/解析链路由 Java 网关文件域控制（分片上传 → `user_file` → `parse_tasks` 异步 worker → `rag_chunk`）；Python 侧**没有**直接入库入口（v2 已删）
- **检索**：`retrieval/retriever.py` 混合检索（向量 top50 + BM25 top50 → RRF → rerank），隔离靠 `rag_chunk JOIN user_file WHERE user_id=? AND status=1`；`dir_id` 可选目录限定；**无纯检索对外接口**（只有生成式 `/api/qa/ask`）
- **表结构**：`user_file`（user_id 外键 → kb_user、dir_id、status 软删）；`rag_chunk`（file_id 外键、embedding vector(768)、无独立隔离列——靠 JOIN user_file）
- **内部鉴权**：Python 直连需 `X-User-Id` + `X-Internal-Key`（/ `X-Gateway-Sign`），仅限内部脚本/运维

### 2.2 club 侧

- **经验现状**：`experience_entry`（结构化条目，SQL 关键词检索 `selectForAgent`）；`activity_summary.report`（复盘文本，未检索）；概念 Agent（`create_agent` + `CONCEPT_TOOLS`，工具集按会话类型隔离）
- **检索工具**：`search_experience`（Python 工具 → Java `/ai/experience` → SQL 检索 + 数据水位 + 低水位联网兜底）——**编排模式（水位判断/改写重查）已存在，直接复用**
- **文件能力**：`StorageService`（本地/COS 双实现 + delete）；`PythonClientFactory`（Java 调 Python 的内部密钥头模式，可复制为调 rag 的客户端）
- **架构原则**：权限在 Java，Python 无状态信使（AI 无写权限）

## 3. 总体架构

### 3.1 数据流

```
[club Java] 管理层上传活动文件（活动详情页）
   → activity_file_lib 表 + StorageService 存储
   → 入库触发：club Java → rag 入库 API（X-Internal-Key + org 标识）
   → rag：parse_tasks 异步解析 → rag_chunk（org 空间隔离）
   → [club Python 概念 Agent] 起草时调检索工具
   → Java /ai/knowledge（ClubPermission 校验社团归属）
   → club Java → rag 检索 API（纯检索，返回 chunks）
   → 工具文本【经验命中】【文件命中】→ 概念 Agent 整合进草案
```

### 3.2 核心决策（D1-D8）

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D1 | rag 的角色 | **检索器**（返回 chunks，不做生成） | 生成/编排留在概念 Agent，LangGraph 戏份落对位置 |
| D2 | 知识库隔离 | `user_file` 加 `owner_type`（personal/org）+ `org_id`（可空）列；`rag_chunk` 不动（JOIN 过滤） | 最小 schema 改动；rag 从"个人知识库"升级为"组织知识库"，多租户故事可讲 |
| D3 | 文件入库 | rag 新增**服务对服务入库 API**（内部密钥 + multipart），club Java 推送 | rag Python 侧无入库入口（v2 删了）；club 复用 rag 完整解析管线（parse_tasks 异步） |
| D4 | 文件检索 | rag 新增**纯检索 API**（query + org_id + top_k → chunks） | 现有 `retrieve()` 包一层 + 鉴权，改量小 |
| D5 | 双检索源 | experience_entry 保持 club SQL 检索；文件走 rag；**概念 Agent 工具合并两路结果** | 短精条目 SQL 足够；长散文件向量主场；不互相稀释 |
| D6 | 鉴权链 | club Python 工具 → club Java（社团校验）→ rag（内部密钥）；Python 不直连 rag | 维持"权限在 Java、Python 无状态"架构原则 |
| D7 | 复盘报告 | 阶段 2 以文本直接推 rag 入库，不做"文件化" | 已是文本，直接向量化；文件化是展示需求非检索前提 |
| D8 | 删除语义 | club 软删文件时调 rag 软删 API（`user_file.status=0`） | 检索过滤 status=1，删了必须查不到 |

## 4. rag 侧改造点

### 4.1 隔离维度（D2）

- `user_file` 加列：`owner_type VARCHAR(10) NOT NULL DEFAULT 'personal'`、`org_id BIGINT NULL`
- 索引：`CREATE INDEX idx_user_file_org ON user_file(org_id) WHERE owner_type='org' AND status=1`
- `retriever.py` 两处 SQL（`_vector_search` / `_bm25_search`）过滤条件从单 `user_id` 改为双分支：
  ```sql
  AND ( (uf.owner_type='personal' AND uf.user_id=%s)
        OR (uf.owner_type='org' AND uf.org_id=%s) )
  ```
- 迁移脚本：`scripts/` 新增 `alter_org_space.sql`（幂等：`ADD COLUMN IF NOT EXISTS`）

### 4.2 入库 API（D3）

```
POST /api/org/ingest
Headers: X-Internal-Key（内部密钥）
Body: multipart/form-data: file（文件流）、org_id、filename、biz_type
Resp: {"file_id": 123, "status": "parsing"}   # 异步解析，不等待
```

- 服务内部：创建 `user_file`（owner_type='org', org_id）+ 复用 `parse_tasks` 异步解析 → `rag_chunk`
- 鉴权：`X-Internal-Key` 校验（复用现有内部密钥机制），**不要求 X-User-Id**（org 语义替代个人语义）

### 4.3 软删 API（D8）

```
POST /api/org/files/{file_id}/deactivate
Headers: X-Internal-Key
Body: {"org_id": 123}
Resp: {"ok": true}
```
- 校验 `file_id` 属于该 org 后置 `status=0`（软删，检索立即不可见）

### 4.4 检索 API（D4）

```
POST /api/org/retrieve
Headers: X-Internal-Key
Body: {"query": "...", "org_id": 123, "top_k": 8}
Resp: {"items": [{"file_id", "filename", "page_no", "heading_path", "content", "chunk_type"}], "total": n}
```

- 实现：`retriever.retrieve(org_id=..., query=..., top_k=...)` 包一层；**不接生成**
- 返回字段含 `filename/page_no/heading_path`：概念 Agent 引用时可标注来源（来源文件名/页码）

### 4.5 不改的部分

- 生成式 `/api/qa/ask`、个人文件域（user_id 路径）、评估/反馈/管理接口——全部不动
- 个人知识库检索 SQL 保持原样（`owner_type='personal'` 分支等价旧行为）

## 5. club 侧改造点

### 5.1 RagClient（Java 组件）

- 新建 `config/RagClientFactory.java`（复制 PythonClientFactory 模式）：DCL 懒初始化 RestClient + `X-Internal-Key` 默认头 + `base-url` 配置（`rag.base-url`，env `RAG_BASE_URL`）
- 方法：`ingestFile(file, orgId)` / `deactivateFile(fileId, orgId)` / `retrieve(query, orgId, topK)`

### 5.2 活动文件库（D3/D8）

- 表 `activity_file_lib`：
  ```
  id BIGSERIAL PK, club_id, activity_id（可空=社团级通用资料）, uploader_id,
  filename, file_size, storage_url, rag_file_id（可空）, rag_status（pending/parsed/voided）,
  status（1正常 0已删）, created_at
  ```
- 接口（Controller `ActivityFileLibController`，前缀 `/clubs/{clubId}/activities/{id}/lib`）：
  - `POST /upload`：管理层（`activity:manage`）→ StorageService 落盘 + 落表 + 调 rag 入库（异步，失败标记 rag_status=failed 可重试）
  - `GET /list`：管理层/成员可见列表（成员只读）
  - `DELETE /{libId}`：管理层 → 软删 + 调 rag 软删
- 上传校验：复用 `AbstractStorageService.validate`（大小/扩展名白名单）

### 5.3 检索接口（D6）

- `ExperienceService`（或新 `KnowledgeService`）新增 `/ai/knowledge`：
  ```
  GET /clubs/{clubId}/ai/knowledge?q=...&topK=8
  权限：@ClubPermission(activity:manage)（概念 Agent 由发起人驱动）
  → club 侧 SQL 经验检索（现有 selectForAgent）+ RagClient.retrieve(orgId=clubId)
  → 返回 {"sql_items": [...], "file_items": [...], "similarActivityCount": n}
  ```

### 5.4 概念 Agent 检索工具（D5）

- Python `tools/experience.py` 升级（或新增 `tools/knowledge.py` 并入 `CONCEPT_TOOLS`）：
  - 调 `java_get("/clubs/{club_id}/ai/knowledge", params={"q": query})`
  - 输出三要素（对齐 B1 模式）：【数据水位】【历史经验命中（SQL）】【文件资料命中（rag，含文件名/页码）】
  - 联网兜底保留（水位低时）
  - K20 铁律：永不抛异常，失败降级提示文案
- 编排策略复用现有 SYSTEM_PROMPT（水位判断 + 覆盖度不足改写重查，上限 2 次）

### 5.5 前端

- 活动详情页新增"活动资料"区块：上传按钮（管理层）+ 文件列表（名称/大小/时间 + 管理层删除）
- 最小实现：Element Plus 上传组件 + 列表；不做分页/搜索（资料量级小）

## 6. 评估方案（方法论延续，证据链）

**原则**：rag 的"一切优化有数据背书"延续到集成——检索质量必须有数字。

- **评估集**：从真实活动文件/复盘提炼 15-20 个"历史经验问题"（如"上次骑行活动的预算偏差""徒步遇到过什么风险"），每题标注答案所在文件
- **指标**：`Recall@k`（top8 内是否命中标注文件）、`MRR`
- **脚本**：`scripts/debug/verify_club_knowledge_eval.py`（club 仓库），复用 rag 的评估思路但不进 rag 的 eval 框架（避免污染 rag）
- **目标线**：Recall@8 ≥ 0.7
- **消融（可选）**：草案引用率——同一问题，无检索 vs 有检索的草案中"引用历史经验"的比例

## 7. 部署与资源

- **本地开发**：同机运行（16GB 内存无压力）；rag 8090/8091 + club Java + club Python 并存
- **4G 服务器（风险项）**：
  - rag 本地模型：embedding（bge-base int8 ~313MB）+ rerank（~1GB 级）≈ 1.3GB+，加上 rag 双服务 + club Java + club Python，**4G 内存紧张**
  - 决策：**部署期专项评估**，备选：① rerank 降级（检索 API 可配 use_rerank=false，走 RRF 原始分，与现有降级路径一致）② 服务器内存升级 ③ rag 只部署主服务+检索所需（问答服务 8091 暂不部署——本集成只用检索，8091 可省！）
  - 注意 ③：**本集成只消费 rag 的检索能力，问答服务 8091 和生成管线可不部署**，这是资源上的一大节省
- 环境变量：rag 侧 `X_INTERNAL_KEY` 共享给 club（`RAG_INTERNAL_KEY`）；club 侧 `RAG_BASE_URL`

## 8. 风险与决策记录

| 风险 | 等级 | 缓解 |
|---|---|---|
| rag schema 变更（user_file 加列）影响个人知识库 | 中 | 双分支 SQL 保持个人路径行为不变；回归跑 rag 现有测试 |
| 异步入库与检索时序（文件刚传就检索查不到） | 低 | 概念 Agent 检索不到时提示"资料未入库/未解析"；数据水位信号天然覆盖 |
| 4G 服务器内存不足 | 中 | §7 备选方案（不部署 8091 + rerank 可关） |
| club 文件删除与 rag 块一致性 | 低 | 软删语义统一（status=0 检索即不可见）；rag_file_id 留痕可对账 |
| rag 独立仓库被改动 | 低 | 改动收敛在 3 个文件（user_file 迁移 + retriever.py + 新增 org API 模块）；rag 测试全绿后才算通过 |

## 附：面试叙事要点（方案配套）

- **主线**："业务沉淀知识、知识反哺业务"闭环（§0）
- **技术细节展开点**：rag 多租户升级（个人 → 组织）、检索器 vs 应答器的取舍、双检索源分离、权限链（Python 无状态信使）、评估方法论延续
- **可防御追问**：
  - "为什么文件走 rag、经验条目不走？" → 检索形态匹配：短精条目 SQL 足够，长散文件向量主场；塞一起互相稀释（D5）

  - "隔离怎么做的？" → user_file 加 owner_type/org_id，双分支 SQL，个人路径行为不变（D2）
  - "评估数据哪来的？" → 15-20 题真实文件评估集，Recall@8 指标（§6）
