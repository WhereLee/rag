# 性能优化与扩展方案

> 原则：**实事求是，数据驱动**。不吹嘘高并发，讲清楚每一层的现状、手段、收益与触发条件；所有参数以黄金集与压测实测为准，不拍脑袋。
>
> 定位：面试叙事主线的"优化与扩展"部分，配合 `docs/高并发计划.md` 使用。

## 一、基线事实（先立"知道自己在哪"）

| 事实 | 数据 |
|---|---|
| 硬件 | 单机 4 核 Xeon 2.5GHz / 3.6G 内存，本地 CPU 推理 |
| 链路实测 | embedding 17-31ms（10 并发 42ms 全算完）；rerank 单次 0.75s（top6）~3.4s（top50）；LLM 生成 5-15s |
| 质量基线 | 黄金集 40 题 MRR 0.8438 / recall 0.8438 / precision 0.7695（评估器已切新链路，真实可信） |
| 天花板 | LLM 外部配额 100 RPM——锁死 QPS 上限，**但锁不死延迟/降级率/稳定性**（这就是优化空间） |

### 当前已知问题（2026-08 实测）
- **ONNX 线程数过订阅**：`ONNX_THREADS=8` 跑在 4 核上（8 线程 × 1 实例 > 4 物理核），OS 上下文切换浪费；已拆分配置并校准（见下文第二层 ①）。
- rerank 信号量 1 时并发 6 排队放大 3.8 倍（p50 0.75s→2.9s）——已改为 2。

## 二、三层优化方案

### 第一层：已落地（代码里已有，面试先讲这些）

1. **FastAPI 假并发修复**：async 端点内同步阻塞（embedding/rerank）独占事件循环，一个慢请求卡全站。已改线程池 + 队列桥接（实测 2 并发 2.0s vs 串行 4.0s）。
2. **rerank 候选 50→20**：黄金集 MRR 完全一致（0.8906@32 题口径），单题延迟降 5.8 倍；模型 v2-m3→base 内存省 277MB。
3. **信号量限流 + 降级路径**：rerank 排队超时降级 RRF 不阻塞链路；低分剔除线 -5（跨查询可比 logits）+ BM25 强命中保护（字面关键词命中不被误杀）。
4. **两级缓存**：L1 精确命中零成本；L2 语义近重复复用；Redis 语义缓存；跨用户同 blob 安全复用；文件变更时缓存失效。

### 第二层：已实施（2026-08 落地）

| 项 | 动作 | 实测结果 |
|---|---|---|
| ① 线程数校准 | 拆分 `EMBED_THREADS`/`RERANK_THREADS`（默认跟随 ONNX_THREADS，服务器 .env 覆盖 4/2） | 实测：4 线程 × 1 并发优于 2×2（见下） |
| ② 信号量 1→2 | `RERANK_CONCURRENCY`（公式：推理线程数 × 并发实例 ≈ 物理核数；CPU 是共享池，CFS 调度非独占） | 实测调参：4 核服务器最终 4×1（见下） |
| ③ 级联 rerank | 双通道共识判据：RRF 融合 top1 同时在向量 top3 且 BM25 top3 → 免精排（`rerank_skipped=True`，高置信） | 黄金集 0/40 误跳；简单直问命中且 top1 与 rerank 一致 |
| ④ 压测基线 | `scripts/bench_retrieval.py` 并发直调 retrieve，采集 QPS/p50/p95/p99/降级率 | ✅ 已采集（下表） |

### 服务器压测实测（2026-08，4 核单机，8 文件语料，每轮 30s）

**RERANK_THREADS=2 × CONCURRENCY=2（2×2）**：

| 配置 | QPS | p50 | 降级率 | 级联跳过 |
|---|---|---|---|---|
| cascade=off / 4 并发 | 0.20 | 19.7s | 50% | 0 |
| cascade=off / 8 并发 | 0.38 | 16.1s | 60% | 0 |
| cascade=on / 4 并发 | 0.23 | 18.1s | **10%** | 30% |
| cascade=on / 8 并发 | 0.66 | 15.3s | 36% | **50%** |

**RERANK_THREADS=4 × CONCURRENCY=1（4×1，最终选择）**：

| 配置 | QPS | p50 | 降级率 | 级联跳过 |
|---|---|---|---|---|
| cascade=off / 4 并发 | 0.26 | **12.5s** | **0%** | 0 |
| cascade=off / 8 并发 | 0.43 | 15.9s | 53% | 0 |
| cascade=on / 4 并发 | 0.46 | **9.9s** | **0%** | **50%** |
| cascade=on / 8 并发 | 0.54 | 15.5s | 42% | 33% |

**结论（数据驱动，推翻直觉）**：
- 2×2（吞吐导向）在 4 核上单次推理太慢（p50 19.7s）→ 降级率 50%；4×1（单次快）p50 12.5s、4 并发内 0 降级。**单次推理速度是延迟与降级率的决定性因素**，并发实例数次之。
- 级联在真实查询集（黄金集+变体）命中 30-50%，降级率减半（50%→10%、60%→36%），QPS 0.20→0.66（8 并发）——**免精排是 4 核服务器上最有效的降载手段**。
- 8 并发降级（53%/42%）是超卖保护的正确行为（降级 RRF 优于无限排队），当前规模（≤4 活跃用户）0 降级。

级联判据的两次修正（教训沉淀）：
- **不能用"分数差距"**：RRF 分是排名倒数和，相邻名次分差极小，不代表确定性；双通道共识（语义 × 字面正交检索器一致）才是强信号。
- **必须排除低质量块**：VLM 失败的图片块（`chunk_type=image`、"图片无法显示"占位）无资格代表共识——refuse 越界题实证：query 词面命中图片占位块，双通道同时被骗；rerank 的价值恰恰是纠错这种误排，跳过它必须有强证据背书。

### 第三层：扩展路径（突破天花板，从便宜到贵）

| 序 | 手段 | 收益 | 成本/触发条件 |
|---|---|---|---|
| 1 | LLM 多 key / 多模型负载均衡 | RPM 100 是单 key 上限，多 key 摊开 | 配置级，先做 |
| 2 | 缓存扩容（Redis 持久化 + 热点预热） | 热点问题零 LLM 成本 | 命中率数据触发 |
| 3 | GPU 独立服务（embedding/rerank 卸载） | 推理秒级→毫秒级，同时释放 4G 内存压力 | 新增实例，数据触发 |
| 4 | 多实例横向扩展（Python 多副本 + 网关 LB） | rerank 并发随副本数线性涨 | 单机饱和后 |
| 5 | 私有化 LLM（开源模型 + GPU） | 摆脱 RPM 天花板 | 最贵，最后做 |

## 二.5、全链路分层压测（2026-08，20 文件语料，两套数据）

> 用户要求两套数据：**① 逐环节极限压测**（每环节单独打满找上限）；**② 日常混合流量模拟**（按真实用户行为比例混合，不含登录/注册密集）。

### 第一套：逐环节极限压测（每环节 15-30s 稳态）

| 环节 | 实测 | 结论 |
|---|---|---|
| 网关·文件列表 GET | QPS 1590 / p50 4.6ms / p99 11.3ms | Java 网关无瓶颈 |
| 网关·问答代理 GET | QPS 740 / p50 10.5ms / p99 17.4ms | 同上 |
| 网关·登录 POST | 单发 112ms（**IP 限流 3 次/分钟，不可也不应压测**） | 防爆破设计正确 |
| 数据库·count/点查/HNSW/联查 | QPS ~56，p50 ~140ms | **psql CLI 进程启动开销主导**（每次查询起一个进程）；真实连接池链路更快，见检索层 |
| 缓存·Redis GET | QPS 5324 / p50 1.2ms / p99 5.0ms | 无瓶颈 |
| 缓存·Redis SET | QPS 4673 / p50 1.4ms / p99 5.8ms | 无瓶颈 |
| 检索层（见下表） | rerank 是唯一 CPU 瓶颈 | 单次 5-20s @ 4 核 |
| 问答链路（MiMo 100RPM 受限） | 正常回答 18-22s（检索 0.2-8s + LLM 生成 8-18s）；**拒答路径 0.9-4.5s（不调 LLM）** | LLM 是外部配额瓶颈，DeepSeek 2500RPM 到位后重测高并发 |

**检索层（20 文件语料 / 48 查询 / 每档 30s / 4×1 生产配置）**：

| 配置 | QPS | p50 | p95 | 降级率 | 级联跳过 | 空结果 |
|---|---|---|---|---|---|---|
| cascade=off / 4 并发 | 0.21 | 14.9s | 25.5s | 0% | 0% | 1 |
| cascade=off / 8 并发 | 0.36 | 18.6s | 28.4s | 43.8% | 0% | 3 |
| cascade=on / 4 并发 | 0.26 | 15.6s | 24.7s | 15.4% | 38.5% | 0 |
| cascade=on / 8 并发 | 0.38 | 20.5s | 26.6s | 47.4% | 21.1% | 2 |

语料 8→20 文件后延迟上升（p50 9.9s→15.6s on/4）：BM25 检索范围与 embedding 候选池变大，rerank 输入增加；**级联仍是最有效降载手段**（4 并发 38.5% 免精排、QPS 提升 24%）。样本量小（9-19 请求/档）波动大，趋势可信、绝对值参考。

### 第二套：日常混合流量模拟（4 并发 × 120s，真实行为比例）

模型：登录 1 次/分钟（低频）+ 上传 1 次/分钟（即传即删）+ 浏览 60% + 问答检索 40%（检索直调，LLM 段单独测）。

| 类型 | 请求数 | QPS | p50 | p95 | p99 | 错误率 |
|---|---|---|---|---|---|---|
| 登录 | 2 | 0.02 | 122ms | 122ms | 122ms | 0% |
| 上传+删除 | 2 | 0.01 | 160ms | 160ms | 160ms | 50%（1 个 500，见坑位 #53） |
| 文件浏览 | 264 | 2.2 | 26.1ms | 111.9ms | 1033.9ms | 0% |
| 问答检索 | 149 | 1.24 | 2.37s | 7.04s | 7.53s | 0% |
| **总体** | 417 | **3.48** | - | - | - | **0.24%** |

**结论**：4 个活跃用户的日常场景（总 QPS 3.48）系统完全稳定——浏览秒回（26ms）、问答检索 p50 2.4s（4 并发内级联跳过 + rerank 排队不显著）、登录/上传低频无压力。**瓶颈归因一句话：网关/Redis/DB 远未饱和（QPS 数百-数千 vs 需求个位数），rerank 是唯一 CPU 瓶颈，LLM 100RPM 是唯一外部配额瓶颈。**

### 压测产出物
- `scripts/bench_infra.py`：网关/DB/缓存分层压测（--gateway/--db/--cache）
- `scripts/bench_retrieval.py`：检索层并发压测（已有，支持 --queries 自定义查询集）
- `scripts/bench_qa.py`：问答链路 SSE 阶段分解（TTFT/检索/LLM 生成/引用）

## 三、面试叙事线

> **"我实测了"** → 三层瓶颈数据（embedding 轻 / rerank 串行 / 事件循环阻塞最致命）
> **"我修了什么"** → 假并发修复、候选数砍半、信号量控制、降级路径、缓存体系、级联免精排
> **"天花板在哪"** → LLM 100 RPM 是外部配额，但延迟/降级率/稳定性是可优化的（LLM 锁死是分析结论，不是不做的借口）
> **"突破怎么办"** → 多 key → GPU 卸载 → 多实例 → 私有化 LLM，每层有成本/收益判断

### 关键追问弹药

- **"为什么信号量是 2？"** → 公式：推理线程数 × 并发实例 ≈ 物理核数，4 核 = 2×2 饱和；且 CPU 是共享池（CFS），线程数只是软限流不是独占核
- **"级联怎么保证不误跳？"** → 双通道共识（正交检索器一致）+ 黄金集实测 0 误跳 + 低质量块排除；误跳兜底：可收紧共识窗口 top3→top2
- **"为什么不直接上 GPU？"** → 成本/资源判断：当前规模 CPU 够用；GPU 是数据触发的下一步（延迟/降级率数据支撑时引入）
- **"压测结果呢？"** → 实话实说：检索层压测基线已采集（QPS/降级率）；全链路被 LLM RPM 锁死是天花板分析结论，不是掩盖
- **"内存预算？"** → 模型常驻内存是固定成本（与并发无关），CPU 调度才是瓶颈；4G 预算：PG 0.5G + Java 1.5G + Python 1.0G + 系统 0.5G ≈ 3.5G

## 四、监控与回退

- **质量回归**：黄金集 MRR ≥ 0.88（当前 0.8438@40 题口径）；每轮检索层改动必须跑
- **降级率监控**：压测与线上日志统计 rerank 降级占比，>5% 报警
- **回退开关**（全 env 可配）：`RERANK_CONCURRENCY`、`EMBED_THREADS`、`RERANK_THREADS`、`CASCADE_TOP_K`；级联误判可收紧窗口或 `CASCADE_TOP_K=0` 关闭
